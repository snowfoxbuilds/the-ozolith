# ADR-0052: The Codex Agent adapter — per-tool compiled knowledge, adapter-derived bake targets, and PROBE + STATIC identity

## Context

The architecture always promised adapter pluggability — ADR-0044 calls the Agent adapter "the variable", ADR-0009 reserved `agents/<tool>/` namespaces "so Codex/Pi compilers have a home", AGENTIC-CODING-PIPELINE.md's upgrade path is "a new model or agent is a new adapter image" — but only one of everything existed: one adapter (`ClaudeAdapter`), one identity module, one knowledge compiler, one run base image, one hardcoded bake target (`/home/ozolith/.claude/` in the node daemon). The goal is a `codex-review` Reviewer worker type running the OpenAI Codex CLI headless, so PRs get reviewed by a non-Claude model.

The genuinely adapter-agnostic surfaces needed **no changes**: the Reviewer driver, the Output Proposal machinery (ADR-0046), dispatch, the secret delivery path, the daemon's build orchestration, and control's worker-type validation (which already delegated every model/effort question to the adapter registry). The work was everything behind those seams, plus two structural holes the seams could not reach: ingest compiled knowledge for exactly one tool with no tool parameter, and the daemon's knowledge bake target was a constant.

Codex facts the design rests on (verified live on codex-cli 0.150.0): the CLI has **no managed-policy config tier** — its only configuration is `$CODEX_HOME/config.toml`, and the CLI *writes* into `CODEX_HOME` at runtime (auth.json, session rollouts, sqlite state). `codex exec --json` emits a JSONL event stream (`thread.started` / `turn.started` / `item.*` / `turn.completed` / `turn.failed` / `error`) that **carries no model signal** — but the CLI's own session rollout journal (`CODEX_HOME/sessions/**/rollout-*.jsonl`) writes a `turn_context` record per turn carrying the `model` and `effort` the turn ran under, and the baked config values flow through it verbatim. Codex consumes the same `skills/<name>/SKILL.md` format the knowledge tree already uses, and `codex login --device-auth` supports a browserless one-time login.

## Decision

### 1. The codex knowledge compiler (amends ADR-0009)

`knowledge/src/theozolith_knowledge/codex.py` compiles a knowledge root for codex, registered beside the claude compiler in a new `compilers.py` registry (`COMPILERS`) that sync, the CLI's `--tool`, the bake, and control's ingest all dispatch through. The mapping:

- `AGENTS.md → AGENTS.md`, **verbatim, no generated marker**. Claude's `CLAUDE.md` carries a marker because it is a *derivative* of `AGENTS.md`; for codex the vendor file IS the canonical format — a "generated from AGENTS.md" comment inside a file named AGENTS.md would mislead and burn context every session. Managed-ness is carried by the sync manifest and, in the pinned build, by the per-tree pins.
- `skills/<name>/ → skills/<name>/`, verbatim — codex consumes the same skills format natively.
- `agents/codex/<n>.md → prompts/<n>.md` (codex custom prompts). `agents/codex/` now loads as `codex_agents` on the knowledge root and counts as root content.
- `workflows/` has no codex target and is **deliberately dropped**, silently in the compiler (a pure root → FileSet function; per-ingest nagging on every shared tree was rejected) and visibly in `theozolith-knowledge validate`'s per-tool section counts.
- **Global scope only**; project scope raises. In project scope the knowledge root *is* the project repo, whose `AGENTS.md` already sits exactly where codex reads it — the transform degenerates into a self-copy — and codex custom prompts have no project-scope home. Every deployment path (ingest compile, node bake) is global-scope, so nothing is lost; revisit if codex grows a project config dir.

### 2. Ingest compiles every tree once per registered compiler (amends ADR-0048)

`theozolith config ingest` compiles each `knowledge/<name>` source tree once per compiler in the registry, into `knowledge/<name>/<tool>/` in the pinned build, with one pin per (tree, tool) keyed `"<name>/<tool>"` in the flat `[knowledge]` table. The pinned build stays a **pure function of the knowledge source** — ingest still never inspects which worker types reference a tree (the alternative, fanning out from referencing types, would make compiled content a function of the worker-type set and add an ordering coupling for negligible savings). An empty per-tool fileset writes no directory and records no pin; a worker type joining an absent pin fails config load with an actionable error naming the tool and the re-ingest fix.

**No fleet retag.** `knowledge_tree_hash` computes relpaths relative to the tree root, so the claude compile moving one level down keeps every claude pin value byte-identical; the identity-hash goldens and a dedicated migration test are the proof. Worker types join `pins.knowledge["<tree>/<adapter>"]`; a legacy bare `"<name>"` key (pre-per-tool pinned build) normalizes to `"<name>/claude"` at load — the only compiler that could have written it — and the compiled-tree presence check accepts the bare legacy layout for claude types. **`theozolith update` does not re-ingest**, so these shims are what let new control code serve an old pinned build; the layout converts on the operator's next `theozolith config ingest` (a no-op source re-ingest migrates it eagerly — the recommended post-update step), and since a codex worker type can only enter the system via an ingest, codex is never live against a legacy layout.

### 3. Adapter-derived bake targets; the daemon stays adapter-blind (amends ADR-0044/0045/0048)

The wire recipe grows from 8 to 10 keys: `knowledge_tool` (which per-tool compile the node stages) and `knowledge_target` (where the bake COPY lands), both computed control-side from the worker type's adapter via a static map (`claude → /home/ozolith/.claude/`, `codex → /home/ozolith/.codex/`; an unmapped adapter with baking knowledge fails config load). The daemon stages the subtree it is told — falling back to the bare tree for a legacy dist or an older control — and COPYs to the path it is told, with fail-closed shape checks (absolute `/home/ozolith/` directory path, plain tool name) that defer the build rather than bake to a bogus path. The pin verification remains the correctness gate on every path: control pinned exactly the bytes the build must consume, so old-daemon/new-dist skew defers visibly (ADR-0042 advisory doctrine) and never bakes wrong bytes.

The identity hash gains a `knowledge_target` key **only when it differs from the historical claude default**. This amends ADR-0045's "exactly these four keys" doctrine deliberately and minimally: a non-default COPY destination is a Dockerfile byte and therefore identity-bearing, while every pre-ADR-0052 claude identity hashes byte-identically — nothing retags on upgrade. (An unconditional fifth key was rejected: it would retag every derived image fleet-wide for zero information.)

The node's deck-facing knowledge export serves the **claude view** of each tree (`export/<name> := dist/knowledge/<name>/claude/`, legacy bare fallback): Flight Decks are claude-only (ADR-0043's machinery is claude-shaped end to end), so the deck mount contract — `CLAUDE.md` at the tree root — never changes across the migration. Control refuses a driverless type with a non-claude adapter that declares knowledge (it could never read the export) or a model/effort (the interactive materialize scope exists only on the claude adapter — the codex adapter also rejects it in-image as the backstop). A codex Flight Deck is recorded as future work.

### 4. The CodexAdapter and PROBE + STATIC identity (amends ADR-0045)

`CodexAdapter` (worker `adapters.py`) + `codexidentity.py` implement the second adapter. Because codex has no managed tier and needs `CODEX_HOME` writable, the baked identity is **theozolith-owned**: `materialize` writes the well-known files plus a root-owned `etc/theozolith/codex/config.toml` (`model`, and `model_reasoning_effort` when an effort is ever proven) — never anything under `~/.codex` (image bytes must not be runtime-writable), with the same symlink-safe atomic write discipline, a conflict scan that refuses to overwrite operator selection keys, and a prepend-merge that preserves unrelated operator TOML. Instruction-discovery keys (`project_doc_fallback_filenames`) are refused in the baked config wherever it is read — the bake-time conflict scan, the per-Run identity static checks, and the identity reader on model-less images — because the Reviewer removes a fixed instruction-file name set (`AGENTS.override.md`, `AGENTS.md`, and the Claude names) from review checkouts, and a baked config able to extend codex's project-doc discovery would silently reopen that involuntary instruction channel; the pipeline's canonical instruction file is AGENTS.md, never a configured alias (amended 2026-08-27, #85). `prepare()` assembles a **fresh throwaway `CODEX_HOME` per Run**: the baked config copied byte-for-byte, the credential written as a 0600 `auth.json` — session state dies with the container, no cross-Run persistence channel. The headless argv is `codex exec <pointer> --json --skip-git-repo-check --sandbox danger-full-access` (the run container IS the sandbox, ADR-0013; codex's own Landlock sandbox is unavailable inside it); nothing on the argv selects a model.

The identity doctrine is **PROBE + STATIC** (operator ruling) — necessarily weaker than Claude's, held honestly:

- **One driver-boot probe** (the existing dry-run mode): static checks, the CLI version floor (`codex-cli 0.150.0` — the `--json` schema, the rollout journal, and exec-mode config binding were verified on it), then one neutral `codex exec` in a throwaway home whose **post-exit rollout journal** must attribute the session to the baked model. Strict: no `turn_context` record means the observation channel itself is broken, and setup is the time to learn that.
- **Per-Run static checks**: baked config still selects the declared identity and carries no foreign steering keys; environment audit over `CODEX_HOME`, `OPENAI_API_KEY`, `OPENAI_BASE_URL` (the credential `CODEX_AUTH_JSON` is deliberately not steering).
- **A benign per-Run observer, no live kill**: the session monitor records the rollout's observed model/effort into evidence at exit and never reports a violation. A detected post-exit mismatch is **evidence, not a failure lane** (pure PROBE + STATIC; escalating it to the Reviewer identity lane is one sentence in a future amendment if wanted). The `stream_stats` model is empty with a note saying why — the rollout is the model source.
- **Effort ships locked**: `turn_context.effort` echoes the *configured* value, not a proven post-clamp one, so no (model, effort) pair is provably enforceable yet — the codex capability table is empty and every nonempty effort fails config load and the build with a message naming spike #76 S7, whose per-model evidence adds rows. The materialize/static/probe/rollout machinery is effort-ready.

Accepted gaps, stated: `-m`/`-c`/`--profile` at invocation would steer, exactly like Claude's `--model` gap — the harness passes none, and out-of-harness invocation is outside the threat model; mid-session steering that leaves no rollout trace is undetectable and recorded as the doctrine's gap; the observed-model channel is same-user filesystem state (fail-loud only, like Claude's capture files).

### 5. The credential: the ChatGPT-plan auth document (validated in production rollout)

The codex adapter's single registered credential is `CODEX_AUTH_JSON` — the **full auth.json document** captured by a one-time `codex login --device-auth` — riding the existing path end to end: Fernet store → worker-type `[secrets]` slot → daemon tmpfs leaf → `<NAME>_FILE` → driver `agent_env` → bare `-e` into the run container → `prepare()`'s 0600 leaf. Zero new machinery; ADR-0013's doctrine intact (a rotatable spend credential, revocable by `codex logout` / the account's device list). A prepare that cannot deliver its preconditions (missing credential) is now a clean pre-session infra status, not a harness crash. The cache-volume guard refuses `.codex` paths exactly as `.claude` (a persistent volume there would carry config, auth, and history across Runs).

This is **design (a)**, adopted as primary. **Pre-merge spike execution is intentionally waived** (operator ruling): the S1–S8 procedure needs the operator's ChatGPT-plan login and a Docker host, so **production rollout is the validation environment** — the first deployed codex-review Runs are where headless plan auth (S2's question) and stored-copy survival across token rotation (S4's question) are actually observed. Authenticated lifecycle behavior has NOT been validated by this change: the local smoke test reached exactly the authentication boundary (a clean `failed:unavailable` on a 401), no further. The harness, procedure, and sanitized-evidence checklist ship in `spikes/issue-76-codex-plan-auth/` as **post-deployment observations** — run them (or record the equivalent from production Run evidence) on issue #76 so the answers are durable. If rotation invalidates the stored copy (S4's question answered no), the recorded fallback is design (b): a persistent auth volume initialized by a one-time in-container login — a secret-delivery class outside the Fernet path whose ADR-0013 deviation and volume-concurrency limits would need their own amendment. If headless plan auth fails outright (S2 answered no), plan auth is unsupported headless and API-key auth becomes the question (note: `OPENAI_API_KEY` sits on the steering blocklist today; adopting it as a credential flips that entry and the credential map together).

### 6. The base image and the publish matrix (rides ADR-0051)

`worker/docker/Dockerfile.codex` mirrors the claude run image with two deliberate divergences: the CLI install is **pinned to exactly `CodexAdapter.MIN_ENFORCING_CLI`** (the experimental `--json` schema and rollout format are the contract the parsers speak — the pin is the policy, the floor the backstop, a deploy test keeps them in lockstep, and a bump re-runs the spike's fixture captures), and no standalone knowledge bake (derived images bake the per-tool tree at the node). CI's `run-image` and `publish-run-image` jobs become a per-agent **matrix** — ADR-0051's write-once / tip-re-check / `:main`-repair machinery is written once and parameterized, with per-image cache scopes and per-image FIFO concurrency groups (each registry ref's monotonic ordering is its own). One-time op note: the `theozolith-run-codex` GHCR package needs the repo Actions grant if it is ever first created by hand.

### 7. The example ships both reviewers; the race is documented, not routed

`deploy/configs-example` gains `codex-review` (worker type + stopped Stack): the same Reviewer driver, its own GitHub identity (no self-grading, ADR-0008), the plan credential, and the **same knowledge tree** as the claude types — one tree, two compiled views, per-tool pins retagging exactly the types whose view changed. Reviewer discovery has no per-PR claim, so two *running* reviewer Stacks race on the same pr_ready pool (first launcher wins; simultaneous polls can double-review). Accepted per operator ruling: run one at a time for deterministic coverage, or treat a double review as a second opinion. Deterministic routing would be new claim machinery (ADR-0017 territory) and is explicitly out of scope.

## Consequences

- A PR can now be reviewed by a non-Claude model with the identical driver, verdict, and evidence machinery; the Reviewer driver needed zero changes, which is the ADR-0044 promise kept.
- One knowledge tree serves both adapters with per-tool selective retagging; claude pins, tags, and deck mounts are untouched by the migration, which self-applies on the next ingest.
- Codex identity is honestly weaker than Claude's: probe + static + post-exit evidence, no live kill, effort locked until proven. The evidence record states what ran; the doctrine states what is not checked.
- Compat shims (legacy pin keys, bare-layout presence check, daemon staging/export fallbacks) carry the migration window and should be deleted once pre-ADR-0052 pinned builds are out of support.
- Spike #76's S1–S8 procedure (login, headless exec, rotation, stale-copy recovery, stream fixtures, sandbox matrix, per-model config binding) is deliberately **not a pre-merge gate**: production rollout validates the credential design, and the checks remain the post-deployment observation procedure — its recorded answers add capability-table rows (S7) or trigger the design-(b) amendment (S4's question answered no).
