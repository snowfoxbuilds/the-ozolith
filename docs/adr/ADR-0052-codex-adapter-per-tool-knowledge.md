Status: ACCEPTED

Date: 2026-08-26

# ADR-0052: The Codex Agent adapter — per-tool compiled knowledge, adapter-derived bake targets, and PROBE + STATIC identity

## Context

The architecture always promised adapter pluggability — ADR-0044 calls the Agent adapter "the variable", ADR-0009 reserved `agents/<tool>/` namespaces "so Codex/Pi compilers have a home", AGENTIC-CODING-PIPELINE.md's upgrade path is "a new model or agent is a new adapter image" — but only one of everything existed: one adapter (`ClaudeAdapter`), one identity module, one knowledge compiler, one run base image, one hardcoded bake target (`/home/ozolith/.claude/` in the node daemon). The goal is a `codex-review` Reviewer worker type running the OpenAI Codex CLI headless, so PRs get reviewed by a non-Claude model.

The genuinely adapter-agnostic surfaces needed **no changes**: the Reviewer driver, the Output Proposal machinery (ADR-0046), dispatch, the secret delivery path, the daemon's build orchestration, and control's worker-type validation (which already delegated every model/effort question to the adapter registry). The work was everything behind those seams, plus two structural holes the seams could not reach: ingest compiled knowledge for exactly one tool with no tool parameter, and the daemon's knowledge bake target was a constant.

Codex facts the design rests on (verified live on codex-cli 0.150.0): the CLI has **no managed tier that can hold a model** — its identity-bearing configuration is `$CODEX_HOME/config.toml` (the system layer `/etc/codex/config.toml` sits *below* user config, and the constraint layer `/etc/codex/requirements.toml`, with the legacy `managed_config.toml` mapped into it, constrains sandbox, approvals, hooks, and a few operational keys but never the primary `model`; corrected 2026-09-04 from "no managed-policy config tier"), and the CLI *writes* into `CODEX_HOME` at runtime (auth.json, session rollouts, sqlite state). `codex exec --json` emits a JSONL event stream (`thread.started` / `turn.started` / `item.*` / `turn.completed` / `turn.failed` / `error`) that **carries no model signal** — but the CLI's own session rollout journal (`CODEX_HOME/sessions/**/rollout-*.jsonl`) writes a `turn_context` record per turn carrying the `model` and `effort` the turn ran under, and the baked config values flow through it verbatim. Codex consumes the same `skills/<name>/SKILL.md` format the knowledge tree already uses, and `codex login --device-auth` supports a browserless one-time login.

## Decision

### 1. The codex knowledge compiler (amends ADR-0009)

`knowledge/src/theozolith_knowledge/codex.py` compiles a knowledge root for codex, registered beside the claude compiler in a new `compilers.py` registry (`COMPILERS`) that sync, the CLI's `--tool`, the bake, and control's ingest all dispatch through. The mapping:

- `AGENTS.md → AGENTS.md`, **verbatim, no generated marker**. Claude's `CLAUDE.md` carries a marker because it is a *derivative* of `AGENTS.md`; for codex the vendor file IS the canonical format — a "generated from AGENTS.md" comment inside a file named AGENTS.md would mislead and burn context every session. Managed-ness is carried by the sync manifest and, in the pinned build, by the per-tree pins.
- `skills/<name>/ → skills/<name>/`, verbatim — codex consumes the same skills format natively.
- `agents/codex/<n>.md → prompts/<n>.md` (codex custom prompts). `agents/codex/` now loads as `codex_agents` on the knowledge root and counts as root content. Custom prompts are a **deprecated compatibility surface** (the official custom-prompts documentation deprecates them in favour of skills; amended 2026-09-04, #132): the mapping stays so existing compiled trees keep their view byte-stable, new reusable authoring goes into `skills/`, and retiring or migrating the `prompts/` target is recorded future work.
- `agents/codex/<n>.toml → agents/<n>.toml` (codex custom agent roles — the native `$CODEX_HOME/agents/*.toml` discovery surface; amended 2026-09-05, #140). A role file is a native codex subagent definition: the role metadata (`name`, `description`, `nickname_candidates`) flattened over a `config.toml` layer (`developer_instructions`, `model`, `model_reasoning_effort`, `sandbox_mode`, `mcp_servers`, `skills.config`, …). The file ships verbatim — never synthesised or rewritten — but the loader validates it first against the **supported codex baseline**, codex-cli 0.153.3, under a contract with three deliberately distinct parts. *Schema-valid* is what Ozolith decides: the metadata rules of codex's standalone role parser (`name`, `description`, and `developer_instructions` required and non-blank after codex's own trimming; the trimmed `name` unique across the root; nickname candidates trimmed, non-blank, unique, and limited to ASCII letters, digits, spaces, hyphens, and underscores), and the configuration layer against the `config.toml` JSON Schema codex generates from its `ConfigToml` type at that version, vendored verbatim into the knowledge package and pinned by digest — a closed top level, nested tables open or closed exactly as the schema says, every value typed as codex deserializes it, only the schema's canonical keys. Malformed TOML, unknown top-level or nested fields, wrong types, invalid nested values, and a symlinked or irregular `agents/` root, tool namespace, or source file all refuse, naming the file and the field. The refusal is the point: codex warn-and-skips a malformed role at startup, so an unvalidated file would silently shrink a deck's roster; ingest (and `theozolith-knowledge validate`) fails it loud once, and the compiled `agents/` folds into the tree pin like every other view file. *Parser-compatible* is wider and is not promised: codex's serde parser also accepts compatibility spellings absent from the generated schema — at 0.153.3 the aliases `agents.max_threads` and `memories.no_memories_if_mcp_or_web_search` — and Ozolith rejects them on purpose; authors write the canonical keys (`agents.max_concurrent_threads_per_session`, `memories.disable_on_external_context`). *Runtime-effective* is narrower: schema validity means codex can parse the setting and the view transports it, not that 0.153.3 applies it to the child. At that baseline the effective role overrides are exactly `developer_instructions`, `model`, `model_reasoning_effort`, `model_reasoning_summary`, `model_verbosity`, `personality`, `service_tier`, the supported feature disables, and the supported skill disables; `sandbox_mode` and `mcp_servers` are schema-valid and transported but are not effective role overrides, so the child inherits the parent session's runtime permission authority and a role's `sandbox_mode = "read-only"` is not an enforcement boundary on 0.153.3. Validation is offline and deterministic — nothing is fetched at ingest — and the baseline moves only by a deliberate, versioned update (a new vendored schema with its recorded tag and digest; the parser rules, the rejected aliases, and the effective override set re-read at that tag), so a key a newer codex adds is refused until the baseline moves. Ozolith imposes no allowlist of its own on top of the schema. Relative paths in the layer keep codex's semantics — resolved against the role file's directory, `$CODEX_HOME/agents/` in the view, and never checked for existence at load — so what they reference must exist in the environment the view is installed into. The file stem names the compiled file (a path slug); the trimmed TOML `name` is codex's identity for the role and may carry spaces. Nothing is synthesised from Markdown at container start.
- `hooks/ → hooks/`, verbatim (amended 2026-09-05, #140): `hooks/hooks.json` is required and must parse as a JSON object, and the scripts it references travel beside it with their executable bits; the event schema itself is codex's to enforce, and hooks run only under codex's persisted hook trust — the compiler ships configuration, never trust. `hooks/` is a codex-only section like `agents/codex/`: the claude compiler ignores both (claude hooks live in settings, which the ADR-0055 policy allowlist refuses), so adding either leaves every claude view and pin byte-identical. Linking `agents/` and `hooks/` from the view into `~/.codex` is the deck start script's job, exactly as for `AGENTS.md`, `skills/`, and `prompts/` (the operator's worker type in the Config Repo).
- `workflows/` has no codex target and is **deliberately dropped**, silently in the compiler (a pure root → FileSet function; per-ingest nagging on every shared tree was rejected) and visibly in `theozolith-knowledge validate`'s per-tool section counts.
- **Global scope only**; project scope raises. In project scope the knowledge root *is* the project repo, whose `AGENTS.md` already sits exactly where codex reads it — the transform degenerates into a self-copy — and codex custom prompts have no project-scope home. Every deployment path (ingest compile, node bake) is global-scope, so nothing is lost; revisit if codex grows a project config dir.

### 2. Ingest compiles every tree once per registered compiler (amends ADR-0048)

`theozolith config ingest` compiles each `knowledge/<name>` source tree once per compiler in the registry, into `knowledge/<name>/<tool>/` in the pinned build, with one pin per (tree, tool) keyed `"<name>/<tool>"` in the flat `[knowledge]` table. The pinned build stays a **pure function of the knowledge source** — ingest still never inspects which worker types reference a tree (the alternative, fanning out from referencing types, would make compiled content a function of the worker-type set and add an ordering coupling for negligible savings). An empty per-tool fileset writes no directory and records no pin; a worker type joining an absent pin fails config load with an actionable error naming the tool and the re-ingest fix.

**No fleet retag.** `knowledge_tree_hash` computes relpaths relative to the tree root, so the claude compile moving one level down keeps every claude pin value byte-identical; the identity-hash goldens and a dedicated migration test are the proof. Worker types join `pins.knowledge["<tree>/<adapter>"]`; a legacy bare `"<name>"` key (pre-per-tool pinned build) normalizes to `"<name>/claude"` at load — the only compiler that could have written it — and the compiled-tree presence check accepts the bare legacy layout for claude types. **`theozolith update` does not re-ingest**, so these shims are what let new control code serve an old pinned build; the layout converts on the operator's next `theozolith config ingest` (a no-op source re-ingest migrates it eagerly — the recommended post-update step), and since a codex worker type can only enter the system via an ingest, codex is never live against a legacy layout.

### 3. Adapter-derived bake targets; the daemon stays adapter-blind (amends ADR-0044/0045/0048)

The wire recipe grows from 8 to 10 keys: `knowledge_tool` (which per-tool compile the node stages) and `knowledge_target` (where the bake COPY lands), both computed control-side from the worker type's adapter via a static map (`claude → /home/ozolith/.claude/`, `codex → /home/ozolith/.codex/`; an unmapped adapter with baking knowledge fails config load). The daemon stages the subtree it is told — falling back to the bare tree for a legacy dist or an older control — and COPYs to the path it is told, with fail-closed shape checks (absolute `/home/ozolith/` directory path, plain tool name) that defer the build rather than bake to a bogus path. The pin verification remains the correctness gate on every path: control pinned exactly the bytes the build must consume, so old-daemon/new-dist skew defers visibly (ADR-0042 advisory doctrine) and never bakes wrong bytes.

The identity hash gains a `knowledge_target` key **only when it differs from the historical claude default**. This amends ADR-0045's "exactly these four keys" doctrine deliberately and minimally: a non-default COPY destination is a Dockerfile byte and therefore identity-bearing, while every pre-ADR-0052 claude identity hashes byte-identically — nothing retags on upgrade. (An unconditional fifth key was rejected: it would retag every derived image fleet-wide for zero information.)

The node's deck-facing knowledge export mirrors the per-tool layout of the applied distribution — `export/<name>/<tool>/ := dist/knowledge/<name>/<tool>/`, a legacy bare tree exported as `<name>/claude` — and control injects the deck's view path, `<name>/<adapter>`, as the `THEOZOLITH_KNOWLEDGE_TREE` selector, so the deck mount contract is one read-only parent plus one env var for every adapter: a claude deck finds `CLAUDE.md` at its view root, a codex deck finds `AGENTS.md`, `skills/`, native `agents/` roles and `hooks/` when the tree ships them (amended 2026-09-05, #140), and the deprecated `prompts/` compatibility surface (amended 2026-09-04). The selector change is an env delta that recreates each existing claude deck once at the upgrade — the same cost ADR-0055 charges for adopting a live surface. The daemon stays adapter-blind: it exports what the distribution holds and never chooses a view. Control refuses a driverless type that declares an effort (ADR-0045, every adapter); a driverless codex type declares knowledge and a model exactly as a claude deck does, and joins its tree's `<name>/codex` pin with the same compiled-tree presence check. A deck references whichever tree it likes; keeping a codex deck's tree separate from a claude deck's is the example's convention (the agent setups diverge), never a product rule — a tree is a layout compiled for every registered tool.

**The export layout change is a one-time breaking transition, never a rolling one (amended 2026-09-04, #132).** The daemon's export moves from the flattened claude view at `export/<name>/` to the per-tool layout `export/<name>/<tool>/`, and control's selector moves from `<name>` to `<name>/<adapter>`; the two halves are one contract and ship in one product release. Mixed Control and Node Daemon versions do not keep existing claude decks usable during the transition (operator ruling): a new Control with an old daemon selects `<name>/claude`, a path the old export never contains, so the deck start refuses the missing tree; an old Control with a new daemon selects `<name>`, which is now the parent of the views rather than the claude view root, and the start must refuse it too — the deck contract requires the adapter's view marker at the selected root (`CLAUDE.md` for claude, `AGENTS.md` for codex), and a bare directory test is not sufficient, because linking into the parent would silently give the deck no knowledge. That guard is the contract's third part, and it does not ship with the release: the start script belongs to the operator's Flight Deck worker type in the Config Repo, so it must land and be ingested before either product half moves — it is backward-compatible under the old selector and export — and an unguarded script paired with an old Control and a new daemon is the one pairing that links the views' parent silently (amended 2026-09-04, #137). With the guard in place, in either pairing a deck launch fails closed or the deck stays unavailable for the maintenance window; no pairing ever serves the wrong tree. Completion is a maintenance window, because the product's update flow cannot order Control ahead of the daemons: `theozolith update` commits the pin and fans the update out to every node in one call, each daemon self-updates on its next heartbeat, and the running Control service takes the new code only on its manual restart (ADR-0051) — so the daemons move first and Control last, the one order in which a running deck's old links dangle and an old Control recreates decks against the new export. In order: guard the start scripts in the Config Repo and ingest; drain every claude deck; run the product update and restart the Control service; wait for every deck-hosting daemon, the Control service, the config distribution, and the CLI pins to converge; verify the marker at the selected root on one recycled deck; recycle the rest — each deck is recreated once, after which `CLAUDE.md` resolves at the claude view root and `AGENTS.md` at the codex view root. Control first — the new selector failing each recreated deck closed until its daemon converges, no drain needed — is an alternative only where that order is actually guaranteed: a source checkout's install-only build on the Control host and a service restart before the pinning build (amended 2026-09-05, #137). Implementation tests must drive both incompatible pairings (each fails visibly without reading the other layout's tree) and the converged new/new case (both views resolve).

### 4. The CodexAdapter and PROBE + STATIC identity (amends ADR-0045)

`CodexAdapter` (worker `adapters.py`) + `codexidentity.py` implement the second adapter. Because codex has no managed tier and needs `CODEX_HOME` writable, the baked identity is **theozolith-owned**: `materialize` writes the well-known files plus a root-owned `etc/theozolith/codex/config.toml` (`model`, and `model_reasoning_effort` when an effort is ever proven) — never anything under `~/.codex` (image bytes must not be runtime-writable), with the same symlink-safe atomic write discipline, a conflict scan that refuses to overwrite operator selection keys, and a prepend-merge that preserves unrelated operator TOML. Instruction-discovery keys (`project_doc_fallback_filenames`) are refused in the baked config wherever it is read — the bake-time conflict scan, the per-Run identity static checks, and the identity reader on model-less images — because the Reviewer removes a fixed instruction-file name set (`AGENTS.override.md`, `AGENTS.md`, and the Claude names) from review checkouts, and a baked config able to extend codex's project-doc discovery would silently reopen that involuntary instruction channel; the pipeline's canonical instruction file is AGENTS.md, never a configured alias (amended 2026-08-27, #85). Interactive scope (a codex Flight Deck) writes only the well-known model file — no baked `config.toml`, nothing under `/etc/codex` or `~/.codex` — and refuses an effort like the claude adapter does; the deck's start script passes the file's value as `--model`, the baked model is a default the human may switch away from in-session (ADR-0045), and the deck's own `config.toml` on its state volume stays the human's (amended 2026-09-04). `prepare()` assembles a **fresh throwaway `CODEX_HOME` per Run**: the baked config copied byte-for-byte, the credential written as a 0600 `auth.json` — session state dies with the container, no cross-Run persistence channel. The headless argv is `codex exec <pointer> --json --skip-git-repo-check --sandbox danger-full-access` (the run container IS the sandbox, ADR-0013; codex's own Landlock sandbox is unavailable inside it); nothing on the argv selects a model.

The identity doctrine is **PROBE + STATIC** (operator ruling) — necessarily weaker than Claude's, held honestly:

- **One driver-boot probe** (the existing dry-run mode): static checks, the CLI version floor (`codex-cli 0.150.0` — the `--json` schema, the rollout journal, and exec-mode config binding were verified on it), then one neutral `codex exec` in a throwaway home whose **post-exit rollout journal** must attribute the session to the baked model. Strict: no `turn_context` record means the observation channel itself is broken, and setup is the time to learn that.
- **Per-Run static checks**: baked config still selects the declared identity and carries no foreign steering keys; environment audit over `CODEX_HOME`, `OPENAI_API_KEY`, `OPENAI_BASE_URL` (the credential `CODEX_AUTH_JSON` is deliberately not steering).
- **A benign per-Run observer, no live kill**: the session monitor records the rollout's observed model/effort into evidence at exit and never reports a violation. A detected post-exit mismatch is **evidence, not a failure lane** (pure PROBE + STATIC; escalating it to the Reviewer identity lane is one sentence in a future amendment if wanted). The `stream_stats` model is empty with a note saying why — the rollout is the model source.
- **Effort ships locked**: `turn_context.effort` echoes the *configured* value, not a proven post-clamp one, so no (model, effort) pair is provably enforceable yet — the codex capability table is empty and every nonempty effort fails config load and the build with a message naming spike #76 S7, whose per-model evidence adds rows. The materialize/static/probe/rollout machinery is effort-ready.

Accepted gaps, stated: `-m`/`-c`/`--profile` at invocation would steer, exactly like Claude's `--model` gap — the harness passes none, and out-of-harness invocation is outside the threat model; mid-session steering that leaves no rollout trace is undetectable and recorded as the doctrine's gap; the observed-model channel is same-user filesystem state (fail-loud only, like Claude's capture files).

### 5. The credential: the ChatGPT-plan auth document (validated in production rollout)

The codex adapter's single registered credential is `CODEX_AUTH_JSON` — the **full auth.json document** captured by a one-time `codex login --device-auth` — riding the existing path end to end: Fernet store → worker-type `[secrets]` slot → daemon tmpfs leaf → `<NAME>_FILE` → driver `agent_env` → bare `-e` into the run container → `prepare()`'s 0600 leaf. Zero new machinery; ADR-0013's doctrine intact (a rotatable spend credential, revocable by `codex logout` / the account's device list). A prepare that cannot deliver its preconditions (missing credential) is now a clean pre-session infra status, not a harness crash. The cache-volume guard refuses `.codex` paths exactly as `.claude` (a persistent volume there would carry config, auth, and history across Runs).

This is **design (a)**, adopted as primary. **Pre-merge spike execution is intentionally waived** (operator ruling): the S1–S8 procedure needs the operator's ChatGPT-plan login and a Docker host, so **production rollout is the validation environment** — the first deployed codex-review Runs are where headless plan auth (S2's question) and stored-copy survival across token rotation (S4's question) are actually observed. Authenticated lifecycle behavior has NOT been validated by this change: the local smoke test reached exactly the authentication boundary (a clean `failed:unavailable` on a 401), no further. The harness, procedure, and sanitized-evidence checklist ship in `spikes/issue-76-codex-plan-auth/` as **post-deployment observations** — run them (or record the equivalent from production Run evidence) on issue #76 so the answers are durable. Two vendor sources read on 2026-09-04 point S4 toward a negative answer ahead of production observation: the official Codex auth documentation states that tokens refresh automatically during use and that the refreshed credentials persist in the cached `auth.json`, and openai/codex#15410 records that the refresh token in `auth.json` is single-use, so any copy is invalidated once the live instance refreshes — the stored copy would be dead after the first in-Run refresh, making design (b) the expected outcome; #76 remains the deployment-specific validation record (noted 2026-09-04, #132). If rotation invalidates the stored copy (S4's question answered no), the recorded fallback is design (b): a persistent auth volume initialized by a one-time in-container login — a secret-delivery class outside the Fernet path whose ADR-0013 deviation and volume-concurrency limits would need their own amendment. If headless plan auth fails outright (S2 answered no), plan auth is unsupported headless and API-key auth becomes the question (note: `OPENAI_API_KEY` sits on the steering blocklist today; adopting it as a credential flips that entry and the credential map together).

### 6. The base image and the publish matrix (rides ADR-0051)

`worker/docker/Dockerfile.codex` mirrors the claude run image with two deliberate divergences: the CLI install is **pinned to exactly `CodexAdapter.MIN_ENFORCING_CLI`** (the experimental `--json` schema and rollout format are the contract the parsers speak — the pin is the policy, the floor the backstop, a deploy test keeps them in lockstep, and a bump re-runs the spike's fixture captures), and no standalone knowledge bake (derived images bake the per-tool tree at the node). CI's `run-image` and `publish-run-image` jobs become a per-agent **matrix** — ADR-0051's write-once / tip-re-check / `:main`-repair machinery is written once and parameterized, with per-image cache scopes and per-image FIFO concurrency groups (each registry ref's monotonic ordering is its own). One-time op note: the `theozolith-run-codex` GHCR package needs the repo Actions grant if it is ever first created by hand.

### 7. The example ships both reviewers; the race is documented, not routed

`deploy/configs-example` gains `codex-review` (worker type + stopped Stack): the same Reviewer driver, its own GitHub identity (no self-grading, ADR-0008), the plan credential, and the **same knowledge tree** as the claude types — one tree, two compiled views, per-tool pins retagging exactly the types whose view changed. Reviewer discovery has no per-PR claim, so two *running* reviewer Stacks race on the same pr_ready pool (first launcher wins; simultaneous polls can double-review). Accepted per operator ruling: run one at a time for deterministic coverage, or treat a double review as a second opinion. Deterministic routing would be new claim machinery (ADR-0017 territory) and is explicitly out of scope.

## Consequences

- A PR can now be reviewed by a non-Claude model with the identical driver, verdict, and evidence machinery; the Reviewer driver needed zero changes, which is the ADR-0044 promise kept.
- One knowledge tree serves both adapters with per-tool selective retagging. Claude knowledge pins and derived-image tags remain byte-stable: a legacy pin re-keys itself on the next ingest and the identity hash gains its extra key only for a non-default bake target, so no claude image retags. Deck exports and their selectors do **not** stay stable — they move in the accepted one-time breaking transition of §3 (amended 2026-09-04, #132), which completes only with a coordinated Control and Node Daemon upgrade, convergence of the distribution on every deck-hosting node, and one recreation of each existing claude deck; until then those decks may be unavailable.
- Compat shims (legacy pin keys, bare-layout presence check, daemon staging of a pre-per-tool distribution and its `<name>/claude` export) carry the *distribution-shape* window only — they never make mixed Control/Node Daemon versions serve a deck — and should be deleted once pre-ADR-0052 pinned builds are out of support.
- Codex identity is honestly weaker than Claude's: probe + static + post-exit evidence, no live kill, effort locked until proven. The evidence record states what ran; the doctrine states what is not checked.
- Spike #76's S1–S8 procedure (login, headless exec, rotation, stale-copy recovery, stream fixtures, sandbox matrix, per-model config binding) is deliberately **not a pre-merge gate**: production rollout validates the credential design, and the checks remain the post-deployment observation procedure — its recorded answers add capability-table rows (S7) or trigger the design-(b) amendment (S4's question answered no).

## Amendments

- **2026-08-27 (#85)**: the baked codex config refuses instruction-discovery keys (`project_doc_fallback_filenames`) at the bake-time conflict scan, the per-Run identity static checks, and the identity reader on model-less images — the judge-isolation boundary, so a baked config cannot reopen the involuntary instruction channel the Reviewer's instruction-file removal closes.
- **2026-09-04 (#132)**: the codex Flight Deck opens — §3's claude-only deck export becomes a per-tool mirror with the view path as the selector, and §4 gains the interactive scope (well-known model file only). The deck was refused because the export could serve one view and the adapter had no interactive contract; both now exist, and nothing in the adapter seam was ever codex-specific. The Context's "no managed-policy config tier" is corrected (0.150.0 loads `/etc/codex/config.toml` and `requirements.toml`; neither can hold the model), §5 records the vendor sources that point design (a) toward failure pending #76's validation (the official auth documentation on automatic refresh and the persisted cache; openai/codex#15410 on single-use copied refresh tokens), and §1 marks `prompts/` a deprecated compatibility surface. A codex deck carries no `CODEX_AUTH_JSON` slot: the human logs in inside the deck (`codex login --device-auth`, which needs device-code authorization enabled on the ChatGPT account) and the per-instance state volume owns the rotating credential. The export layout change is recorded as a one-time breaking transition: mixed Control/Node Daemon versions are not required to keep claude decks usable, both incompatible pairings fail closed at the deck start (the start script requires the view marker at the selected root), and recovery is upgrade-both, converge, one recreate per claude deck (§3); the Consequences no longer claim deck mounts are untouched — only claude knowledge pins and derived-image tags stay byte-stable.
- **2026-09-04 (#137)**: §3's transition names its third part — the view-marker guard in the deck start script, which ships with the operator's worker type in the Config Repo rather than with the release — and orders completion Config Repo, then Control, then the daemons: the guard is backward-compatible under the old export, and without it an old Control paired with a new daemon links the views' parent silently, the one pairing the earlier text wrongly counted as fail-closed.
- **2026-09-05 (#137)**: §3's completion order follows the product updater instead of assuming Control can move first: `theozolith update` fans the pin out to every daemon in one call and leaves the Control service to a manual restart, so the release lands in a maintenance window (guard, drain the claude decks, update and restart, converge, verify, recycle); Control-first stays only as the source-checkout alternative whose install-only build guarantees the order.
- **2026-09-05 (#140)**: §1 gains the native codex mappings beside the retained deprecated `prompts/` surface — `agents/codex/*.toml → agents/*.toml` (custom agent roles) and `hooks/ → hooks/` verbatim (`hooks.json` required, must be a JSON object) — and §3's codex view lists them. Both sections are claude-blind, so claude views and pins stay byte-identical. Review overturned the first cut's Ozolith-only five-field allowlist for roles: a role file is a native codex subagent definition carrying a full `config.toml` layer, so the loader validates the complete standalone role schema of the supported codex baseline (codex-cli 0.153.3) — codex's own vendored, digest-pinned `config.toml` schema plus its role-parser metadata rules — trims name and nickname identity the way codex does, and refuses a symlinked `agents/` root or tool namespace, not only a symlinked file. A second review pass fixed the contract's wording: *schema-valid* (the vendored schema's canonical keys; the parser's compatibility aliases are rejected on purpose) is neither *parser-compatible* nor *runtime-effective* — 0.153.3 applies a bounded override set, `sandbox_mode` and `mcp_servers` are transported but not applied, and the child inherits the parent's permission authority. The product prerequisite (#139) for a Codex Flight Deck that ships a delegated subagent roster and a PreToolUse guard from the Config Repo.
