# ADR-0015: M3 substrate contracts — control-plane API, Config Repo format, secret store, defaults, packaging

## Context

The M3 brief (Control Node + Node Daemon + secrets) delegates five decisions to the implementing PR: the control-plane API schemas (heartbeat, command, run-event, secrets-pull), the Config Repo file format, the secret store's cryptography and key management, the liveness/janitor/recycle defaults, and the Node Daemon's packaging and host-OS baseline. The governing constraints are ADR-0002 (the Control Node is advisory in coordination; GitHub is the only claim authority), ADR-0006 (git-backed Config Repo, working home on the Control Node, desired state over the channel, node-cached degraded mode, channel invariant), and ADR-0013 (node-resident drivers as process Stacks, kill-the-tree, labeled ephemeral run containers).

## Decision

### Control-plane API (JSON over HTTPS, bearer tokens, versioned under /api/v1)

Two credentials, both static bearer tokens compared in constant time: the **node token** (Node Daemons and drivers) and the **admin token** (CLI now, M4 web UI later). TLS is mandatory on the channel; endpoints that carry secret values (secret set and pull) additionally refuse to serve over plaintext unless the server was started with an explicit `--insecure-dev` flag (tests and local development only).

- `POST /api/v1/nodes/register` (node token) — `{node, version}` → `{ok}`. Idempotent; a heartbeat from an unknown node also registers it, so registration is a courtesy, not a precondition.
- `POST /api/v1/heartbeats` (node token) — request: `{node, version, stacks: [{name, kind, state, detail}], run_containers: [{name, run_id, owner, status}], images: [{name, tag, base_digest, instruction_hash, built_at}], config_commit, completed_commands: [id, …]}`. Response: `{commands: [{id, verb: drain|recycle|update|rebuild, target}], config: {commit, stacks: […], images: […]}}` — the node's full desired state rides every heartbeat response (ADR-0006); `completed_commands` in the next request acknowledges execution, and a command is re-delivered until acknowledged. `target` names a Stack (drain/recycle), an image (rebuild), or is null (whole node / the product itself for update).
- `POST /api/v1/events` (node token) — one namespaced event per request: `{type, …payload}`. Known types are `theozolith.run` `{worker, node, stack, issue, run_id, attempt, phase: claimed|gate|pr-open|failed|escalated, pr}` and `theozolith.review` `{reviewer, node, pr, issue, round, verdict}`; **unknown types are accepted and stored verbatim** (the typed-event extension point, [NODE-SUBSTRATE.md](http://node-substrate.md/)). Events are facts about the past, never commands.
- `POST /api/v1/claim-intents` (node token) — `{issue, worker}` → `{allow, holder}`. Grants a short exclusive *intent* (TTL below) to the first asker and answers `allow: false` to others while it lives; the M2 wire format is kept verbatim (only an explicit `allow: false` vetoes, so every M2 fallback path still degrades to "allow"). A pre-filter answer is never a claim; GitHub assign-and-verify remains the only authority (ADR-0002). *(Superseded by ADR-0017 — see Amendments.)*
- `PUT /api/v1/secrets/{name}` (admin token, TLS) — `{value}`. Write-only entry: no API returns a stored value to an admin. The M4 web form writes through this same endpoint.
- `POST /api/v1/secrets/pull` (node token, TLS) — `{node, names}` → `{secrets: {name: value}}`. **Node-scoped**: the Control Node computes, from the Config Repo, the set of secret names referenced by Stacks placed on the requesting node and refuses names outside it (HTTP 403), including for nodes with no placed Stacks.
- `POST /api/v1/commands` (admin token) — `{node, verb, target}` → queued command, delivered on the node's next heartbeat.
- `GET /api/v1/state` and `GET /api/v1/audits` (admin token) — read models for the CLI and the M4 dashboard: last-seen per node, stack/container/build status (build skew across nodes is visible here), janitor actions, and auditor findings.
The **channel invariant** holds by construction: heartbeat responses carry desired state (stack declarations, image recipes, compose text) and references (image names, secret names); the only value payload anywhere on the channel is the secrets-pull response, over TLS.

### Config Repo file format

TOML (stdlib `tomllib`), parsed **only on the Control Node**; nodes receive the parsed JSON desired state over the channel and never read the repo (ADR-0006). Layout inside the git-backed folder (default `~/.theozolith/configs`):

- `stacks/<name>.toml` — one Stack per file, name = file stem: `kind = "process" | "container"`, `node = "<node name>"` (placement, exact match), `state = "running" | "stopped"` (desired), `env = {NAME = "value", …}` (non-secret), `secrets = {ENV_NAME = "secret-name", …}` (each delivered as `ENV_NAME_FILE` pointing at the materialized file). Process kind: `command = "theozolith-worker"` (argv string, from the product distribution), optional `run_image = "<images/ name>"` — resolved to the derived image's deterministic tag at reconcile time and injected as `THEOZOLITH_RUN_IMAGE`. Container kind: either `image = "<pinned ref>"` with optional `ports = […]`, `volumes = […]`, or `compose = "<repo-relative path>"` with optional `overlays = […]` — compose and overlay **file contents are inlined** into the distributed desired state (declarative topology is desired state, not a value payload) and materialized by the daemon under its state directory before `docker compose -f base -f overlay… up -d`.
- `images/<name>.toml` — derived-image recipe: `base = "<ref pinned by digest>"` (must contain `@sha256:`), `setup = ["<shell line>", …]`, optional `knowledge_source` + `knowledge_pin` (baked via the M1 `theozolith-knowledge bake` CLI at build time, never at container start).
- `product.toml` — optional `[product] version = "X.Y.Z"`: the version the update command installs (ADR-0013 §8). Absent = latest.
Built-in Stacks (worker, reviewer, control) are ordinary files in this same format — the daemon has no hardcoded workload knowledge; worker and reviewer are process-kind Stacks, control is a container Stack.

**Derived-image tag**: `theozolith/<name>:<base-tag>-<hash12>` where `<base-tag>` is the tag component of the base ref and `<hash12>` is the first 12 hex chars of SHA-256 over the canonical JSON of `{base, setup, knowledge_source, knowledge_pin}`. Changing any instruction changes the tag; an image whose tag already exists locally is not rebuilt (the `rebuild` command forces `--no-cache`). Build metadata is stamped as image labels (`theozolith.base-digest`, `theozolith.instruction-hash`, `theozolith.built-at`) and reported in heartbeats.

### Secret store cryptography and key management

- **Cipher**: Fernet (AES-128-CBC + HMAC-SHA256, from the `cryptography` package) — authenticated symmetric encryption with a boring, audited implementation. Values are encrypted per-secret; the SQLite database stores only `{name, token, updated_at}`.
- **Key**: a master key file at `<data-dir>/master.key`, mode 0600, generated on first start; may be supplied instead via `THEOZOLITH_MASTER_KEY(_FILE)`. The key never transits the channel and never enters the database.
- **Rotation**: `theozolith-control rotate-key` — offline re-encryption of every stored secret under a fresh key (old key read, new key written, single transaction). Rotating a *secret value* is just re-entering it. Compromise of the DB file alone reveals nothing; compromise of key + DB is a full secret compromise, accepted for a single-operator V1 (the pluggable provider interface is the air-gap escape hatch, out of scope per the brief).
- This permits `fastapi`, `uvicorn`, `cryptography`, `jinja2`, and `python-multipart` as runtime dependencies of `control/` — a deliberate amendment of ADR-0010's zero-dependency rule, confined to the one always-containerized component. `jinja2` implements the approved M4 server-rendered dashboard; `python-multipart` implements the approved login and secret-entry forms. `worker/`, `nodedaemon/`, and `knowledge/` remain stdlib-only (the Node Daemon must stay trivially installable on any host).
### Liveness, janitor, and recycle defaults (env-tunable)

- Heartbeat interval **60s** (`THEOZOLITH_HEARTBEAT_SECONDS`).
- Zombie-claim grace period **600s** = 10 missed heartbeats (`THEOZOLITH_ZOMBIE_GRACE_SECONDS`); janitor sweep every **60s** (`THEOZOLITH_JANITOR_SWEEP_SECONDS`). A Worker's liveness is the freshest of: its node's last heartbeat and the last event it emitted. The janitor acts only on issues whose latest `theozolith.run` event is non-terminal (claimed/gate), re-verifies claim state on GitHub before acting, and **skips issues whose open PR carries ****`pr_ready`** (the Reviewer, not the janitor, owns that path). Action: strip all assignees, remove `in_progress`, restore `plan_ready`, and record the action in Control Node state — the janitor writes claim state only in this one restorative direction (ADR-0002). *(Janitor action superseded by ADR-0016 — see Amendments.)*
- Retry-audit sweep every **300s** (`THEOZOLITH_AUDIT_SWEEP_SECONDS`). Expected attempts on a PR = max(revise-verdict round from review events, max Run attempt − 1); a label mismatch is recorded as a finding and **never corrected on GitHub** (the auditor performs no GitHub writes at all).
- Claim-intent TTL **120s** (`THEOZOLITH_CLAIM_TTL_SECONDS`).
- Recycle/stop policy: SIGTERM to the process group, **30s** grace (`THEOZOLITH_STOP_GRACE_SECONDS`), then SIGKILL; the Stack's labeled run containers are force-removed in the same operation (kill-the-tree, ADR-0013). The optional GitHub Action janitor backstop (deploy/github/) is a pure GitHub-data fallback with a deliberately conservative 24h staleness window.
### Node Daemon packaging and host baseline

- **Packaging**: `theozolith-nodedaemon` (pip-installable, stdlib-only) into a dedicated venv at `/opt/theozolith` by `deploy/install-nodedaemon.sh`, which also installs `theozolith-worker` + `theozolith-knowledge` (the drivers the daemon supervises ship in the same versioned distribution, ADR-0013 §8).
- **Supervision**: systemd unit `theozolith-nodedaemon.service` with `KillMode=control-group` (every TheOzolith process on the node is a live descendant of the daemon or does not exist), `Restart=always`, `RuntimeDirectory=theozolith` (secrets tmpfs), `StateDirectory=theozolith` (config cache, materialized compose files).
- **Secrets materialization**: pulled at deploy time to `$RUNTIME_DIRECTORY/secrets/<name>` (tmpfs under `/run`, mode 0600); process Stacks receive `ENV_NAME_FILE` pointing there; container Stacks get the file bind-mounted read-only at `/run/secrets/<name>` plus the matching `ENV_NAME_FILE`. Values never touch node disk; a daemon stop wipes tmpfs.
- **Update command**: stop all process Stacks (their run containers die with them), install the Config-Repo-pinned product version into the venv, then `os.execv` the daemon binary — same PID, fresh code, and the restarted reconcile loop brings the Stacks back. No self-restart race with systemd.
- **Host baseline**: Linux with systemd, docker (compose plugin included), and Python ≥ 3.11. The daemon assumes flat IP reachability of the Control Node URL and a CA bundle for its self-signed/provisioned TLS (`THEOZOLITH_TLS_CA`); no Tailscale anywhere in product code ([NODE-SUBSTRATE.md](http://node-substrate.md/)).
### Component dependency

`theozolith-control` depends on `theozolith-worker`: the janitor and auditor are pipeline-aware jobs by design (ADR-0002 places them on the Control Node), and reusing the worker's rate-limited GitHub client and label vocabulary beats forking them. [ARCHITECTURE.md](http://architecture.md/) only isolates `knowledge/`; this dependency keeps exactly one implementation of GitHub I/O in the product.

## Consequences

- **Positive**: one JSON desired-state document per node makes degraded mode trivial (cache the last response); the channel invariant is testable by transcript inspection; secret scoping falls out of Stack placement with no extra configuration; deterministic image tags make build skew a string comparison in Control Node state; every janitor/auditor action is recorded and auditable; the M2 pre-filter wire format survives unchanged, so M2 drivers interoperate with an M3 Control Node.
- **Negative**: a shared node token means any node can heartbeat as any other (acceptable single-operator V1; per-node tokens are a straightforward hardening later); inlining compose text in desired state grows heartbeat responses (bounded: compose files are small declarative documents); `control/` abandons zero-dependencies (confined, and it is the one component that always ships as a container); re-exec-based update means the daemon briefly serves no heartbeats during an update.
- **Neutral**: the janitor depends on Run events for issue→worker mapping, so a claim made while the Control Node was down is invisible to it until the next event — the GitHub Action backstop and the failed-Run machinery cover that gap; SQLite is a single-writer store, fine at fleet sizes where one Pi is the control plane.
## Alternatives rejected

- **Per-node client TLS certificates** (mTLS): stronger, but provisioning cost is out of proportion for a single-operator LAN deployment; bearer token + TLS matches the NODE-SUBSTRATE trust model (dashboard access = cluster access).
- **Nodes cloning the Config Repo directly**: violates ADR-0006 (working home is the Control Node; desired state flows over the channel) and would give every node a git credential for the private repo.
- **age/SOPS or OS keyring for the secret store**: pluggable-provider material (air-gapped deployments, post-V1); the Control Node provider is the V1 decision in the brief.
- **A message queue or long-poll command channel**: the 60s heartbeat *is* the command channel by design ([NODE-SUBSTRATE.md](http://node-substrate.md/)); anything faster is dashboard polish, not correctness — commands tolerate a one-interval delay.
- **Janitor keyed on heartbeat stack status instead of Run events**: stack status says a driver process is alive, not which issue it holds; only the driver knows its claim, and it already emits that as an event.
- **Auto-correcting attempt-N labels from the auditor**: explicitly forbidden by the brief and ADR-0002 — the auditor flags, a human reconciles.
## Amendments (2026-07-17, grilling session)

- **Claim intents → claim grants (ADR-0017)**: the advisory `claim-intents` endpoint, its TTL, and the pre-filter concept are superseded — the Control Node is the single writer of claim creation on GitHub, mutating issue state (assignee + `in_progress`) before granting work to a requesting driver. GitHub assign-and-verify is deleted.
- **Janitor authority (ADR-0016)**: strip-assignees/restore-`plan_ready` is superseded by two-phase evidence-first escalation — dashboard flag on silence past grace, then release + `failed` + `needs_human` with the evidence link once the boot sweep pushes it; the janitor never re-queues. The retry auditor dies with ADR-0014's marker machinery.
- **Telemetry on the channel (ADR-0016)**: `theozolith.run.progress` joins the known event types (size caps enforced at ingestion); the control database is a cache, never the archive — ~10GB transcript-tail budget, oldest-first eviction, terminal events kept indefinitely.
- **Queue-behind recycle/update (recorded in **[**NODE-SUBSTRATE.md**](http://node-substrate.md/)** Decisions, 2026-07-17)**: commands received mid-Run queue behind the current Run as a drain→apply→undrain composition instead of killing it; job-dir presence is the in-flight signal; `--force` keeps kill-the-tree.
- **M4 control-only dependencies**: `jinja2` and `python-multipart` join the `control/` runtime-dependency exception for the approved server-rendered dashboard and HTML forms. The stdlib-only rule remains unchanged for `worker/`, `nodedaemon/`, and `knowledge/`.
## Amendments (2026-07-22, grilling session)

- **Two update paths (recorded in **[**NODE-SUBSTRATE.md**](http://node-substrate.md/)** Decisions, 2026-07-22)**: `theozolith update` (user path) resolves the latest published release — or an explicit `--version` — and pins it; `theozolith build` (developer path) builds the distribution from the source checkout on the Control Node, pins the checkout's git SHA (`-dirty` marked when uncommitted changes exist), and serves the built artifact for node pulls. Both paths converge on the same machinery: pin bump committed to product.toml, update command fanned out over heartbeat responses (drain-aware queue-behind), Control Node self-update last via the existing `os.execv` path. product.toml's "absent = latest" default is softened: absent means the installer resolves the latest release and **writes the pin** — a running fleet always has a recorded version. Nodes never pull source and never build the product distribution.
- **Update convergence and dispatch eligibility (PR #7 review, 2026-07-22)**: the pin is desired state, not a one-shot command — the Node Daemon reconciles its running product version against the pinned version on every heartbeat (startup is just the first pass), so a failed update retries automatically; the fan-out command is a nudge, never the mechanism of record. Dispatch eligibility follows the heartbeat-reported running version, not command acks (a node can ack, fail the install, and never converge): a node whose reported version differs from the recorded pin receives no new work grants. Issuing an update therefore pauses new dispatch fleet-wide by design — running Runs drain (queue-behind), and each node returns to eligibility as it converges. Escalation: a node still off-pin several consecutive heartbeats after pin delivery gets a restart command; if that fails, an error event is emitted and the node stays ineligible until a human intervenes. Control Node down mid-rollout: nodes back off exponentially (capped) until it returns — no special case, since dispatch is already paused.
- **`build`**** refuses a dirty tree (PR #7 review, 2026-07-22)**: `theozolith build` refuses to run when the source checkout has uncommitted changes — a `.dirty` pin does not name a unique artifact set (two different trees on the same commit produce the same pin, and re-uploads silently overwrite), which weakens "never deploy an unrecorded version". Every deployed pin is therefore a committed SHA. Local iteration relies on `theozolith test`; deeper deployment-grade signals come from the future integration-test node (design recorded in [NODE-SUBSTRATE.md](http://node-substrate.md/)).
