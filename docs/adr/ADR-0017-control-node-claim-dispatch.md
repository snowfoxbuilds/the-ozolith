# ADR-0017: Control Node claim dispatch — claim-write-through

## Context

M3 made the Control Node operationally load-bearing (secrets distribution, infrastructure commands, the zombie-claim janitor) while ADR-0002 still framed it as advisory in issue coordination. Per-driver GitHub polling duplicated discovery across the fleet, the assign-and-verify race dance existed only because claiming had no arbiter, and the advisory pre-filter left a window where GitHub showed a plan_ready issue that was effectively spoken for. Grilling 2026-07-17 resolved the contradiction.

## Decision

Claims dispatch through the Control Node, write-through to GitHub:

- Workers and the Reviewer request work from the Control Node instead of polling GitHub. One dispatch path for both kinds: an Issue Worker is granted an issue, a PR Worker is granted a PR (its issue resolved through the `ozolith/issue-N` branch), and both grants claim the issue:PR set — the "Reviewer side is discovery-only" reading is retired (amended 2026-09-03, #120).
- The Control Node is the single writer of claim creation: it selects the target, writes the claim to GitHub itself — adds the worker's GitHub login as an assignee alongside any human assignee, adds in_progress, and atomically removes the definition's `consumes` labels (amended 2026-09-03, #120) — then returns the target in the same response. Spoken-for is in_progress alone: a human assignee never blocks dispatch (amended 2026-09-03, #120). Grants are serialized internally; assign-and-verify is deleted. *(Amended 2026-08-17, #52: the grant's issue payload is claim authority plus a convenience snapshot for logging and the pre-clone metadata write — never the Run's context. The driver re-reads the full issue and PR context from GitHub at checkout, every Run.)*
- GitHub remains the sole source of coordination truth. The Control Node reconciles to GitHub, never the reverse; hand-edited labels stay meaningful; a lost Control Node database rebuilds from GitHub.
- Claim release has three owners: the driver releases on every classified ending (completion — for an Issue Worker, PR push; failure; empty PR), removing its own login and in_progress only (amended 2026-09-03, #120); the Control Node releases claims it wrote that never activated (no claimed event within the activation window, ~60 seconds — a lost response or a driver death before pickup is otherwise invisible to every reaper, since a never-activated Run emits zero events), restoring the consumed labels (amended 2026-09-03, #120); the janitor handles death after activation, past the zombie grace period.
- Availability: Control Node down = in-flight Runs finish and publish (drivers hold their own PATs for all non-claim GitHub writes); new claims and new review rounds pause. Richer fallback behavior is a backlog item.
- Dev mode: --once requires a reachable Control Node; running theozolith-control serve locally is the daemon-less path. No second claim path exists.
- Prerequisites: the Control Node's GitHub token graduates from optional (janitor-only) to required, and driver registration carries each driver's GitHub login.

## Consequences

- **Positive**: claim races are structurally impossible (single serialized writer); GitHub is never stale about ownership; one GitHub poller instead of N (rate-limit headroom); the Control Node's live-claim picture becomes first-party (it granted every claim it watches), tightening zombie detection.
- **Negative**: the Control Node is a single point of failure for pipeline throughput (accepted; fallback is backlog); it requires a write-scoped GitHub token and knowledge of driver identities; ADR-0002's "the pipeline ships PRs without it" narrows to "in-flight Runs ship without it".
- **Neutral**: supersedes ADR-0002 in part — GitHub-owns-coordination survives; the advisory claim path is retired. Residual ADR-0002 invariant: the Control Node never originates coordination beyond claim creation (it cannot approve, revise, or advance an issue); janitorial liveness corrections are the enumerated exception.

## Alternatives Considered

- **Advisory pre-filter (status quo, ADR-0002)**: rejected — the M3 reality already made the Control Node load-bearing, and the advisory posture bought availability the operator no longer wants at the cost of racy, duplicated discovery.
- **Control arbitrates, driver writes the claim (lease model)**: rejected — requires new lease/TTL logic, and GitHub is stale between grant and the driver's write; write-through removes both the staleness window and the lease machinery.
- **Control Node database as coordination authority (GitHub as rendering)**: rejected — breaks hand-edited labels and human workflows until a full control UI exists; makes the Control Node database load-bearing for cluster state; inverts rather than solves the two-sources-of-truth problem.

## Amendments

- **2026-08-17 (#52, Context Tree)**: the no-re-read clause is deleted. The original decision let the driver treat the granted issue payload as the Run's context ("the grant is the issue — no re-read needed"), which froze the issue snapshot at dispatch time and gave round-1 Runs no comments at all. The grant now carries **claim authority only**: the claim exists on GitHub and the driver may run. Every Run — including local retries — re-reads the issue and PR context (body, all comment surfaces, timeline, reviews, commits, checks) from GitHub at checkout and materializes it into the job directory as the Context Tree (`input/issue/`, `input/pr/`). The dispatch response still returns the issue payload; it serves logging and the pre-clone `input/issue.json` metadata write, nothing more. Claim-write-through, serialized grants, and GitHub as the sole source of coordination truth are unchanged.
- **2026-08-17 (#52, comment authority)**: the Context Tree's completeness is bounded by an authority filter — the one deliberate exception to the "never relevance-filter" doctrine, and a security rule, not a relevance heuristic. Autonomous workers act on what they read, so comment influence is an authorization decision: the tree contains comments, reviews, and comment/review payloads (including those embedded in the issue timeline) **only from authors GitHub reports as `OWNER` or `MEMBER`** (`author_association`). COLLABORATOR, CONTRIBUTOR, FIRST_TIME_CONTRIBUTOR, FIRST_TIMER, NONE, and missing/unknown associations are removed before serialization and leave no worker-visible trace — no body, snippet, filename, index entry, or count. Machine verdicts obey the same boundary: the driver selects the latest `theozolith:verdict` block only from authorized PR-conversation comments, so an unauthorized comment can never designate reset or cherry-pick state. Within the boundary, context is complete and uncapped — PR commits are enumerated from the driver's trusted checkout (the `/pulls/{n}/commits` endpoint caps at 250 and is not used), timeline events keep their documented per-kind fields plus common identity (unrecognized kinds withhold their payload), CI state covers check runs plus legacy commit statuses, and review threads carry resolution and grouping state (GraphQL `reviewThreads`; REST exposes no resolution surface). "No trace" includes linkage: an authorized reply never names an unauthorized parent (`in-reply-to` renders only when the referenced comment is itself authorized), and a thread whose comments are all unauthorized vanishes entirely — id included. The boundary applies to comments, reviews, and embedded comment/review payloads, and nothing else: issue/PR metadata such as a cross-referenced item's title is not comment content and renders whenever GitHub provides it, same-repo or not. The exact `input/` tree each Run saw is embedded byte-for-byte in its evidence bundle from a **trusted snapshot frozen immediately before the run container launches**: the job directory is agent-writable through the `/job` bind mount from launch onward, so neither the live evidence push nor the boot sweep ever re-reads input — or derives the bundle's publish path — from the job directory after execution. A missing snapshot proves no container ever launched (capture strictly precedes launch), the only case where the job directory's input is still driver-authored and collected directly.
- **2026-09-02 (ADR-0056, multi-repo coordination)**: the "one coordination target per Control Node" reading is retired. The Control Node coordinates every Bound Workspace of its deployment — the workspaces its Pinned Build's driver-bearing Stacks bind — and the dispatch request names its `repo` and `stack`, verified against the Pinned Build (missing or mismatched Stack = 403; fail-open only while the Pinned Build is unreadable or absent) — and only a worker Stack verifies: resolved from a worker type with a non-empty driver, process-kind; a Flight Deck or generic Stack is 403 even on the right node. Every verified 200 response — grants, discovery batches, no-work, and pause answers alike — echoes the verified binding in one exact shape per role, and a Driver validates it before interpreting the payload, refusing an answer without its matching binding before checkout — the mixed-version guard: pin convergence gates node versions, not the Control Node's own binary, so a new Driver against an old Control refuses the unbound grant and the already-written claim is recovered by this ADR's existing activation-timeout release. Every coordination cache keys by repo (exact per-table keys in ADR-0056); `theozolith.run`/`theozolith.review` events carry (repo, stack), authorized against the Pinned Build exactly as dispatch is — with one continuity exception: a verified grant or discovery leaves a cache-only authorization lease, scoped to the claim or review round rather than a single Run (the lease, not bind state, is the operation authority — a missing, expired, or mismatched lease refuses the event even while the repo is bound; a failed Run keeps it alive through the bounded retry lanes with an atomic `run_id` rotation, and while bound the janitor renews an activated Implementer lease from GitHub truth so ADR-0016's unbounded zombie recovery is never cut short; a Reviewer round activates its per-actor discovery lease with an acknowledged `theozolith.review` `phase="started"` handshake — confirmed and echo-validated before checkout, identical retries idempotent, exclusive per PR across live activations with the leased label-derived round matched (rediscovery re-rounds an unactivated lease when the labels advance) — before its `phase="completed"` outcome counts; a claim-ending outcome, a round's conclusion, an activation-deadline expiry, bound GitHub-truth reconciliation, or an activated lease's budget-derived expiry once renewal stops retires it, and retiring a live review activation — completion, reconciliation, or expiry — atomically invalidates the PR's unactivated peer leases whatever round each records, so participation after it takes fresh discovery — lost terminal telemetry never strands authorization), and facts exactly matching it are accepted after unbinding, so an in-flight claim's completion still reconciles the claim and node health (nothing new is authorized); the janitor sweeps per bound repo; `THEOZOLITH_REPO` is no longer a Control Node setting (a set variable fails settings load loudly). Claim-write-through, serialized grants, and GitHub as the sole source of coordination truth are unchanged — "one GitHub poller instead of N" becomes one poller per bound repo, still control-side. See ADR-0056 for the full contract.
- **2026-09-03 (#120, ADR-0057)**: both worker kinds claim. Under the declarative worker model a PR Worker (the Reviewer among them) is granted one PR and claims the issue:PR set exactly as an Issue Worker claims an issue — the "Reviewer side is discovery-only" clause is retired, and with it ADR-0056's review-specific discovery leases and activation handshake (see that ADR's amendment). The claim write adds the worker's login alongside any human assignee, adds `in_progress`, and atomically removes the definition's `consumes` labels (today's plan_ready removal, generalized); spoken-for is `in_progress` alone, so a human assignee never blocks dispatch; every worker releases only its own login plus `in_progress` on every classified ending — the Implementer now releases at PR push rather than holding until revise — and Control's never-activated release restores the consumed labels. Reason: one claim path gives every PR at most one worker of either kind at a time and lets deck-lane issues carrying a human assignee still be reviewed.
