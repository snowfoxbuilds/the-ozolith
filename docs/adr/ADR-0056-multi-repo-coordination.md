# ADR-0056: Multi-repo coordination — dispatch and janitor keyed by repository

## Context

ADR-0017 bound coordination to the single `THEOZOLITH_REPO` the `serve` process was started with, while ADR-0044/0047 already let several Stacks of one Worker-Type Definition each bind a different workspace. The two halves disagreed: a second Implementer Stack bound to another repo loaded cleanly, was granted issues from `THEOZOLITH_REPO`, and worked a foreign issue number in its own checkout — a wrong-repo grant enforced only by convention. Grilling 2026-09-02 (issue #96) settled the amendment: the Claim Protocol is keyed by the repository the Driver will actually check out, end to end. Post-review of PR #99 hardened four seams the first draft left open — the mixed-version update window, the gap between the request's repo and the checkout's, event ingestion trusting its sender, and the unbinding story — and made the store identity exact. A second review round closed what that pass still left open: refusing an unbound repo's events contradicted "rebinding resumes reconciliation" (fixed by the authorization lease), verification accepted any Stack shape (now worker Stacks only), the canonicalization rules were not implementable as written, and chained dependents were missing from the unbound-obligations scan. A third round completed the lease's state machine — the first cut read as if any terminal Run event were claim-ending and every discovered PR indefinitely leased; the lease is now scoped to the claim or review round, with the retry lanes and an explicit Reviewer activation — and resolved the store map's `janitor_actions` contradiction (a blanket `repo TEXT NOT NULL` over a ledger whose node-scoped actions carry no repo) with a nullable column. A fourth round made the wires exact and the lease lifecycle self-sufficient: every verified 200 answer carries its binding in one published shape per role (reason-only pause and no-work answers included), the review round's start and completion became two phases of one authenticated `theozolith.review` event, lease retirement stopped depending on best-effort terminal telemetry (bound repos reconcile leases against GitHub truth; activated leases expire on bounded, budget-derived deadlines), and Reviewer leases are keyed per verified actor so concurrent Reviewer Stacks cannot overwrite each other. A fifth round made activation a reliable handshake and the lease the sole operation authority: the "redundant while bound" reading is retired (a missing, expired, or mismatched lease refuses the operation event bound or unbound), the Reviewer confirms its acknowledged `phase="started"` before checkout or any GitHub mutation — with idempotent identical retries, so a lost response is recoverable — batch discovery became per item (fresh verified discovery immediately before each PR, so a long earlier review never strands later targets), bound Implementer leases renew from GitHub truth so ADR-0016's intentionally unbounded zombie-recovery lane is never cut short while unbound expiry honestly ends Control's acceptance, and review activation became exclusive per round: the first acknowledged `started` wins.

Numbering note: this decision was drafted as ADR-0055 and renumbered — that number went to the Flight Deck live-surfaces ADR, which merged first. Issue-tracker references from the grilling window ("ADR-0055, multi-repo") predate the renumber and mean this ADR.

## Decision

- **Bound Workspace** (glossary term): a repository the Control Node coordinates — the workspace of a resolved driver-bearing (process-kind) Stack in the Pinned Build, **regardless of desired state** (a stopped Implementer's zombie claims still need the janitor). A Bound Workspace is identified by the **effective GitHub host plus canonical owner/name the Driver will actually access** — the checkout-identity rules below make the `workspace` field and the effective target provably the same thing. Flight Deck workspaces are never bound (decks are not pipeline actors), and a worker Stack's dispatch-verification failure never gates a deck's operation — decks never call dispatch, a structural property, not a carve-out. The bound set scopes dispatch verification, event authorization, the janitor's sweeps, and the state document's `repos`.
- **Wire**: the dispatch request body gains `repo` (owner/name) and `stack` (the Driver's `THEOZOLITH_STACK`); a request missing either is refused 400. The Control Node verifies the pair against the Pinned Build — the named Stack must exist, be placed on the authenticated node, resolve to exactly that workspace, **and be a worker Stack: resolved from a worker type with a non-empty driver, which is what makes it process-kind** — otherwise **403** with a detail naming the Stack and both repos. Existence is not enough: a Flight Deck Stack, a generic container Stack, or a generic process Stack is refused 403 even when node and repo match — dispatch authority belongs to pipeline workers alone, and the refusal never touches a deck's own operation (decks never call dispatch). A missing Stack is a 403, not a soft no-grant: a `reason` response is reserved for *verified* requests with nothing eligible, so a typo'd Stack name can never fall back to the request's repo. **Every verified 200 answer echoes the verified binding — empty and reason-only answers included.** The shapes are exact: the Implementer response is `{"repo": …, "stack": …, "issue": <object|null>, "reason": <optional>}` and the Reviewer response is `{"repo": …, "stack": …, "prs": [...], "reason": <optional>}` — one shape each across every 200 outcome: a grant, a discovery batch, a plain no-work answer, a convergence block, a quarantine or pending-work block, a dependency wait or malformed state, and the GitHub-error pause (its `reason` rides the same shape). The response names what was verified, and the Driver validates the echoed binding **before interpreting `issue`, `prs`, or `reason`** — a pause explanation under the wrong binding is refused exactly as a grant would be (see mixed-version safety). 400 and 403 stay refusals, never successful bound answers: an error status carries no echo contract. Verification is fail-open only while the Pinned Build is unreadable or absent (the ADR-0004 deletion-test boot — the existing posture of the pin gates); this is the dev shape's door, alongside declaring a real Stack and setting `THEOZOLITH_STACK`. Reviewer discovery verifies identically.
- **Mixed-version safety**: the wire breaks with no backward compatibility, and pin convergence alone does **not** make that safe. The pin-eligibility gate is control-side and gates *node* versions; it cannot gate the Control Node's own binary, and the ADR-0051 update lifecycle — nodes converge by heartbeat while the control service restarts separately — can run a new Driver against an old Control Node. An old Control ignores unknown request keys and would grant from its single configured repo. Safety is therefore driver-side: a new Driver **refuses any dispatch or discovery response whose echoed binding is absent or names a different `(repo, stack)` than it sent — before checkout, before any work**. The refused grant recovers through the existing lane: the Driver never emits a claimed event, so the old Control's already-written claim expires in the activation window and its janitor releases it (unassign + remove in_progress) exactly as for any never-activated grant; the Driver's normal poll pacing bounds the churn to one written-and-released claim per poll until the Control Node restarts onto the new wire. The reverse pairing is inert: an old Driver's repo-less request meets the new endpoint's 400 and nothing is written. An end-to-end mixed-version test is an implementation obligation (below): a new Driver against a Control serving the previous wire executes no foreign issue.
- **Checkout identity**: the repository named on the wire must be the repository the Driver actually touches — three rules make the `workspace` field, the wire's `repo`, and the checkout one thing. (1) *Injection-only identity spellings*: the resolved Stack env's `THEOZOLITH_REPO` comes only from the resolved workspace and `THEOZOLITH_STACK` only from the Stack's own name — a worker-type Stack `[env]` naming either refuses at config load, joining the ADR-0045/0047/0048 guard family (an env override here is the same convention-not-structure hole the wire just closed, and an overridden Stack name is impersonation of a sibling binding). (2) *Provable clone/API targets* — two separate validations that must agree. *Clone-target*: a declared `THEOZOLITH_CLONE_URL` on a driver-bearing Stack must canonicalize to the bound logical GitHub host plus canonical owner/name; the supported forms are `https://<host>/<owner>/<name>[.git]`, `ssh://git@<host>/<owner>/<name>[.git]`, and the scp form `git@<host>:<owner>/<name>[.git]`; canonicalization lowercases the host (DNS is case-insensitive), compares owner and name case-insensitively (GitHub resolves them so), and strips one trailing `.git`. *API-target*: a declared `THEOZOLITH_API_URL` establishes the logical GitHub host — `https://api.github.com` **is** the host `github.com` (the one host whose API lives on a different name), and a GHES `https://<host>/api/v3` is the host `<host>`, whose clone host is that same `<host>` — and, paired with the declared repo, it must identify the same target the clone URL canonicalizes to. Anything else — another host, another owner/name, or a form that cannot name a GitHub host+repo at all (`file://`, a bare path) — refuses at ingest and config load, before any driver launches. (3) *Driver startup re-check*: the Driver re-derives the same two validations at startup, **unconditionally**, and fails before its first dispatch request when its effective clone/API target and its `THEOZOLITH_REPO` disagree — production startup rejects `file://` always, dev shape included. The worker test rig's `file://` remotes therefore move behind a test-only injected transport/checkout seam (or a canonically valid fake target intercepted beneath the validator); production validation is never weakened or made env-conditional to accommodate a test.
- **Events**: `theozolith.run` and `theozolith.review` events carry `repo` **and `stack`**, and ingestion authorizes them exactly as dispatch verifies: `(repo, stack, authenticated node)` against the Pinned Build. A missing or empty key is 400 naming it; a Stack that is absent from the pin, placed on another node, resolving a different workspace, **or not a worker Stack** (the same driver-bearing, process-kind rule as dispatch — a Flight Deck or generic Stack name is 403 for events too, even on the right node) is **403 and the event is never stored**; an absent Pinned Build is accepted (the same ADR-0004 dev door as dispatch); an unreadable one is accepted under the same posture as dispatch's broken-config door — fail-open is confined to loudly-visible config breakage, never to a mismatch. One continuity exception, defined next: an event that exactly matches a live authorization lease is accepted even when its repo or Stack has left the Pinned Build. Authorization is what keeps the store honest: grant activation deletes on the *verified* `(repo, issue)` and claim reads group by `(repo, issue)`, so an event can never activate, terminate, hide, or collide with another repo's same-numbered grant or claim. `theozolith.run.progress` stays keyed by `run_id` and `theozolith.error` stays node/component-scoped — unchanged. `theozolith.review` gains a **required `phase`** and the wire is exact: `phase="started"` carries `repo`, `stack`, `reviewer`, `node`, `pr`, `round`, and `run_id`, and no `verdict` — the round's activation fact, the review counterpart of `claimed`; `phase="completed"` carries the same identity fields plus `issue` and the `verdict`. Both phases require node authentication and the same Pinned-Build worker-Stack authorization as dispatch. A `started` atomically activates a matching unactivated discovery lease, and the acknowledgment is the handshake's commit: an **identical retry** of an already-accepted `started` — the same `(repo, stack, node, pr, round, run_id)` as the recorded activation — returns idempotent success **without storing a second activation event**, which is what makes a lost activation response recoverable by resending the identical request; no matching lease, an expired one, a mismatched identity, a conflicting `run_id`, actor, or round, or a `started` for a round another actor's acknowledged activation already holds refuses, and a refused event is never stored. A `completed` is stored, and retires anything, only when it matches the activated PR, round, `run_id`, and `(repo, stack, node)` — **a `completed` with no prior accepted `started` never counts, even while the repo is bound**: activation is the single authorization lane for review outcomes, not an unbound-only formality. Refusal codes are exact and shared with run events: **400** for a malformed shape (a missing required field, an unknown `phase`, or the retired phase-less, `run_id`-less terminal review shape — no legacy wire compatibility), **403** for failed `(repo, stack, node)` authorization, **409** for an authorized event the lease lifecycle refuses (no, expired, or mismatched lease; a conflicting activation or a competing actor's `started` on an already-activated round — the identical same-identity retry is idempotent success, never a refusal; completion-before-start; a duplicate `completed`; a superseded-`run_id` replay; an over-budget successor) — never stored, in every case. Event renderers and read models derive a verdict **only from a `phase="completed"` row**: a `started` row is an activation fact and never renders or counts as a verdict.
- **Authorization lease**: every successful verified grant, and every PR a verified Reviewer discovery names, creates a *cache-only lease* recording `(repo, stack, authenticated node, operation target)` — the granted issue or the discovered PR — plus the recorded `run_id` once an event names it. This is not the claim-write "lease model" ADR-0017 rejected — claim creation stays write-through and serialized; this lease only admits *facts about work control already granted*. The division of labor is exact, bound or unbound: Pinned-Build verification authenticates the **actor** — that this `(repo, stack, node)` may speak at all — while the lease authorizes the **specific operation and its lifecycle**; a run/review operation event with no live matching lease (missing, expired, or mismatched) refuses 409 even while the repo is bound and its sender verifies, and a verified grant or discovery is the **only** way operation authority comes into being. Unbinding then changes exactly one thing — continuity: run/review facts that **exactly match** a live lease are still accepted — the live claim resolves and the node's consecutive-failure counter moves (node health stays honest), whether the repo is rebound before or after — while a lease authorizes nothing new: no dispatch, no discovery, no janitorial GitHub write, and no event naming a different target, a different sender, or a `run_id` outside the lifecycle below. A lease is scoped to the **claim or review round, never to a single Run**:
  - *Implementer lease — claim-scoped*: created by the grant; the claimed event stamps the recorded `run_id`. A terminal `failed` ends one Run, **not the claim** — the events doctrine already says so (every non-completed Run emits `failed`; only a spent budget adds `escalated` for the claim) — so accepting it preserves the lease while a retry lane remains: the ADR-0016 uniform local-retry budget or the one ADR-0046 completion retry. The permitted successor transition has exactly one shape: an event for the **same leased target from the same `(repo, stack, node)`** carrying a new `run_id` atomically replaces the recorded one, bounded by those same budgets — and because claimed delivery is best-effort (ADR-0017's activation event is delivery-attempted, never guaranteed), the successor's first observed event may be `claimed`, `gate`, or terminal; whichever arrives first performs the rotation, so lost retry telemetry never makes an authorized retry irreconcilable. After rotation the superseded `run_id` is unknown — its replays refuse — and a successor beyond the applicable budget refuses. The lease retires on a claim-ending outcome: `pr-open`, `escalated` (the driver has released the claim and handed the issue over), or the never-activated grant's activation-window expiry — never on an intermediate `failed`; when the claim-ending event itself is lost, the reconciliation-and-expiry lane below retires it from GitHub truth or on its bounded deadline. And while the repo stays bound, that deadline never cuts a legitimate claim short: the reconciliation pass **renews** the activated lease's expiry whenever GitHub still proves the same issue assigned and `in_progress` under the claim — idempotent cache maintenance, never a GitHub write — so ADR-0016's intentionally unbounded, evidence-first zombie-recovery lane keeps its lease exactly as long as GitHub says the claim stands; once GitHub proves conclusion, reconciliation retires it.
  - *Reviewer lease — round-scoped*: a discovery answer is a batch, but a discovered PR is not indefinitely authorized work — the batch is an ordered candidate list (oldest first, unchanged), not standing authority. Each discovery lease is born **unactivated** with a bounded activation deadline (the grant activation window's analog). Activation is the authenticated `theozolith.review` event with `phase="started"` (the exact wire above) — the review counterpart of `claimed` — naming `(repo, stack, pr, round, run_id)` from the authenticated node, and it is an **acknowledged handshake, never fire-and-forget**: the Reviewer obtains the accepted activation response *before* checkout, agent launch, or any verdict-related GitHub mutation. A lost response is recoverable — the Driver resends the identical request and the identical-identity retry answers idempotent success (the wire above) — and a Reviewer that cannot confirm activation within bounded attempts **abandons the target**: no Review Run, no GitHub write, the untouched lease expiring at its deadline. The round's `phase="completed"` outcome is then accepted, bound or unbound, only when it matches the activated PR, round, `run_id`, and `(repo, stack, node)`; completion delivery stays best-effort, with reconciliation and expiry as its recovery. The batch progresses **per item**: immediately before taking up each PR, the Reviewer performs a fresh verified discovery and continues only if that PR is still present and reviewable — the fresh discovery creates or refreshes that actor's unactivated lease (re-creating an expired one included) and never resets an activated lease — then runs the activation handshake. So an earlier Review Run outlasting later targets' original deadlines strands nothing (each later target re-discovers and activates at its turn), a target removed or relabeled meanwhile is skipped, and a stopped Reviewer performs no refresh — its untouched leases expire naturally. The lease is **per verified actor** while activation is **exclusive per round**: the lease identity includes the verified `(stack, node)` binding, so two verified Reviewer Stacks discovering the same PR hold two distinct unactivated leases — a second actor's discovery never overwrites, resets, or invalidates the first's lease or its in-flight completion, and a repeated discovery by the *same* actor refreshes only its own unactivated deadline — but one round takes one reviewer: the first acknowledged `started` wins `(repo, pr, round)`, and a competing actor's `started` on that round refuses 409. When the winning round completes — or GitHub reconciliation proves it concluded — its activated lease retires and the unactivated peer leases for that now-obsolete round are invalidated with it; a peer participates again only through fresh discovery of a still-current round. If the winning activation expires before conclusion and GitHub still exposes the PR as reviewable, fresh discovery and a fresh acknowledged activation — by any verified actor — take the round over. An unactivated lease expires at its deadline with **no GitHub write** — discovery is write-free, so there is nothing to unwind — which is exactly what keeps a Reviewer dying after discovery, or an earlier PR aborting an ordered batch, from leaving the untouched PRs permanently authorized. A terminal `completed` retires only the lease matching its actor and round; a later round takes a fresh discovery and a fresh activation.
  - *Reconciliation and expiry — retirement never trusts telemetry*: event delivery stays best-effort by design — a Control outage must not fail a successful GitHub publication or verdict — so a lease cannot depend on its claim-ending event arriving. While the repo is bound, the janitor's per-repo pass **reconciles live leases against GitHub truth**: an Implementer lease retires when the issue is no longer claimed/`in_progress` and its PR or escalation state shows the claim concluded; an activated review lease retires when the PR's current labels and round state show that activated round concluded. Reconciliation is cache cleanup only — idempotent (a repeated pass over the same GitHub state is a no-op) and never itself a GitHub write; the GitHub-side corrections stay with their existing janitor lanes. Every **activated** lease additionally carries a bounded expiry derived from the budgets that already bound the work it covers — the Run liveness/zombie deadlines and the remaining retry budget for an Implementer lease, the review Run's timeout and recovery budgets for an activated round — plus an explicit grace period. The deadline bounds *unattended* authorization, not legitimate work, because no finite deadline can outlive ADR-0016's intentionally unbounded zombie-recovery lane — **renewal** covers that instead: while the repo is bound, the same reconciliation pass renews an activated Implementer lease's expiry whenever GitHub still proves the claim standing (the sub-bullet above), while an activated review lease is **never renewed past its round** — the review Run's timeout and grace finitely bound it, and there is no evidence-first indefinite Reviewer recovery lane to preserve. An unbound repo performs no GitHub read and therefore **no renewal**: the deadline stamped while bound eventually expires, and expiry performs **no GitHub read or write** — it retires the cache authorization, which *explicitly ends Control's ability to accept later facts* for that work; a node returning after that boundary meets refusal and recovers through the documented operator/GitHub procedure — this ADR does not claim every indefinitely delayed legitimate lane survives unbinding. The persisted lease row carries its lifecycle as absolute timestamps — the unactivated `activation_deadline`, the activated `expiry_deadline`, and the `last_renewal` stamp — so a Control restart changes nothing: leases, activation ownership, and deadlines read back exactly as stored (no boot-time reset or recomputation), and renewal and reconciliation simply resume on the next janitor pass. A late event after expiry refuses like any lease-less event.
  - Live leases are obligations: activated or not, they appear in the unbound-obligations scan and the state/status/TUI surfaces until reconciliation or expiry retires them — a lease is unfinished authorized work even before its first Run event arrives, and leaves the view the moment it stops being one. And leases are cache rows like every other coordination cache: deleting the cache retires them all, a late event then refuses — even while the repo is otherwise bound, because the lease, not bind state, is the operation authority — and the authoritative recovery is GitHub-side (cache-not-archive, ADR-0016).
- **Settings**: `THEOZOLITH_REPO` is retired from the Control Node; a set variable is a `ConfigError` everywhere control settings load — never silently ignored (the shipped unit never sets it; a lingering hand-configured export must not change coordination behavior without a signal). `coordination_jobs_enabled` becomes "a control PAT is present"; without a PAT, dispatch stays 503. The `serve` startup notice lists the bound repos (or that none are bound), and the sweep loop reads the bound set per pass, so a re-ingest binds or unbinds repos without a restart.
- **Store**: exact per-table identity — `repo` joins every coordination cache, keyed and typed as the underlying object demands, never by one blanket rule (NOT NULL everywhere except the janitor ledger, whose node-scoped rows are the one legitimate no-repo case):
  - `grants`, `malformed_states`, `dispatch_waits`: PRIMARY KEY `(repo, issue)`.
  - `zombie_flags`: PRIMARY KEY `(repo, issue, run_id)` — a flag is per Run, not per issue.
  - `chained_dependents`: PRIMARY KEY `(repo, dependent_pr)`.
  - `janitor_actions`: keeps its autoincrement `id` — an action ledger, several actions per `(issue, run)` must coexist — and its `repo` column is **nullable**, the only cache where it is: a repo-owned action kind (never-activated releases, zombie escalations, base-drift acts and their comment sub-keys) stores the canonical owner/name it acted in; a node-scoped kind stores NULL — never an empty-string sentinel, which would be an undocumented spelling of "no repo" that reads as a repo named nothing. The action kind decides the class at insert; the `janitor_acted` idempotency lookups on repo-owned actions include `repo`, so same-numbered issues or PRs in two workspaces never mask each other's actions; rendering shows `owner/name#N` where a repo is present and the node otherwise; and the schema bump recreates the ledger with the column like every cache — safe because the GitHub-state guards and the base-drift ledger-healing lane already make a fresh ledger act-once.
  - `drivers`: keyed by driver name; `repo` and `stack` are observational attributes recording the driver's last verified request, never part of the key — the Pinned Build, not the registry, is the authority on bindings.
  - the authorization lease (above) is a new cache table keyed `(repo, target kind, target number, stack, node)` — an issue lease and a PR lease with the same number must coexist, and so must two verified Reviewer actors' leases on one PR (the actor binding is identity, so a second discovery can never overwrite the first) — with the recorded `run_id`, the rotation count, and the lease's activation state, round, and absolute-timestamp lifecycle fields (`activation_deadline`, `expiry_deadline`, `last_renewal`) as matched attributes, never key parts — restart-stable by construction, with activation exclusivity per `(repo, pr, round)` enforced at activation time, not by the key.
  - `events`: **kept** — `repo` is ALTER-added as an extracted column (NULL on pre-amendment rows) with repo-aware indexes for the claim reads; `live_claims()` and `run_states()` group by `(repo, issue)`; repo-less legacy rows are metrics history only, excluded by a marked legacy fence everywhere claims are derived.
  - Every idempotency and clearing lookup on a repo-scoped object includes `repo` — grant activation and release, wait/malformed clearing, zombie-flag set/clear, pause record/clear, lease creation, rotation, activation, and retirement.
  The six coordination caches are cache tables (ADR-0016): the schema bump drops and recreates them and the next dispatch pass rebuilds them from GitHub — never a backfill, because a guessed repo would be exactly the wrong-repo collision the re-key prevents. The per-repo pause table and the lease table are born in this schema as the same cache class. The `events` history is preserved across the migration. Accepted gap: a Run in flight across the control upgrade loses zombie coverage — rare, and visible on GitHub either way.
- **Clients**: one `GitHubClient` factory memoized per repo over the one control PAT and one `api_url`. **v1 doctrine: one GitHub host and one control PAT per Control Node** — every bound workspace must be reachable by both (mixing github.com and a GHES instance on one Control Node is out). The single global dispatch lock stays.
- **Per-repo dispatch pause**: `grant_work` / `review_targets` catch `GitHubError` and answer the bound shape — `"issue": null` (or `"prs": []`) with a `reason`, the binding echo included like every 200 — instead of propagating a 500 — one broken repo must not make a healthy Control Node look broken. The pause is recorded in a per-repo pause cache table in the `malformed_states`/`dispatch_waits` mold — written on a failing pass, cleared on the repo's next successful pass, surfaced in `/api/v1/state`, `theozolith status`, and the TUI. ADR-0053's fail-loud dependency-read posture keeps its identity (the distinct reason text) but rides the same reason path.
- **Janitor**: every pass iterates the bound set, one client per repo, a failing repo isolated from the others exactly as one broken claim is isolated today; the per-repo pass also runs the lease reconciliation above (cache cleanup from GitHub truth, idempotent, never a write); `janitor --once` sweeps every bound repo and fails loud on an unreadable config (a human command owes a loud answer).
- **Unbinding**: removing a repo from the bound set **withdraws coordination coverage, and the withdrawal is surfaced, never silent**. Every janitor pass runs an *unbound-obligations scan*: pending grants awaiting activation, live authorization leases (activated or not), live claims (from events), zombie flags, chained-dependent links, dispatch waits and malformed rows, and dispatch pauses whose repo is no longer bound are logged and surfaced (state document, `theozolith status`, TUI) — and never acted on: **no GitHub write of any kind in an unbound repo** (no release, no unassign, no label, no base-drift escalation), and nothing new authorized (no grant, no discovery answer) — only leased facts (above) are still accepted. The `janitor_actions` ledger stays out of the obligation set: it records actions already taken, not unfinished work. The operator obligation is explicit: on unbinding, leftover GitHub claim state — assignees, `in_progress` labels, an in-flight Run's eventual PR, a chained dependent's un-swept base drift — is the operator's to resolve, by hand or by rebinding. Lifecycle:
  - *unbound before activation*: the pending grant is surfaced and expires un-released — its assignee and label stay on GitHub for the operator (releasing would be a GitHub write in a repo control no longer speaks for);
  - *unbound during a live claim*: the work finishes and publishes driver-side (GitHub truth is unaffected), and its facts still land — its events match the authorization lease, the live claim resolves, node health moves — **wherever in the claim's lifecycle the unbind falls**: before a failure (the `failed` is accepted and the lease survives into the retry lanes), between failure and retry, or mid-retry (the successor rotates the lease and its facts land the same way), because the lease is claim-scoped, not Run-scoped; after the claim concludes the lease is retired and later events refuse like any unbound event. What freezes is everything forward-looking (no new grant, no janitorial write), and the scan surfaces the live lease among the obligations until its facts conclude it — or, when the claim-ending telemetry itself was lost, until its bounded expiry retires the cache authorization with no GitHub read or write (no reconciliation and no renewal runs unbound — the scan never reads GitHub), explicitly ending Control's acceptance of later facts and leaving the GitHub cleanup — a node returning after that boundary included — to the operator recovery procedure;
  - *unbound during a GitHub failure*: the pause row and cached obligations remain scannable — the scan reads only the cache, never GitHub;
  - *after cache deletion*: the scan has nothing to say and the leases are gone — a late terminal event refuses, its completion fact lost to control (GitHub still shows the truth); the cache never backs a coverage guarantee (ADR-0016), so the authoritative recovery procedure is GitHub-side (review the unbound repo's open `in_progress` issues and worker-assigned claims); this is exactly why best-effort sweeps from cached claims were rejected;
  - *rebinding the same repo*: the keys are identical, so the rows come back into scope unchanged — activation timeouts, zombie escalation, and pause clearing resume on the next pass; no migration, no special case, and no permanently stale live claim or lease: a completion accepted under its lease while unbound has already resolved the one and retired the other, and a repo rebound before an activated lease's expiry simply resumes GitHub-truth reconciliation on the next pass.
- **Driver**: `DispatchClient` sends `repo` and `stack` on both roles and refuses an answer without the matching echoed binding on **every** 200 outcome — the binding validates before `issue`, `prs`, or `reason` is interpreted (mixed-version safety above). The Reviewer's discovery is per repo — one Reviewer Stack per workspace, matching the Implementer — and its batch progression is per item: fresh verified discovery immediately before each PR, then the acknowledged activation handshake; no checkout, agent launch, or verdict-related GitHub mutation precedes the confirmed `started`, and bounded unconfirmed attempts abandon the target.
- **Surfaces**: `/api/v1/state` publishes `repos` (the singular `repo` field is dropped — no compatibility window); every run/grant/wait/malformed/pause row carries its repo, and the dashboard Runs view, TUI, `theozolith status`, and `theozolith flags` render `owner/name#N` with per-row links.
- **Unchanged by this ADR**: cross-repo Dependency Edges stay malformed (ADR-0053) even between two bound workspaces — the Driver's PAT and the Context Tree remain bound to one repo, so the original rejection holds. Node health and quarantine stay node-scoped and repo-agnostic: a node failing consecutively in one repo is quarantined for all (node health is about the node).

## Implementation obligations

These bind the implementation issues split from #96 — each lands with the change that makes it true:

1. Identical issue numbers in two Bound Workspaces stay independent across every store and read-model path — grants, waits, malformed states, zombie flags, chained dependents, live claims, run states, and every surface.
2. Mixed-version, end to end: a new Driver against a Control Node serving the previous (repo-less) wire executes no foreign grant — the unbound response is refused before checkout and the written claim is released by the activation timeout. Response-binding negative coverage is per outcome: a missing or mismatched echoed binding on every 200 shape — grant, discovery batch, plain no-work, convergence block, dependency wait/malformed, and GitHub-error pause — is refused by the Driver with `issue`, `prs`, and `reason` uninterpreted.
3. A mismatched clone/API target fails at config load, and again at Driver startup, before any dispatch request is issued — proven by positive and negative canonicalization matrices for both validators (https/ssh/scp forms, trailing `.git`, host and owner/name case, `api.github.com` ⇔ `github.com`, GHES `/api/v3` ⇔ its own host; foreign host, foreign owner/name, `file://`, forms naming no host+repo), with the worker test rig exercising checkout through a test-only injected transport/checkout seam — never a weakened or env-conditional production validator.
4. A cross-repo run/review event is refused (403, never stored) and cannot activate, terminate, hide, or collide with another repo's same-numbered grant or claim — negative coverage per verb. The review wire's matrix is explicit: a missing required field, an unknown `phase`, the retired phase-less/`run_id`-less terminal shape, a `completed` before any accepted `started`, a conflicting `started` (wrong `run_id`, actor, or round, or a competing actor on an already-activated round), a duplicate `completed`, a replay after retirement, and each single-field identity mismatch (repo, stack, node, pr, round, run_id) refuse with the exact code — 400, 403, or 409 — and store nothing; the identical-identity `started` retry after a lost response is the one non-refusal — idempotent success with no second stored activation.
5. Schema migration preserves the `events` history, recreates the six coordination caches empty, supports repo-owned (canonical owner/name) and node-scoped (NULL `repo`) janitor actions, and retains multiple ledger entries per `(issue, run)`.
6. Unbinding surfaces pending grants, live claims, live authorization leases (activated and unactivated), and chained-dependent links without a single GitHub write (lifecycle coverage includes the chained-dependent lane); rebinding the same repo resumes normal reconciliation with no migration.
7. Dashboard, TUI, `theozolith status`, `theozolith flags`, and the event-derived Run indexes key every row and link by repository. Verdict read models and renderers count only `phase="completed"` review rows — a `started` row never renders or aggregates as a verdict.
8. Dispatch and event verification refuse a non-worker Stack: a Flight Deck Stack, a generic container Stack, and a generic process Stack each receive 403 even when node and repo match — negative coverage per shape — and a deck's own operation is unaffected throughout.
9. Implementer lease lifecycle: a first Run completing after unbinding reconciles the claim and node health; a first Run failing, the repo unbinding, and the local retry activating with a new `run_id` and succeeding reconciles the same way — and so does the completion-retry class; a retry whose `claimed` telemetry is lost still reconciles from its first observed event; a superseded `run_id`'s replay, a successor beyond the applicable retry budget, a wrong target, and a wrong `(repo, stack, node)` each refuse; final escalation retires the lease; a bound zombie-lane lease survives repeated janitor renewal and a long node absence while GitHub still shows the claim standing; unbinding stops renewal — after expiry a late returning node's events refuse and the surfaced obligation names the operator recovery path; after cache deletion a late event refuses even while the repo is still bound, and recovery is GitHub-side; rebinding leaves no permanently stale live claim or lease.
10. Reviewer lease lifecycle: a batch discovery followed by process death, or by an earlier item aborting the ordered batch, expires the untouched leases at their activation deadline with no GitHub write; a review activated and completed after unbinding reconciles; a wrong PR, round, `run_id`, or `(repo, stack, node)` refuses; the concluded round's lease is retired and a later round requires fresh discovery and activation. Cardinality and exclusivity: two verified Reviewer Stacks discovering the same PR hold independent leases — one actor completing (after unbinding included), expiring, or replaying affects only its own lease; repeated same-actor discovery refreshes only its own unactivated deadline and never resets an activated lease; only one actor activates a given round — the competing `started` is 409; the winner's completion or GitHub reconciliation invalidates the round's stale peer leases; and the winner's expiry admits a fresh actor only after fresh discovery re-establishes current GitHub eligibility.
11. Lease reconciliation and expiry: a lost `pr-open`, a lost `escalated`, and a lost completed-review event are each recovered while bound by the GitHub-truth reconciliation pass, and a repeated pass over the same state is a no-op (idempotent); a Control restart preserves live leases, activation ownership, and their absolute deadlines; a repo unbound before recovery keeps its lease surfaced until bounded expiry retires it with no GitHub read, write, or renewal; a repo rebound before expiry resumes reconciliation and renewal; an expiry followed by a late event refuses; a lease leaves the obligation surfaces exactly when reconciliation or expiry retires it.
12. Activation handshake and batch progression: a response lost after the server committed the activation is recovered by the identical retry — idempotent success, exactly one stored activation event; a conflicting retry refuses 409; no Review Run, checkout, or verdict-related GitHub write occurs without a confirmed `started`, and bounded unconfirmed attempts — permanent Control failure included — abandon the target with no GitHub write; a multi-PR ordered batch whose first review exceeds later targets' original activation deadlines still activates each later target through its per-item fresh discovery; a target removed or relabeled before its turn is skipped after fresh discovery; process death and an earlier-item exception leave untouched leases to expire naturally; oldest-first ordering is unchanged throughout.

## Consequences

- **Positive**: a wrong-repo grant becomes structurally unrepresentable **of the checkout, not merely the request body** — the request names its repo, the Pinned Build vouches for the (Stack, node, repo) binding, config load and driver startup prove the clone/API target is that repo, and the Driver refuses a response that does not echo the verified binding; identical issue numbers in two workspaces can never collide in the coordination caches; an in-flight claim's completion survives unbinding through its lease, the bounded retry lanes included — no permanently stale claim or lease, no frozen node-health counter — while a discovered-but-untouched PR's authorization expires instead of persisting; one repo's GitHub trouble pauses that repo visibly instead of 500-ing the fleet's dispatch; a lost terminal event never strands authorization (bound repos reconcile — and, while GitHub shows a claim standing, renew — leases from GitHub truth; activated leases expire on bounded, budget-derived deadlines once renewal stops); a lost activation response never wedges a Reviewer (the identical retry is idempotent) and no review work or GitHub verdict ever precedes a confirmed activation; and concurrent Reviewer Stacks on one PR hold independent discovery leases while exactly one activates any given round.
- **Negative**: the wire and the store schema break with no compatibility window — Driver and Control move together, and until the Control Node restarts onto the new wire a converged Driver's polls write-and-timeout one claim per poll interval in the old Control's repo (bounded by the activation window, but visible in that repo's issue timeline); the one control PAT must cover every bound workspace (a broader token than any single-repo deployment needed); a repo removed from the config keeps only the unbound-obligations scan's surfacing — its GitHub state is the operator's.
- **Neutral**: amends ADR-0017 (the coordination target is every Bound Workspace, named per request; responses echo the verified binding; `THEOZOLITH_REPO` retired from the Control Node), ADR-0015 (dispatch API body and exact response shapes, the review event's required `phase`, event ingestion authorization, state document), and ADR-0016 (janitor scope per bound repo; the unbound-obligations scan; the bound renewal lane exists precisely to keep its evidence-first zombie recovery unbounded); the ADR-0053 eligibility lanes are untouched; the control PAT's persisted-config gap (env-only today) remains a separate issue.

## Alternatives Considered

- **Missing-Stack fallback to the request's repo**: rejected — reopens the exact convention-not-structure footgun through a typo'd Stack name; fail-open is reserved for an unreadable or absent Pinned Build.
- **Trusting pin convergence to bound the wire skew**: rejected — the pin-eligibility gate is control-side over *node* versions and cannot gate the Control Node's own binary; the ADR-0051 update lifecycle can pair a new Driver with an old Control, so safety lives driver-side in the refused unbound response.
- **Verifying events by `repo` alone**: rejected — a repo key without authorization lets any driver-credentialed sender speak for any bound repo; ingestion authorizes `(repo, stack, node)` against the same Pinned Build dispatch uses.
- **Verifying Stack existence without shape**: rejected — a Flight Deck or generic Stack name would let dispatch or an event ride a workload that is not a pipeline worker; the verifier requires a driver-bearing, process-kind worker Stack, and the deck stays ungated because it never enters this protocol at all.
- **Refusing an unbound repo's terminal events outright**: rejected — control already authorized that work, and dropping its completion freezes the live claim and the node's failure counter forever; "rebinding resumes reconciliation" could never be honest about a fact that was refused. The lease accepts exactly the leased facts and authorizes nothing new.
- **Retiring the lease on any terminal Run event**: rejected — `failed` ends one Run, not the claim (the local and completion retries run under the same claim, and the events doctrine reserves `escalated` for the spent budget); a Run-scoped lease would drop an authorized retry's completion, recreating the exact frozen-claim contradiction the lease exists to fix. Retirement is claim-ending only: `pr-open`, `escalated`, or activation-window expiry.
- **Requiring the successor's `claimed` event before accepting its facts**: rejected — claimed delivery is best-effort by design, so demanding it would let lost telemetry permanently orphan an authorized retry; the successor's first observed event performs the rotation, within budget, whatever its phase.
- **Treating every discovered PR as indefinitely leased**: rejected — a write-free batch scan must not confer permanent authority over PRs no Reviewer round ever touched; a discovery lease expires unactivated at a bounded deadline, and expiry writes nothing to GitHub because discovery wrote nothing.
- **A new event type for review activation**: rejected — a second type would grow its own authorization, storage, and renderer paths and drift from the completion's; the existing `theozolith.review` gains a required `phase`, both halves of a round ride one authenticated shape, and read models key on `phase`, never on type.
- **Waiving review activation while the repo is bound**: rejected — two authorization lanes diverging on bind state would let a `completed` land on a round no lease ever authorized and make the unbound path untestable against the bound one; a `completed` without its accepted `started` never counts, bound or unbound.
- **Trusting terminal telemetry for lease retirement**: rejected — delivery is best-effort by design (a Control outage must never fail a successful publication or verdict), so a lost `pr-open` or completed review would strand its lease as standing authorization; bound repos reconcile leases against GitHub truth and every activated lease carries a bounded, budget-derived expiry with an explicit grace period.
- **Target-keyed Reviewer leases (last discovery wins)**: rejected — one valid Reviewer's discovery would overwrite another's lease and orphan its in-flight completion; the lease key includes the verified actor `(stack, node)`, so concurrent Reviewer Stacks hold independent discovery leases (activation stays exclusive per round) and a completion retires only its own actor's round.
- **Fire-and-forget review activation**: rejected — with a lost acknowledgment the Reviewer cannot distinguish an activated round from a refused one, so it must either run unauthorized work or abandon authorized work; activation is an acknowledged handshake, confirmed before checkout or any GitHub mutation, and bounded unconfirmed attempts abandon the target cleanly.
- **Refusing the identical `started` retry as a duplicate**: rejected (the fourth round's shape) — under at-least-once delivery the identical retry *is* the normal recovery of a lost response, and a 409 there would strand exactly the handshake it should complete; the identical activated identity answers idempotent success with no second stored event, and only conflicts refuse.
- **One-shot batch authorization**: rejected — leases minted once at batch discovery must either outlive the longest earlier review (indefinite deadlines) or strand every later target behind a long first item; discovery is re-verified per item immediately before its turn, refreshing only that actor's unactivated lease, so deadlines stay short and a stopped Reviewer's leases still die naturally.
- **A bounded expiry claimed to outlive every legitimate lane**: rejected as dishonest — ADR-0016's evidence-first zombie-recovery lane is intentionally unbounded, so no finite deadline covers it; while bound, GitHub-truth renewal carries the Implementer lease exactly as long as the claim stands, and unbinding stops renewal so expiry honestly ends Control's acceptance, with the remainder explicitly the operator's.
- **Independently completable concurrent Reviewer rounds**: rejected — two acknowledged activations on one `(repo, pr, round)` would race two verdicts onto one round's labels and state; discovery leases coexist per actor, activation is exclusive per round, the first acknowledged `started` wins, and peers re-enter only through fresh discovery of a still-current round.
- **An empty-string `repo` sentinel for node-scoped janitor actions**: rejected — an undocumented sentinel that reads as a repo named nothing and quietly satisfies NOT NULL; the column is nullable, and the action kind — not the reader's guess — decides which class a row is.
- **Counting historical `janitor_actions` among unbound obligations**: rejected — the ledger records actions already taken; an obligation is unfinished work (pending grants, live claims, flags, waits, chained dependents, pauses), nothing else.
- **Per-repo control PATs**: deferred, not rejected — v1 takes one PAT; a workspace it cannot reach degrades to the per-repo pause, which is the honest surface for the gap.
- **Honoring cross-repo edges between bound workspaces**: rejected again — ADR-0053's grounds (Driver PAT and Context Tree bound to one repo) are untouched by control coordinating several repos.
- **Best-effort janitor sweeps of unbound repos from cached live claims**: rejected — pretends a guarantee the cache-not-archive doctrine cannot back; the unbound-obligations scan surfaces without acting, and the authoritative recovery is GitHub-side.
- **Releasing an unbound repo's pending grants at unbind time**: rejected — a GitHub write in a repo control no longer speaks for; the grant is surfaced instead and the leftover claim state is explicitly the operator's.
- **Dropping the `events` table on the schema bump**: rejected — loses the metrics substrate while buying nothing; the legacy fence has the same (accepted) zombie-coverage gap.
- **Keeping HTTP 500 as the per-repo pause**: rejected — a noisy per-poll failure that makes a healthy Control Node look broken and gives operators no persistent "still paused" surface.
- **Silently ignoring a lingering `THEOZOLITH_REPO`**: rejected — an upgrade must never change coordination behavior without a signal; the fix is one `unset`.
