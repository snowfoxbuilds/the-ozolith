# ADR-0056: Multi-repo coordination — dispatch and janitor keyed by repository

## Context

ADR-0017 bound coordination to the single `THEOZOLITH_REPO` the `serve` process was started with, while ADR-0044/0047 already let several Stacks of one Worker-Type Definition each bind a different workspace. The two halves disagreed: a second Implementer Stack bound to another repo loaded cleanly, was granted issues from `THEOZOLITH_REPO`, and worked a foreign issue number in its own checkout — a wrong-repo grant enforced only by convention. Grilling 2026-09-02 (issue #96) settled the amendment: the Claim Protocol is keyed by the repository the Driver will actually check out, end to end. Post-review of PR #99 hardened four seams the first draft left open — the mixed-version update window, the gap between the request's repo and the checkout's, event ingestion trusting its sender, and the unbinding story — and made the store identity exact.

Numbering note: this decision was drafted as ADR-0055 and renumbered — that number went to the Flight Deck live-surfaces ADR, which merged first. Issue-tracker references from the grilling window ("ADR-0055, multi-repo") predate the renumber and mean this ADR.

## Decision

- **Bound Workspace** (glossary term): a repository the Control Node coordinates — the workspace of a resolved driver-bearing (process-kind) Stack in the Pinned Build, **regardless of desired state** (a stopped Implementer's zombie claims still need the janitor). A Bound Workspace is identified by the **effective GitHub host plus canonical owner/name the Driver will actually access** — the checkout-identity rules below make the `workspace` field and the effective target provably the same thing. Flight Deck workspaces are never bound (decks are not pipeline actors), and a worker Stack's dispatch-verification failure never gates a deck's operation — decks never call dispatch, a structural property, not a carve-out. The bound set scopes dispatch verification, event authorization, the janitor's sweeps, and the state document's `repos`.
- **Wire**: the dispatch request body gains `repo` (owner/name) and `stack` (the Driver's `THEOZOLITH_STACK`); a request missing either is refused 400. The Control Node verifies the pair against the Pinned Build — the named Stack must exist, be placed on the authenticated node, and resolve to exactly that workspace — otherwise **403** with a detail naming the Stack and both repos. A missing Stack is a 403, not a soft no-grant: a `reason` response is reserved for *verified* requests with nothing eligible, so a typo'd Stack name can never fall back to the request's repo. **Every successful answer echoes the verified binding**: a grant carries `repo` and `stack` alongside `issue`, and a discovery answer carries them alongside `prs` — the response names what was verified, and the Driver refuses an answer whose binding is absent or differs from what it asked (see mixed-version safety). Verification is fail-open only while the Pinned Build is unreadable or absent (the ADR-0004 deletion-test boot — the existing posture of the pin gates); this is the dev shape's door, alongside declaring a real Stack and setting `THEOZOLITH_STACK`. Reviewer discovery verifies identically.
- **Mixed-version safety**: the wire breaks with no backward compatibility, and pin convergence alone does **not** make that safe. The pin-eligibility gate is control-side and gates *node* versions; it cannot gate the Control Node's own binary, and the ADR-0051 update lifecycle — nodes converge by heartbeat while the control service restarts separately — can run a new Driver against an old Control Node. An old Control ignores unknown request keys and would grant from its single configured repo. Safety is therefore driver-side: a new Driver **refuses any dispatch or discovery response whose echoed binding is absent or names a different `(repo, stack)` than it sent — before checkout, before any work**. The refused grant recovers through the existing lane: the Driver never emits a claimed event, so the old Control's already-written claim expires in the activation window and its janitor releases it (unassign + remove in_progress) exactly as for any never-activated grant; the Driver's normal poll pacing bounds the churn to one written-and-released claim per poll until the Control Node restarts onto the new wire. The reverse pairing is inert: an old Driver's repo-less request meets the new endpoint's 400 and nothing is written. An end-to-end mixed-version test is an implementation obligation (below): a new Driver against a Control serving the previous wire executes no foreign issue.
- **Checkout identity**: the repository named on the wire must be the repository the Driver actually touches — three rules make the `workspace` field, the wire's `repo`, and the checkout one thing. (1) *Injection-only identity spellings*: the resolved Stack env's `THEOZOLITH_REPO` comes only from the resolved workspace and `THEOZOLITH_STACK` only from the Stack's own name — a worker-type Stack `[env]` naming either refuses at config load, joining the ADR-0045/0047/0048 guard family (an env override here is the same convention-not-structure hole the wire just closed, and an overridden Stack name is impersonation of a sibling binding). (2) *Provable clone/API targets*: a declared `THEOZOLITH_CLONE_URL` or `THEOZOLITH_API_URL` on a driver-bearing Stack is admitted only when, after canonicalization (host case, trailing `.git`, the https and ssh spellings of the one deployment host), it provably addresses the same bound host and owner/name; anything else — another host, another repo, a form that cannot name a host+repo at all (`file://`) — refuses at ingest and config load, before any driver launches. (3) *Driver startup re-check*: the Driver re-derives the same comparison at startup and fails before its first dispatch request when its effective clone/API target and its `THEOZOLITH_REPO` disagree — the belt for hand-set env in the dev shape, where no Pinned Build exists to lint (the worker test rig's `file://` remotes live only there).
- **Events**: `theozolith.run` and `theozolith.review` events carry `repo` **and `stack`**, and ingestion authorizes them exactly as dispatch verifies: `(repo, stack, authenticated node)` against the Pinned Build. A missing or empty key is 400 naming it; a Stack that is absent from the pin, placed on another node, or resolving a different workspace is **403 and the event is never stored**; an absent Pinned Build is accepted (the same ADR-0004 dev door as dispatch); an unreadable one is accepted under the same posture as dispatch's broken-config door — fail-open is confined to loudly-visible config breakage, never to a mismatch. Authorization is what keeps the store honest: grant activation deletes on the *verified* `(repo, issue)` and claim reads group by `(repo, issue)`, so an event can never activate, terminate, hide, or collide with another repo's same-numbered grant or claim. `theozolith.run.progress` stays keyed by `run_id` and `theozolith.error` stays node/component-scoped — unchanged.
- **Settings**: `THEOZOLITH_REPO` is retired from the Control Node; a set variable is a `ConfigError` everywhere control settings load — never silently ignored (the shipped unit never sets it; a lingering hand-configured export must not change coordination behavior without a signal). `coordination_jobs_enabled` becomes "a control PAT is present"; without a PAT, dispatch stays 503. The `serve` startup notice lists the bound repos (or that none are bound), and the sweep loop reads the bound set per pass, so a re-ingest binds or unbinds repos without a restart.
- **Store**: exact per-table identity — `repo TEXT NOT NULL` joins every coordination cache, keyed as the underlying object demands, never by one blanket rule:
  - `grants`, `malformed_states`, `dispatch_waits`: PRIMARY KEY `(repo, issue)`.
  - `zombie_flags`: PRIMARY KEY `(repo, issue, run_id)` — a flag is per Run, not per issue.
  - `chained_dependents`: PRIMARY KEY `(repo, dependent_pr)`.
  - `janitor_actions`: keeps its autoincrement `id` — an action ledger, several actions per `(issue, run)` must coexist; repo-owned actions (claim releases, zombie escalations, base-drift) carry their repo; a node-scoped janitorial action carries none.
  - `drivers`: keyed by driver name; `repo` and `stack` are observational attributes recording the driver's last verified request, never part of the key — the Pinned Build, not the registry, is the authority on bindings.
  - `events`: **kept** — `repo` is ALTER-added as an extracted column (NULL on pre-amendment rows) with repo-aware indexes for the claim reads; `live_claims()` and `run_states()` group by `(repo, issue)`; repo-less legacy rows are metrics history only, excluded by a marked legacy fence everywhere claims are derived.
  - Every idempotency and clearing lookup on a repo-scoped object includes `repo` — grant activation and release, wait/malformed clearing, zombie-flag set/clear, pause record/clear.
  The six coordination caches are cache tables (ADR-0016): the schema bump drops and recreates them and the next dispatch pass rebuilds them from GitHub — never a backfill, because a guessed repo would be exactly the wrong-repo collision the re-key prevents. The `events` history is preserved across the migration. Accepted gap: a Run in flight across the control upgrade loses zombie coverage — rare, and visible on GitHub either way.
- **Clients**: one `GitHubClient` factory memoized per repo over the one control PAT and one `api_url`. **v1 doctrine: one GitHub host and one control PAT per Control Node** — every bound workspace must be reachable by both (mixing github.com and a GHES instance on one Control Node is out). The single global dispatch lock stays.
- **Per-repo dispatch pause**: `grant_work` / `review_targets` catch `GitHubError` and answer `{"issue": None, "reason": ...}` instead of propagating a 500 — one broken repo must not make a healthy Control Node look broken. The pause is recorded in a per-repo pause cache table in the `malformed_states`/`dispatch_waits` mold — written on a failing pass, cleared on the repo's next successful pass, surfaced in `/api/v1/state`, `theozolith status`, and the TUI. ADR-0053's fail-loud dependency-read posture keeps its identity (the distinct reason text) but rides the same reason path.
- **Janitor**: every pass iterates the bound set, one client per repo, a failing repo isolated from the others exactly as one broken claim is isolated today; `janitor --once` sweeps every bound repo and fails loud on an unreadable config (a human command owes a loud answer).
- **Unbinding**: removing a repo from the bound set **withdraws coordination coverage, and the withdrawal is surfaced, never silent**. Every janitor pass runs an *unbound-obligations scan*: pending grants awaiting activation, live claims (from events), zombie flags, dispatch waits and malformed rows, and dispatch pauses whose repo is no longer bound are logged and surfaced (state document, `theozolith status`, TUI) — and never acted on: **no GitHub write of any kind in an unbound repo** (no release, no unassign, no label). The operator obligation is explicit: on unbinding, leftover GitHub claim state — assignees, `in_progress` labels, an in-flight Run's eventual PR — is the operator's to resolve, by hand or by rebinding. Lifecycle:
  - *unbound before activation*: the pending grant is surfaced and expires un-released — its assignee and label stay on GitHub for the operator (releasing would be a GitHub write in a repo control no longer speaks for);
  - *unbound during a live Run*: the Run finishes and publishes driver-side (GitHub truth is unaffected), but its events now fail Stack authorization and its cache rows freeze — the scan carries them until the operator acts or rebinds;
  - *unbound during a GitHub failure*: the pause row and cached obligations remain scannable — the scan reads only the cache, never GitHub;
  - *after cache deletion*: the scan has nothing to say — the cache never backs a coverage guarantee (ADR-0016), so the authoritative recovery procedure is GitHub-side (review the unbound repo's open `in_progress` issues and worker-assigned claims); this is exactly why best-effort sweeps from cached claims were rejected;
  - *rebinding the same repo*: the keys are identical, so the rows come back into scope unchanged — activation timeouts, zombie escalation, and pause clearing resume on the next pass; no migration, no special case.
- **Driver**: `DispatchClient` sends `repo` and `stack` on both roles and refuses an answer without the matching echoed binding (mixed-version safety above). The Reviewer's discovery is per repo — one Reviewer Stack per workspace, matching the Implementer.
- **Surfaces**: `/api/v1/state` publishes `repos` (the singular `repo` field is dropped — no compatibility window); every run/grant/wait/malformed/pause row carries its repo, and the dashboard Runs view, TUI, `theozolith status`, and `theozolith flags` render `owner/name#N` with per-row links.
- **Unchanged by this ADR**: cross-repo Dependency Edges stay malformed (ADR-0053) even between two bound workspaces — the Driver's PAT and the Context Tree remain bound to one repo, so the original rejection holds. Node health and quarantine stay node-scoped and repo-agnostic: a node failing consecutively in one repo is quarantined for all (node health is about the node).

## Implementation obligations

These bind the implementation issues split from #96 — each lands with the change that makes it true:

1. Identical issue numbers in two Bound Workspaces stay independent across every store and read-model path — grants, waits, malformed states, zombie flags, chained dependents, live claims, run states, and every surface.
2. Mixed-version, end to end: a new Driver against a Control Node serving the previous (repo-less) wire executes no foreign grant — the unbound response is refused before checkout and the written claim is released by the activation timeout.
3. A mismatched clone/API target fails at config load, and again at Driver startup, before any dispatch request is issued.
4. A cross-repo run/review event is refused (403, never stored) and cannot activate, terminate, hide, or collide with another repo's same-numbered grant or claim — negative coverage per verb.
5. Schema migration preserves the `events` history, recreates the six coordination caches empty, and retains multiple janitor actions per `(issue, run)`.
6. Unbinding surfaces pending grants and live claims without a single GitHub write; rebinding the same repo resumes normal reconciliation with no migration.
7. Dashboard, TUI, `theozolith status`, `theozolith flags`, and the event-derived Run indexes key every row and link by repository.

## Consequences

- **Positive**: a wrong-repo grant becomes structurally unrepresentable **of the checkout, not merely the request body** — the request names its repo, the Pinned Build vouches for the (Stack, node, repo) binding, config load and driver startup prove the clone/API target is that repo, and the Driver refuses a response that does not echo the verified binding; identical issue numbers in two workspaces can never collide in the coordination caches; one repo's GitHub trouble pauses that repo visibly instead of 500-ing the fleet's dispatch.
- **Negative**: the wire and the store schema break with no compatibility window — Driver and Control move together, and until the Control Node restarts onto the new wire a converged Driver's polls write-and-timeout one claim per poll interval in the old Control's repo (bounded by the activation window, but visible in that repo's issue timeline); the one control PAT must cover every bound workspace (a broader token than any single-repo deployment needed); a repo removed from the config keeps only the unbound-obligations scan's surfacing — its GitHub state is the operator's.
- **Neutral**: amends ADR-0017 (the coordination target is every Bound Workspace, named per request; responses echo the verified binding; `THEOZOLITH_REPO` retired from the Control Node), ADR-0015 (dispatch API body and response, event ingestion authorization, state document), and ADR-0016 (janitor scope per bound repo; the unbound-obligations scan); the ADR-0053 eligibility lanes are untouched; the control PAT's persisted-config gap (env-only today) remains a separate issue.

## Alternatives Considered

- **Missing-Stack fallback to the request's repo**: rejected — reopens the exact convention-not-structure footgun through a typo'd Stack name; fail-open is reserved for an unreadable or absent Pinned Build.
- **Trusting pin convergence to bound the wire skew**: rejected — the pin-eligibility gate is control-side over *node* versions and cannot gate the Control Node's own binary; the ADR-0051 update lifecycle can pair a new Driver with an old Control, so safety lives driver-side in the refused unbound response.
- **Verifying events by `repo` alone**: rejected — a repo key without authorization lets any driver-credentialed sender speak for any bound repo; ingestion authorizes `(repo, stack, node)` against the same Pinned Build dispatch uses.
- **Per-repo control PATs**: deferred, not rejected — v1 takes one PAT; a workspace it cannot reach degrades to the per-repo pause, which is the honest surface for the gap.
- **Honoring cross-repo edges between bound workspaces**: rejected again — ADR-0053's grounds (Driver PAT and Context Tree bound to one repo) are untouched by control coordinating several repos.
- **Best-effort janitor sweeps of unbound repos from cached live claims**: rejected — pretends a guarantee the cache-not-archive doctrine cannot back; the unbound-obligations scan surfaces without acting, and the authoritative recovery is GitHub-side.
- **Releasing an unbound repo's pending grants at unbind time**: rejected — a GitHub write in a repo control no longer speaks for; the grant is surfaced instead and the leftover claim state is explicitly the operator's.
- **Dropping the `events` table on the schema bump**: rejected — loses the metrics substrate while buying nothing; the legacy fence has the same (accepted) zombie-coverage gap.
- **Keeping HTTP 500 as the per-repo pause**: rejected — a noisy per-poll failure that makes a healthy Control Node look broken and gives operators no persistent "still paused" surface.
- **Silently ignoring a lingering `THEOZOLITH_REPO`**: rejected — an upgrade must never change coordination behavior without a signal; the fix is one `unset`.
