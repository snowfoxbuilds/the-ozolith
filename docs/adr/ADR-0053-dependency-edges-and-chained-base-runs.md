# ADR-0053: Dependency Edges, dependency-aware dispatch, and Chained-Base Runs

## Context

The pipeline spec claimed "parallel PRs are serialized via issue dependencies" with no enforcing mechanism: dependencies existed only as prose, dispatch listed plan_ready issues newest-first (GitHub's default sort — granting the *last* issue of a plan first, since plans publish foundations-first), and a dependent issue could not start until its blocker's PR carried the human merge stamp — serializing the pipeline on human availability when review itself is agent-fast. The grilling of issue #78 (2026-08-27) settled the design; the planning-side half (publishing the relations) is config-repo work (ozolith-configs#3).

## Decision

- **Dependency Edges are the machine-readable ordering truth.** GitHub-native `blocked by` relations between workspace-repo issues, published at planning time, hand-editable in the UI, rebuildable from GitHub alone; body prose ("depends on #N") is a mirror, never a source. Only true build-on dependencies get edges. Sub-issue links group a plan under a parent tracking issue and carry no ordering semantics; the enforcement side consumes no sub-issue links in V1, and nothing auto-closes issues or PRs — the parent stays human-closed. A cross-repo edge on a claimable work issue is a malformed state; cross-repo edges on parent/tracking issues are ignored and never followed — cross-repo work enters ordering only through a locally created stand-in sub-issue in the workspace repo.
- **Dependency-aware dispatch — claim selection only.** A plan_ready issue is grantable only when every Dependency Edge is satisfied: the blocker issue is closed as completed (`state_reason`), or the Chained Base go-ahead holds. A blocker closed as not_planned does not satisfy its edge — the dependent is surfaced as a malformed state (the failed + plan_ready precedent) for the human to re-edge or abandon. A dependency cycle in the blocked-by closure is detected at dispatch and surfaced as malformed, never granted; the driver's pre-Run closure walk remains a fail-loud infra-class backstop. The dependency graph is read live per grant (reconcile-to-GitHub by construction); store caching is permitted later only as cache, never authority.
- **Creation-order draining.** Both dispatch listings pass `sort=created&direction=asc`: issues drain in creation (= plan) order, and Reviewer discovery drains oldest-first — load-bearing for chains, where a blocker must be reviewed before its dependents' go-ahead can hold.
- **Chained Base go-ahead.** An open blocker qualifies when its PR — resolved via the deterministic `ozolith/issue-N` branch — carries `pr_ready` + `needs_human` without `blocked`: the label state only an approve verdict produces (approve-with-nits is forbidden, so an approved branch is stable by convention). Labels only; dispatch never parses verdict comments. The open blockers' PRs must form a single chain by `base_ref` linkage — each targets the default branch or another open blocker's branch, with exactly one tip — and the dependent bases on the tip. An open blocker with no PR, or parallel open blocker lines (fan-in), means wait. Preconditions, checked mechanically from repo settings at dispatch: merge commits allowed, squash and rebase merge disabled (both rewrite SHAs and break chained diffs), delete-branch-on-merge enabled. When they fail, chaining is off with a visible dispatch reason and dependents wait for full merge. There is no mechanical rebase step: no actor owns a dependent post-PR, and a rebase force-push would invalidate the Reviewer's designated resume commit.
- **Driver mechanics.** The grant carries claim authority only (ADR-0017 as amended); the driver re-resolves the chain fresh at checkout and proceeds with current truth — every blocker merged means the default branch; a live chain means its current tip — and reconciles the base again at ship time, on every ship path (fresh Run, resume round, completion retry): an existing dependent PR is reloaded (GitHub may have retargeted it mid-session), and a recorded base branch that no longer exists must be PROVEN merged — its PR resolved across all states — with the dependent following the merged PR's actual base branch, layer by layer through any already-merged chain, to the live successor (the default branch only when that is the true successor base), verifying the recorded base commit is contained in the resolved target before publishing against it. Branch absence alone is never merge proof: an absent, closed-unmerged, or otherwise unverifiable blocker PR fails the Run loudly as infra — never a guessed base. The dependent PR targets the blocker branch. The driver-owned, machine-parseable **"Based on #N at `<sha>`"** PR-body zone is the durable base record (survives a lost control DB; not model prose — same class as the verdict machine block) and the human-gate warning: GitHub does not structurally prevent merging the dependent first (that would merge it into the blocker branch), so the zone says merge #N first; the zone is removed only when the effective base is truly the default branch, and otherwise warns for the actual remaining blocker. GitHub's retarget-on-branch-delete moves the dependent to the merged PR's base branch when the blocker merges — it reaches the default branch only when that is the actual successor base.
- **Janitor base-drift lane — the enumerated-exception extension (amends ADR-0016/0017).** Only when the dependent PR is open with a Based-on zone, the named blocker PR is still open, and the blocker branch tip no longer matches the recorded SHA, the janitor applies `blocked` + `needs_human` on the dependent PR with a comment naming the blocker and both SHAs; idempotent, never auto-repair. Blocker merged-and-branch-deleted is the healthy retarget path, not drift. A human-rejected or abandoned blocker is a human act: the dashboard lists its chained dependents; no automated write.
- **Context Tree dependency closure.** `input/deps/issue-N/` carries the full transitive closure over Dependency Edges (same-repo only), each dependency serialized exactly like the primary issue/PR within the OWNER/MEMBER authority boundary, closed/merged dependencies included with state and merge SHA — no depth cap, no relevance filtering, no truncation — plus a top-level `input/deps/index` in topological order. The Decisions Section of an unlanded blocker PR is the highest-value item.
- **Review Run workspace parity (amends ADR-0014's review-inputs shape).** Every Review Run gets a full sanitized PR-branch checkout with history — same reference-clone machinery and credential isolation as Implementer Runs, base ref fetched — plus Context Tree parity: `input/issue/`, `input/pr/`, `input/deps/`. The driver supplies the PR's base commit and the cumulative changed-file list, computed driver-side from git (`--name-status` against the PR's own base — also feeding the mechanical review signals); the truncated single-blob diff is retired — the agent runs `git diff` itself. Tests are a permission, not a step: the Reviewer may build and run anything in its workspace at its discretion, citing results in the verdict. Capability parity: inside the container a Review Run can do everything an Implementer Run can; the asymmetry is the Output Proposal schema (a verdict, never applied code) and the driver boundary. Stated consequence, not product-enforced: the Reviewer worker type's base image carries the workspace toolchain.
- **Prompt contracts.** Implementer on a Chained Base: the base includes unmerged work from #N — treat its interfaces as authoritative, do not refactor it, record blocking defects in the Decisions Section and proceed best-effort. Reviewer: deviation/risk grading is relative to the chained base; the diff under review is the dependent's changes only.
- **Rejected for now**: the aggressive chaining knob (chain on unreviewed `pr_ready`, even `risk:low`) — the approve-gate overlap captures most of the throughput win at a fraction of the stacked-rebase risk; do not re-propose without evidence that it is insufficient. Sub-issue-driven parent auto-close — closing is human authority.

## Consequences

- **Positive**: the human stamps plan_ready on an entire approved plan in one sitting and dispatch releases issues as blockers land — the "come back and stamp the next one" loop dies; dependents overlap exactly the long pole (the human merge stamp); creation-order draining fixes the newest-first inversion even for edge-less plans; base drift is mechanically detectable from public GitHub state; the Reviewer judges a real workspace (diffs, history, tests) instead of a truncated blob.
- **Negative**: dispatch pays per-grant API reads (edges plus one PR lookup per open blocker); the janitor gains a coordination write lane — accepted only under its narrow, mechanically-verifiable trigger; review rounds get heavier (clone, larger discoverable surface, optional tests) and the Reviewer image must carry the toolchain; chaining is unavailable on squash/rebase workspaces (dependents wait for full merge there).
- **Neutral**: amends ADR-0016/0017 (janitor enumerated exception) and ADR-0014 (review inputs); ADR-0002's residual invariant survives — eligibility filtering is claim *selection* inside existing dispatch authority; the planning-side publication contract lives in the config repo (ozolith-configs#3); glossary gains Dependency Edge and Chained Base, and Review Run is redefined.

## Alternatives Considered

- **Verdict-comment parsing at dispatch for the go-ahead**: rejected — `pr_ready` + `needs_human` − `blocked` is produced only by approve; labels keep dispatch out of comment parsing and hand-edited labels stay meaningful.
- **Mechanical rebase-onto-main for dependents of squash-merged blockers**: rejected — no actor owns a dependent post-PR (the Implementer released the claim, the Reviewer never runs workspace git, control has no git), and the force-push invalidates the Reviewer's resume commit; scoping chaining to merge-commit workspaces deletes the entire mechanism.
- **Control-store dependency graph as the read source**: rejected as authority (GitHub owns coordination truth; the store is cache-never-archive); per-grant live reads are cheap at this fleet size.
- **Honoring cross-repo edges**: rejected — drags the driver's PAT and the Context Tree across a repo boundary the authority model never contemplated; silent-ignore was also rejected (a dropped ordering constraint should be loud).
- **Deps-only Reviewer inputs (keep curated flat inputs, add `input/deps/`)**: rejected — dependencies would be serialized richer than the primary PR itself, and the curated, truncated inputs already violated the never-truncate doctrine; full workspace parity chosen.
- **Cycle detection only driver-side (fail-loud pre-Run)**: rejected as primary — a deterministic config-shaped failure would burn container launches and the local retry; dispatch walks the edges anyway and the malformed-state lane is free.
