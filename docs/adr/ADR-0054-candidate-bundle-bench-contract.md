# ADR-0054: Candidate Bundles and the published bench contract

## Context

SilverquiLLM-bench adopted the ruling that a Benchmark Candidate IS a worker-type definition (SilverquiLLM-bench#39): benchmark evidence transfers to deployment because both consume the identical derived image. Its 2026-08-27 correction comment established that a worker-type TOML is not self-contained and promised ozolith-side tooling — a self-contained candidate export, an independently verifiable identity spec, a standalone build path, and job-dir contract stability. The operator now also wants Reviewers benchmark-able, which that comment had deferred. TheOzolith must decide whether, and in what form, to expose its internals as a public contract.

## Decision

TheOzolith publishes a versioned bench-export contract (docs/specs/BENCH-CONTRACT.md) and owns all four of its parts; the bench side owns modes, task synthesis, evaluation, results, and scheduling.

1. **Candidate Bundle, exported from a local config-repo-shaped directory — never from the Pinned Build.** `theozolith candidate export` runs the ingest resolution machinery (per-tool knowledge compile, base digest resolution, pins, instruction hash) against an already-materialized local config-repo-shaped directory and writes a self-contained, docker-buildable bundle: `candidate.json` manifest, the compiled knowledge tree for the candidate's adapter tool only, and a Dockerfile emitted by the Node Daemon's own codegen. v1 accepts local directories only: URLs are rejected, callers clone repositories themselves (preferably at an immutable commit), and remote Git retrieval, Git auth, ref resolution, submodules, and LFS are non-goals. A private base resolves via the ADR-0049 Docker-compatible credential model — a caller-supplied `DOCKER_CONFIG` — never a raw value in argv, and the credential reaches no bundle byte, log, or evidence. Benchmark variants never enter deployment config history; benchmark↔deployment equivalence is identity-hash equality, not shared provenance. Secret slot names travel, values never.
2. **Identity is the triple (base digest, instruction hash, adapter name), kind-agnostic, always recomputed — and verification authenticates the whole build context.** The production instruction-hash formula (ADR-0045/0052) is published with golden vectors; `theozolith candidate verify` recomputes from bundle bytes everything capable of affecting the built image — strict manifest parse (unknown fields refused), knowledge-pin recomputation, materialized setup and identity triple, wire-recipe reconstruction, an exact byte match of the Dockerfile against the shared production codegen, and an allowlisted bundle layout (no unexpected entries, symlinks, or traversal) — refusing on any mismatch before Docker is invoked. The supported standalone build is a wrapper that stages a private snapshot, fully verifies it, builds that same snapshot, tags only after verification, and cleans up on every exit path; raw `docker build` stays mechanically possible but yields no trusted benchmark evidence. Implementer vs reviewer is a benchmark-mode property — the manifest's `mode` field alone selects the proposal schema, so one candidate runs either kind.
3. **The Run Contract is the production Run at full fidelity, for both kinds.** Bench replays the job-dir contract with the production prompt renderers, PR-body composition, gate-step sequence, and GitHub Relay (amended 2026-09-03, ADR-0057) — exposed as stable entry points in the worker package's public API, never copied. The first-party gate runs in implementer-mode bench runs. The relay runs in every bench run with an injectable upstream: live (a real scratch repository carrying the task's issue and, in review mode, its branch and PR — the full-fidelity shape) or none (every request refused with an explicit message, recorded as a benchmark-mode variable). A Review Run job dir is constructible from a synthetic issue + a git branch + an implementer-contract output (no live GitHub PR), pinned at round 1 of 3 — the prompt carries the issue body and the composed PR body inline, so the no-upstream mode still presents a complete task. The reviewer proposal schema is unchanged — no structured findings field; evaluation parses prose bench-side.
4. **Versioning is visibility, not immutability — three keys with exact ownership.** `schema_version` (currently 1; 2 is the accepted successor reserved for the GitHub Relay surface — decided 2026-09-03, ADR-0057 — and activated only by its implementation PR, which lands the runtime constant, the job-dir layout, the prompt-renderer signature, the relay entry point, the bench behavior, this wording, and the Changelog transition atomically, so the current value stated here and the code constant never disagree) owns the Run Contract (job-dir layout, proposal schemas, prompt-renderer/PR-body/gate/validation entry points, the GitHub Relay entry point); `bundle_format_version` (2 — amended 2026-09-02, ADR-0055) owns the bundle format, structure verification, and verified-build behavior; `identity_spec_version` (2 — amended 2026-09-02, ADR-0055) owns canonical serialization and identity computation. The values here are the current contract; the Changelog in BENCH-CONTRACT.md is the authoritative history of each bump. Every exposed surface maps to exactly one key; CLI syntax follows the product CLI policy and bumps no contract version. Every breaking change bumps its owning key and lands an entry in the spec's Changelog — no silent breaks, no compatibility windows.

## Consequences

- **Positive**: benchmark evidence transfers to deployment by construction — same image, same prompts, same gate, same proposal validation. Experimental candidates stay out of the Pinned Build. Identity verification needs no trust in the exporter. Reviewer benchmarking gets a contract without a schema change. Contract drift between bench and production becomes structurally impossible where entry points are shared.
- **Negative**: the job-dir layout, proposal schemas, prompt renderers, and gate sequencing become public surface — internal churn now carries a version-bump and changelog obligation. Export re-resolves base digests, so the same source can yield different identities across time as tags move (recorded, but a footgun for naive comparisons). The Control package becomes a bench-host dependency.
- **Neutral**: the standalone build wrapper carries snapshot-staging and cleanup obligations in exchange for closing the verify-then-mutate race; raw `docker build` remains possible but untrusted. A private base needs the caller to stage a `DOCKER_CONFIG` (no Fernet store off the Control Node — and no second credential store invented). Callers wanting a remote source clone it themselves first. Deviating from the production prompt template remains possible, but as a recorded benchmark-mode variable.

## Alternatives Considered

- **Export from the Pinned Build only**: strongest provenance story, but forces every benchmark variant through the deployment's machine-owned config history and a control-node ingest; identity-hash equality already carries the transfer guarantee without shared provenance.
- **Bench maintains its own copies of prompts/gate/composition**: every production template improvement becomes silent, unmeasured drift between what is benchmarked and what deploys — the exact failure the candidate ruling exists to prevent.
- **Freeze the job-dir contract**: immutability is unpayable while the pipeline is young; the promise worth making is no silent breaks.
- **Structured findings field in the reviewer proposal (schema v2)**: changes the production contract for bench convenience, inverting the fidelity principle; the LLM judge must read prose regardless. Revisit only if prose judging proves unreliable.
- **Worker kind in candidate identity**: would fork every candidate into an implementer and a reviewer twin with identical images; kind is run-shape, and the manifest already selects it.
- **Git URLs as export sources in v1**: pulls Git authentication, ref resolution, submodules, and LFS into the exporter's threat surface for no contract gain — a caller-side clone at an immutable commit yields the same bytes with the trust decision where it belongs.
- **Private-base credential as a raw CLI flag or env value**: argv leaks through process listings and shell history, and env values leak through diagnostics; ADR-0049's Docker-compatible model already exists, so export discovers credentials from a caller-supplied `DOCKER_CONFIG` instead.
- **Verify only the identity triple, not the Dockerfile and layout**: a bundle could carry a smuggled `RUN` or an extra build-context file while its recorded identity still verified — the identity would authenticate an image nobody actually builds. Full build-context authentication closes this.

## Amendments

- **2026-09-02 (ADR-0055)**: decision 4's values move to `bundle_format_version` 2 and `identity_spec_version` 2 — the Candidate Bundle gains the baked Agent Policy tree under `policy/` with the required `policy`/`policy_pin` manifest keys, and the canonical identity serialization gains the same keys conditionally (pre-existing vectors byte-identical). The original decision published all three keys at 1.
- **2026-09-03 (ADR-0057)**: decision 3 amended — the Run Contract gains the GitHub Relay as `schema_version` 2 surface (decision 4 records 2 as the accepted successor of the current 1, activated atomically by the implementation PR that lands the surface together with the current-version wording and the Changelog transition): the job dir carries the relay socket, `worker`'s API exports the relay with an injectable upstream, and two upstream modes exist (live, none). A real scratch repository carrying the task's objects is the full-fidelity bench shape; running with no repository is a permitted, recorded benchmark-mode variable. The Context Tree leaves the job dir; the prompt carries the task statement inline, so a review job dir stays constructible without a live PR.
