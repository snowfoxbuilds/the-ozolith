# Node Substrate

Cluster-management layer of TheOzolith: Control Node, Node Daemon, Config Repo, Stacks, secrets, and extension points. The coding pipeline ([AGENTIC-CODING-PIPELINE.md](AGENTIC-CODING-PIPELINE.md)) is one consumer of this substrate.

## Context

TheOzolith is cluster management, not container management: it manages physical nodes that run declarative workloads. The substrate serves any adopter of a coding-worker fleet; operator-specific needs are expressed as configuration in a private Config Repo, never as product code.

## Design

### Components

One definition per component; [CONTEXT.md](../../CONTEXT.md) is the canonical glossary.

- **Control Node** — the product's central service (always its own systemd unit, never a Stack): claim dispatcher, secret store, config authority, artifact server, operator surfaces.
- **Node Daemon** — the uncontainerized daemon that makes a box a Container-Host: heartbeats, pin and desired-state reconciliation, local derived-image builds, supervision of every Stack in its cgroup.
- **Config Repo** — git-backed, human-authored single source of truth for one deployment: Stacks, worker-type definitions, overlays, secret names, `control.toml`, `drivers/`, `knowledge/` (per-worker-type knowledge roots; ADR-0048). Lives wherever the operator likes (ingest accepts a local path or a git URL), carries no computed pins, never secret values.
- **Pinned build** — the machine-owned git tree at the control data dir's `configs/` that only `theozolith config ingest` commits to (ADR-0048): the lint-checked, pin-resolved, knowledge-compiled materialization of one Config Repo commit, source-SHA-stamped. Config load reads it and the config distribution serves it; rollback is `git revert` there — the resolved pins exist nowhere else. Durable git-class state (ADR-0024).
- **Product distribution** — the versioned public artifact (Node Daemon, built-in drivers, harness, adapters), pinned in product.toml.
- **Config distribution** — the hash-pinned artifact packaged from the pinned build's `drivers/` + compiled `knowledge/` trees on config change (one hash covers both, kept under the original drivers-hash name for protocol stability), reconciled like the product pin (ADR-0042/0048).
- **Stack** — the generic declarative workload unit: name, workload (container or process kind), placement, desired state. Deliberately thin; never carries worker identity — the only worker content it may carry is the per-placement bindings (env, workspace, secret-slot rebindings; ADR-0047).
- **Worker-type definition** — the complete customization unit for one worker: base image + setup instructions, optional Knowledge Source (`knowledge = "knowledge/<name>"`; ADR-0048), driver reference, Agent adapter, model + reasoning effort, workspace (target repo), secret names. Workspace and each secret slot's binding are the type's defaults — a Stack may rebind either per placement, and an empty slot name declares a binding every instantiating Stack must provide (ADR-0047). A worker Stack instantiates exactly one. Model and reasoning effort are typed fields the derived-image compiler materializes into the tool's native config at build; a model the adapter cannot map fails the build (grilling 2026-08-10).
- **Driver** — the credentialed node-resident half of a worker, run as a process-kind Stack: all GitHub I/O, Claim Protocol, Run lifecycle. Named as `builtin:<name>` or `drivers/<name>`.
- **Agent Harness** — immutable product plumbing, PID 1 of every run container; invokes the Agent adapter one-shot and talks to the driver only through the job directory. Never a per-deployment variable.
- **Agent adapter** — the per-tool invocation layer (Claude Code, Pi) the harness calls; selected by the worker-type definition. "Default harnesses" are really default adapters.
- **Run** — one ephemeral, headless, credential-free container executing one agent session.
- **Flight Deck** — the interactive, human-driven, credentialed agent container Stack: the only attach target and the knowledge-authoring surface.
- **Knowledge Source** — a worker-type definition's `knowledge = "knowledge/<name>"` reference into the Config Repo's knowledge tree, pinned by an ingest-computed per-tree content hash and compiled at ingest (ADR-0048); baked into HOTL derived images at build, read-only bind-mounted into Flight Decks.
- **Operator surfaces** — the TUI (`theozolith top` / `theozolith status`, primary), the frozen web UI, and the web terminal (PTY bridge). Pure API consumers.

### Node model

- The Node Daemon (renamed from "Node Agent" — Agent is reserved for LLM tool configs; ADR-0013) is the uncontainerized TheOzolith daemon installed on every physical node, registering it as a Container-Host. It runs as a systemd unit with cgroup kill semantics (KillMode=control-group): every TheOzolith process on the node is a live descendant of the Node Daemon or does not exist — no zombie processes by construction. Bootstrap = install the daemon; everything else flows from config.
- Heartbeats (60s — node, stack, and labeled run-container status) flow to the Control Node; heartbeat responses carry infrastructure commands (drain, recycle, update, rebuild) that the Node Daemon reconciles.
- Ephemeral run containers: pipeline drivers create per-Run containers, labeled (`theozolith.run-id`, `theozolith.owner`) and deterministically named. The Node Daemon observes labeled ephemerals via docker, reports them in heartbeats, kills them on drain/recycle of the owning Stack, and reaps orphans (label present, owner gone) at startup; the pipeline's zombie-claim janitor escalates dead claims evidence-first (ADR-0016). Creation authority is pipeline-side; lifecycle authority is substrate-side (ADR-0013).
- Infrastructure commands are not coordination. The Control Node is authoritative for node and docker lifecycle; in the coding pipeline it is additionally the single writer of claim creation on GitHub (claim-write-through dispatch; ADR-0017, superseding ADR-0002 in part) and performs janitorial liveness corrections. GitHub remains the sole source of coordination truth: the Control Node reconciles to GitHub, never the reverse, and cannot approve, revise, or advance an issue.
### Deployment boundary

- Dependency rule: private depends on public, never the reverse (ADR-0004). The private config repo consumes TheOzolith releases; TheOzolith never references the private repo, specific hosts, or tailnet names.
- TheOzolith publishes versioned product images (GHCR); a deployment's entire private surface is one Config Repo (digest-pinned bases, private Stacks, overlays, secret names). Product changes release in TheOzolith, then a version bump in the Config Repo; hosting changes touch the Config Repo only. Two update paths share one machinery (pin bump committed to product.toml → update command fanned out over heartbeat responses → drain-aware node updates → the Control Node updates itself last): `theozolith update` (user path) resolves the latest published release — or an explicit --version — and pins it; `theozolith build` (developer path) builds the distribution from the local source checkout on the Control Node, pins the checkout's git SHA, and serves the built artifact for node pulls — build refuses a dirty tree, so every pin names a committed SHA (2026-07-22). The pin is desired state: the Node Daemon reconciles its running version against the pin on every heartbeat (startup is the first pass), so a failed update retries automatically. A recycle/update arriving mid-Run queues behind the current Run as drain→apply→undrain (job-dir presence is the in-flight signal; the heartbeat reports the deferral, bounded by the agent-timeout budget; `--force` keeps ADR-0013 kill-the-tree semantics). Dispatch eligibility follows the heartbeat-reported running version — an off-pin node receives no new work grants, so an update pauses new dispatch fleet-wide until nodes converge; a node that stays off-pin gets a restart command, then an error event and human attention. When the Control Node is unreachable, node polling backs off exponentially (capped). Nodes never pull source and never build the product. Never deploy :latest — restated: never deploy an unrecorded version; a pinned committed git SHA is a legitimate pin.
- Testing signals: `theozolith test` runs the product test suite and is the local-development signal. Future (design recorded 2026-07-22, not yet scheduled): an **integration-test node** — deploy the candidate build to a dedicated test node whose Stack spawns a fresh, isolated copy of TheOzolith (its own Control Node, Node Daemon, and Stacks) and runs end-to-end tests against it — deployment-grade signals no unit suite provides.
- Substrate admission rule: a feature enters the product only if an external adopter of a coding-worker fleet would want it; operator-specific needs are implemented in the Config Repo against extension points (custom stacks, overlays, out-of-band scripts).
- Transport-agnostic protocol: nodes reach the Control Node via HTTPS with bearer-token auth at a configured URL — an IP-based URL persisted at provisioning; the hostname origin is browser-only, so nodes never depend on DNS (ADR-0023). Control Node IP stability (static IP or DHCP reservation) is a deployment prerequisite; an IP change is recovered with one join-string re-paste per node. TLS is mandatory since secrets transit the channel; a self-signed or install-provisioned CA is fine. Tailscale is a deployment detail: hosts join the tailnet via private-side setup; product images contain no tailscaled, auth keys, or MagicDNS assumptions. Per-container tailnet identity, if wanted, enters via the Stack's derived-image setup instructions in the Config Repo (grilling 2026-08-06; the earlier sidecar-overlay suggestion is retired for this use — a sidecar delivers a tailnet address, but its Tailscale SSH terminates in the sidecar's filesystem, not the workspace). The enrollment auth key is a named secret — reusable, tagged, ACL-bounded (settled in issue #24: one key enrolls every instance of the worker type and deliberately re-enrolls one after state-volume loss) — stored encrypted control-side and delivered only through the standard secret machinery: node-scoped TLS pull → host tmpfs → read-only /run/secrets mount wired as <ENV>_FILE. It is consumed only while the explicit enrollment completion marker is absent from the tailnet-state volume — an Ozolith-owned file (/var/lib/tailscale/.theozolith-enrolled-v1) that is the sole enrollment predicate, never tailscaled.state: the daemon writes its machine key there before auth-key registration completes, so a rejected enrollment leaves a non-empty state file that must still re-enroll. Marker absent ⇒ enrollment with the key, even over a non-empty tailscaled.state; marker present ⇒ keyless identity reuse; the marker is promoted atomically (temp file + same-volume rename) only after a successful tailscale up; state-volume loss removes state and marker together, correctly returning the instance to deliberate enrollment (amended per issue #31). No durable plaintext copy exists anywhere: the only instances are the encrypted store and the host tmpfs, which evaporates with the daemon/reboot — there is no shred step because there is nothing to shred. Optional hardening (per instance, ADR-0047): unbind the key for an instance with `TS_AUTHKEY = ""` in its Stack's [secrets] once its completion marker is promoted, and remove the worker type's default binding after every instance has enrolled; re-enrollment after state-volume loss is explicit — restore the binding (if removed or unbound), recreate the volume, restart, and prune the stale tailnet machine by hand. tailscaled's runtime state volume is node-generated state like SSH host keys, out of scope for the secrets-never-on-node-disk doctrine.
- Network model: the substrate assumes flat IP reachability — every node can reach the Control Node's URL, and the Control Node can reach nodes for interactive access. A single LAN satisfies this; Tailscale's only role (private-side) is extending the flat network to devices off the LAN (laptop or phone away from home). TLS is mandatory even on a LAN because secrets transit the channel.
- Deletion test (restated 2026-07-27; ADR-0023): with the private config repo gone, TheOzolith must run anywhere with docker, the TheOzolith package, and `sudo theozolith init` output — all tunables at shipped defaults, environment variables as the expert override; `.env` is no longer a user-facing surface. Driver `--once` modes are the daemon-less dev path (ADR-0013).
- Single-node is a deployment shape, not a mode: `sudo theozolith init --with-local-node` runs standard init, installs the Node Daemon on the same box, and executes the unmodified join flow internally against loopback (covered by the server cert's IP SAN, so the local node is immune to LAN IP changes). It scaffolds a complete, commented worker Stack + worker-type definition at desired state stopped — first boot deploys nothing, so born-misconfigured infrastructure can never trip the quarantine gate. Nothing downstream knows the deployment is single-node.
### Extension points (all config, no code hooks)

- Custom worker types: the worker-type definition is the complete per-worker customization unit (grilling 2026-08-09) — base image + user setup instructions, optional Knowledge Source (`knowledge = "knowledge/<name>"` — a reference into the Config Repo's knowledge tree of skills, subagents, and workflows, content-hash-pinned per tree and compiled at ingest, baked in by the knowledge machinery at image build; ADR-0048), driver reference (`builtin:<name>` or `drivers/<name>`; ADR-0042), Agent adapter (which product adapter the harness invokes; the harness itself is immutable product plumbing, never a variable), model + reasoning effort (typed fields the compiler materializes into the tool's native config at derived-image build — never hand-written in setup instructions, never invocation-time selected; an adapter-unmappable value fails the build; grilling 2026-08-10), workspace (target repo), and secret names. Declared in the Config Repo and compiled at config-change time into a derived image tagged deterministically (base digest + instruction hash, the hash covering the materialized model/effort config and the referenced knowledge tree's pin — so editing one knowledge tree re-tags only the types referencing it); setup instructions never execute at container start. The worker Stack stays thin (worker type + placement + desired state, plus optional per-placement bindings: workspace and secret-slot rebindings, ADR-0047) — the Stack format never carries worker identity.
- Knowledge lifecycle (grilling 2026-08-08; delivery rewritten by ADR-0048): agent-home state (e.g. ~/.claude) splits by class. Runtime state — sessions, transcripts, resume history — persists on each Flight Deck's own state volume, never shared and never worker-visible. Knowledge — skills, subagents, workflows — lives in the Config Repo's `knowledge/` tree, compiles at ingest (the ADR-0009 compiler; compile errors surface at ingest, not at image build or container start), and delivers on the HITL/HOTL line. HOTL workers consume it baked into the derived image at build — the image stands alone, and live-mounting knowledge into worker images stays forbidden (it breaks pin reproducibility and opens a silent persistence channel into credential-free Runs). HITL Flight Decks read-only bind-mount the node's applied pinned knowledge tree; the applied tree swaps by atomic rename, so a running deck keeps its old inode until agent restart — restart = pick up new knowledge is the stated semantic. Authoring happens in the Config Repo; edits reach every deck on every node through the config distribution the substrate already runs (ADR-0043's shared writable clone, promote workflow, and knowledge volume are retired; its no-sync-daemon doctrine stands — git via config distribution is the only transport, cross-node live mounts rejected). Per-Stack knowledge is rejected: two Stacks needing different knowledge are two worker types, and worker types are cheap.
- Stacks: the Node Daemon has no hardcoded workload knowledge. Built-in (worker, reviewer) and user-defined (e.g. script runner) Stacks share one declarative format: name, workload, placement, desired state (worker-type Stacks may add per-placement bindings; ADR-0047). The Control Node process is never a Stack: it always runs as its own systemd unit on its host — the substrate never supervises its own control plane (2026-08-04; the built-in control Stack kind is deleted). Two workload kinds: container (image or compose plus overlays) and process (a native command from the product distribution or the deployment's hash-pinned config distribution (ADR-0042), supervised as a Node Daemon child inside its cgroup — how worker drivers deploy; ADR-0013).
- Compose overlays: topology changes (sidecars such as Tailscale, extra mounts, networks) layer onto product compose files.
- Typed event API: the run-event endpoint generalizes to namespaced event types; dashboards render known types richly and unknown types generically, so custom Stacks get first-class visibility without product changes. Drivers and the Node Daemon report their own faults as theozolith.error events (component, error class, message, size-capped context) — advisory diagnostics under the channel invariant, not log shipping; depth stays node-local (systemd journal) and in evidence bundles.
- Config Repo and pinned build (ADR-0006/0048): the human Config Repo lives wherever the operator likes (ingest accepts a local path or a git URL) and carries no computed pins. `theozolith config ingest` — the only write path, `control.toml` settings included — harvests the repo at its current commit, lints with exactly the fail-loud checks config load applies, resolves mechanical pins (per-tree knowledge content hashes; base tag→digest, via the managed `registry:<host>` credential for a private base, ADR-0049; the tailscale sha256 stays human-entered, never computed), compiles knowledge, and commits the pinned build at the control data dir's `configs/` stamped with the source commit SHA, then reloads in place. Rollback is `git revert` on the pinned build — re-ingesting an old source commit re-resolves pins and is not a rollback. Config load reads and config distribution serves only the pinned build; hand edits to it are refused. Desired state flows to Node Daemons over the command channel; nodes cache last-applied config for degraded mode.
- Image builds: each container-host builds derived images locally when instructed — base image pinned by digest plus setup instructions from the Config Repo. No registry or builder node for derived images; base and product images still come from GHCR. A private base is supported: its tag resolves to a digest at ingest and its `FROM …@sha256:…` pulls at build time using the managed `registry:<host>` credential, injected for that one build as a tmpfs `DOCKER_CONFIG` (ADR-0049). Containers exist for containment, not byte-identical reproducibility: build skew is surfaced, not prevented — build metadata (base digest, instruction hash, build timestamp) is stamped as image labels and reported in heartbeats, and rebuild is a standard command.
- Secrets: configs carry secret names — the worker type declares the slots with optional default names (an empty name = a required slot every instantiating Stack must bind), a Stack rebinds per placement (ADR-0047); values are entered once via the web UI or the Control Node CLI (both write through the same API to the same encrypted store), stored encrypted at rest on the Control Node, and pulled by container-hosts at deploy time — pull-only, node-scoped (only secrets referenced by Stacks placed on that node), TLS mandatory, materialized to /run/secrets (tmpfs), never written to node disk. The provider interface stays pluggable (Control Node default; systemd-creds/SOPS for air-gapped deployments). All TheOzolith services accept the VAR_FILE convention. One reserved-name class extends the store without a new surface (ADR-0049): a secret named `registry:<host>` (value `<user>:<token>`, e.g. a GHCR PAT with read:packages) is a managed registry pull credential — ingest resolves private base digests with it, and container-hosts pull private bases with it at build time. It is infrastructure, never workload config: the write surface shape-checks it, a `registry:`-prefixed name is rejected as a Stack/worker-type `[secrets]` binding value, node scoping unions in `registry:<host>` for every worker type behind a running worker-type Stack on the node, and the heartbeat carries `registry_secrets` names-only (the value rides the node-scoped secrets pull, preserving the channel invariant).
- Channel invariant (restated by ADR-0016): the heartbeat/command channel carries desired state, references, and advisory telemetry — typed run-progress events with size-capped payloads enforced at ingestion, never coordination authority; the only secret payload it ever carries is node-scoped secret values over TLS.
- Custom drivers (ADR-0042): the single enumerated code-level exception to "all config, no code hooks." Driver code lives in the Config Repo's `drivers/` — the ADR-0004 privacy boundary outranks the pure-data charter, since custom worker definitions are operator content that must not be published in a public checkout. On config change the Control Node packages `drivers/` into a hash-pinned config distribution served over the artifact-pull path; the channel carries only the drivers-hash, which the Node Daemon reconciles like the product pin — off-hash nodes are dispatch-ineligible. Worker-type definitions reference `driver = builtin:<name>` (product) or `drivers/<name>` (config distribution); defaults are referenced, never copied — a fork is a deliberate copy from the product checkout stamped with its ancestor product version. The stable extension API is the designated `theozolith.worker.api` module (base Worker, built-in type classes, job-directory/claim-protocol interfaces); version skew is advisory (stale stamp visible in status/flags), and real breakage crashes at driver start into existing supervision, theozolith.error events, and quarantine. Applied-tree verification is fail-closed and continuous: the node recomputes the canonical manifest over the applied tree after extraction and again on every pass, and a symlink, an irregular entry (FIFO/socket/device), an unenumerable subtree, or a rogue entry in the applied root reads as non-converged and triggers repair — an entry either participates in the verified hash or fails verification, and a pointer or directory name is never integrity evidence by itself. Repair is staged and atomic: the replacement fully verifies in a staging directory while the old tree stays intact and usable, affected custom-driver Stacks stop only after verification and before the active path is exchanged (never removed beneath a running process), convergence queues behind active Runs, and the `current` pointer publishes only after the complete transition — a crash at any step leaves an honest, retryable state.
- Anything these mechanisms cannot express is a product feature request subject to the admission rule — never a new hook (custom drivers above are the enumerated code exception; ADR-0042).
### Dashboard and operator access

- Operator TUI (2026-08-04): the primary routine-operations surface is terminal-based — `theozolith top` (in the operator CLI; Textual joins control/'s enumerated dependency exception) plus the stdlib-only `theozolith status` one-shot, run on the Control Node over SSH. It is a pure API consumer over loopback with the admin bearer token (origin-exempt per ADR-0022); it never reads cache.db or the secret store directly. TUI v1 writes are exactly three — infrastructure commands (typed confirmation on destructive verbs), quarantine release, and secret entry; `control.toml` stays git-native ($EDITOR + commit in the Config Repo, then `config ingest`; ADR-0048), rendered read-only. `theozolith status` prints a human table on stdout with `--json` as the only parsing contract; exit codes 0 healthy / 1 degraded / 2 Control Node unreachable (then still a pure API consumer — no local systemd/docker probing). Live log streaming, tail-size bumps, and direct node polling are recorded non-goals (channel invariant; cache-not-archive). No embedded terminal: the attach action prints a pastable command with `{host}`/`{container}` resolved from the latest heartbeat's live-container record, refusing when heartbeat evidence is stale. Pasted SSH commands bypass terminal-audit.log by accepted design — the audit contract covers the PTY bridge only, and SSH access to the Control Node already equals cluster access. Reads ride `GET /api/v1/state` (which carries `now`, `product_pin`, and `desired_stacks`) and `GET /api/v1/events` (bearer, JSON, node/component/type filters, newest-first, `since` + opaque id cursor; serves whatever survives the cache-not-archive eviction budget and reports evicted history honestly — the `evicted` indicator is query-relative to the call's own filter conjunction, `any_evicted` is the global fact; ADR-0038). `GET /api/v1/audits` never shipped — the auditor died with ADR-0016/0018; `/api/v1/flags` is the de-facto replacement. The web UI (dashboard, secret form, settings form, web terminal) is frozen at its shipped M4/M5 scope until multi-node and per-deployment DNS reinvestment.
- Web terminal: the dashboard embeds a terminal; a Control Node PTY bridge runs a config-supplied **argv array** per Stack, for example `["ssh", "{host}", "-t", "docker", "exec", "-it", "{container}", "tmux", "attach"]`. Free-form command strings are rejected; `{host}` and `{container}` may appear only as complete arguments and are validated before launch. The server resolves the target from a fresh live-container heartbeat and derives the owning Stack from the container record—caller-supplied Stack identity is never authority (ADR-0022). Run containers execute headless and are never attach targets (ADR-0019; see [AGENTIC-CODING-PIPELINE.md](AGENTIC-CODING-PIPELINE.md), Agent session contract). The terminal's primary target is the Flight Deck—the interactive, human-driven agent container Stack—plus any other Stack with configured attach argv. Input typed into an attached Flight Deck session is audited via the session transcript. No attach configuration means no terminal exposure. All terminal sessions are audit-logged (who attached, when, target, command, and detach reason).
- Control web origin and TLS (rewritten 2026-08-04 per ADR-0034/0036 as landed): browsers dial the same persisted control IP nodes dial — the browser origin is `https://<control_ip>[:<control_port>]`, with `control_port` a read-only `[control]` field (absent = 443; present-but-malformed fails closed at load, serve, and recover). The slug origin, `--base-domain`, `THEOZOLITH_PUBLIC_ORIGIN`, and the per-device DNS step are retired. Browser enablement is lazy: `init` mints the CA and a server cert with IP SANs only (the box's IP + loopback), and `init --host` / `tls-init --host` accept validated IP literals only. The opt-in `sudo theozolith origin-init` prompts for the browser origin (IP by default; a hostname here is the one hostname entry point into the certificate) and the admin password together, re-mints the server cert from the same CA (no node touched), and persists `browser_origin` as the enablement bit; until then the whole web mount answers 503 with a pointer at `origin-init` (websockets close 4403) while the bearer `/api/v1` surface is untouched. TLS trust follows the TrueNAS model: first visit clicks through the interstitial; trusting the per-deployment CA is an optional green-lock upgrade; "no HSTS" is an invariant. Cookie-authenticated writes and websockets require the exact Host and Origin derived from the address, armed only over TLS; bearer clients remain exempt (ADR-0022).
- Trust model: dashboard access = cluster access. Secret entry and the terminal sit behind the same single admin credential — acceptable for a single-operator deployment where the dashboard is reachable only from the trusted network. Finer-grained roles are post-V1.
- V1 web UI scope: read-only fleet dashboard, secret entry (web UI or CLI), and the settings view for `control.toml` — display-only since ADR-0048: the form refuses writes with a pointer at ingest, because the pinned build has no second writer; a settings edit is a Config Repo commit plus a `config ingest`. Topology editing (`stacks/`, `worker-types/`) stays git-native in V1 — the operator edits the Config Repo directly; the free-form web config editor is post-V1. The terminal is a small addition (PTY bridge plus frontend) and may ship in V1 or immediately after.
