# Node Substrate

Cluster-management layer of TheOzolith: Control Node, Node Daemon, Config Repo, Stacks, secrets, and extension points. The coding pipeline ([AGENTIC-CODING-PIPELINE.md](http://agentic-coding-pipeline.md/)) is one consumer of this substrate.

## Context

TheOzolith is cluster management, not container management: it manages physical nodes that run declarative workloads. The substrate serves any adopter of a coding-worker fleet; operator-specific needs are expressed as configuration in a private Config Repo, never as product code.

## Design

### Node model

- The Node Daemon (renamed from "Node Agent" — Agent is reserved for LLM tool configs; ADR-0013) is the uncontainerized TheOzolith daemon installed on every physical node, registering it as a Container-Host. It runs as a systemd unit with cgroup kill semantics (KillMode=control-group): every TheOzolith process on the node is a live descendant of the Node Daemon or does not exist — no zombie processes by construction. Bootstrap = install the daemon; everything else flows from config.
- Heartbeats (60s — node, stack, and labeled run-container status) flow to the Control Node; heartbeat responses carry infrastructure commands (drain, recycle, update, rebuild) that the Node Daemon reconciles.
- Ephemeral run containers: pipeline drivers create per-Run containers, labeled (`theozolith.run-id`, `theozolith.owner`) and deterministically named. The Node Daemon observes labeled ephemerals via docker, reports them in heartbeats, kills them on drain/recycle of the owning Stack, and reaps orphans (label present, owner gone) at startup; the pipeline's zombie-claim janitor escalates dead claims evidence-first (ADR-0016). Creation authority is pipeline-side; lifecycle authority is substrate-side (ADR-0013).
- Infrastructure commands are not coordination. The Control Node is authoritative for node and docker lifecycle; in the coding pipeline it is additionally the single writer of claim creation on GitHub (claim-write-through dispatch; ADR-0017, superseding ADR-0002 in part) and performs janitorial liveness corrections. GitHub remains the sole source of coordination truth: the Control Node reconciles to GitHub, never the reverse, and cannot approve, revise, or advance an issue.
### Deployment boundary

- Dependency rule: private depends on public, never the reverse (ADR-0004). The private config repo consumes TheOzolith releases; TheOzolith never references the private repo, specific hosts, or tailnet names.
- TheOzolith publishes versioned product images (GHCR); a deployment's entire private surface is one Config Repo (digest-pinned bases, private Stacks, overlays, secret names). Product changes release in TheOzolith, then a version bump in the Config Repo; hosting changes touch the Config Repo only. Two update paths share one machinery (pin bump committed to product.toml → update command fanned out over heartbeat responses → drain-aware node updates → the Control Node updates itself last): `theozolith update` (user path) resolves the latest published release — or an explicit --version — and pins it; `theozolith build` (developer path) builds the distribution from the local source checkout on the Control Node, pins the checkout's git SHA (marked -dirty when uncommitted changes exist), and serves the built artifact for node pulls. Nodes never pull source and never build the product. Never deploy :latest — restated: never deploy an unrecorded version; a pinned git SHA is a legitimate pin.
- Substrate admission rule: a feature enters the product only if an external adopter of a coding-worker fleet would want it; operator-specific needs are implemented in the Config Repo against extension points (custom stacks, overlays, out-of-band scripts).
- Transport-agnostic protocol: nodes reach the Control Node via HTTPS with bearer-token auth at a configured URL. TLS is mandatory since secrets transit the channel; a self-signed or install-provisioned CA is fine. Tailscale is a deployment detail: hosts join the tailnet via private-side setup; product images contain no tailscaled, auth keys, or MagicDNS assumptions. Per-container tailnet identity, if wanted, is a compose overlay (tailscale sidecar) layered onto the product compose.
- Network model: the substrate assumes flat IP reachability — every node can reach the Control Node's URL, and the Control Node can reach nodes for interactive access. A single LAN satisfies this; Tailscale's only role (private-side) is extending the flat network to devices off the LAN (laptop or phone away from home). TLS is mandatory even on a LAN because secrets transit the channel.
- Deletion test: with the private config repo gone, TheOzolith must run anywhere with docker, the TheOzolith package, and a .env; driver `--once` modes are the daemon-less dev path (ADR-0013).
### Extension points (all config, no code hooks)

- Custom worker types: base image + user setup instructions + optional Knowledge Source (git URL + pin to a repo of skills, subagents, and workflows, baked in by the knowledge machinery at image build), declared in the Config Repo and compiled at config-change time into a derived image tagged deterministically (base tag + instruction hash). Setup instructions never execute at container start.
- Stacks: the Node Daemon has no hardcoded workload knowledge. Built-in (worker, reviewer, control) and user-defined (e.g. script runner) Stacks share one declarative format: name, workload, placement, desired state. Two workload kinds: container (image or compose plus overlays) and process (a native command from the product distribution, supervised as a Node Daemon child inside its cgroup — how worker drivers deploy; ADR-0013).
- Compose overlays: topology changes (sidecars such as Tailscale, extra mounts, networks) layer onto product compose files.
- Typed event API: the run-event endpoint generalizes to namespaced event types; dashboards render known types richly and unknown types generically, so custom Stacks get first-class visibility without product changes. Drivers and the Node Daemon report their own faults as theozolith.error events (component, error class, message, size-capped context) — advisory diagnostics under the channel invariant, not log shipping; depth stays node-local (systemd journal) and in evidence bundles.
- Config Repo: git-backed folder (default ~/.theozolith/configs) with its working home on the Control Node; the web UI edits by committing. Desired state flows to Node Daemons over the command channel; nodes cache last-applied config for degraded mode. See ADR-0006.
- Image builds: each container-host builds derived images locally when instructed — base image pinned by digest plus setup instructions from the Config Repo. No registry or builder node for derived images; base and product images still come from GHCR. Containers exist for containment, not byte-identical reproducibility: build skew is surfaced, not prevented — build metadata (base digest, instruction hash, build timestamp) is stamped as image labels and reported in heartbeats, and rebuild is a standard command.
- Secrets: configs carry secret names; values are entered once via the web UI or the Control Node CLI (both write through the same API to the same encrypted store), stored encrypted at rest on the Control Node, and pulled by container-hosts at deploy time — pull-only, node-scoped (only secrets referenced by Stacks placed on that node), TLS mandatory, materialized to /run/secrets (tmpfs), never written to node disk. The provider interface stays pluggable (Control Node default; systemd-creds/SOPS for air-gapped deployments). All TheOzolith services accept the VAR_FILE convention.
- Channel invariant (restated by ADR-0016): the heartbeat/command channel carries desired state, references, and advisory telemetry — typed run-progress events with size-capped payloads enforced at ingestion, never coordination authority; the only secret payload it ever carries is node-scoped secret values over TLS.
- Anything these mechanisms cannot express is a product feature request subject to the admission rule — never a new hook.
### Dashboard and operator access

- Web terminal: the dashboard embeds a terminal; a Control Node PTY bridge runs a config-supplied **argv array** per Stack, for example `["ssh", "{host}", "-t", "docker", "exec", "-it", "{container}", "tmux", "attach"]`. Free-form command strings are rejected; `{host}` and `{container}` may appear only as complete arguments and are validated before launch. The server resolves the target from a fresh live-container heartbeat and derives the owning Stack from the container record—caller-supplied Stack identity is never authority (ADR-0022). Run containers execute headless and are never attach targets (ADR-0019; see [AGENTIC-CODING-PIPELINE.md](http://agentic-coding-pipeline.md/), Agent session contract). The terminal's primary target is the Flight Deck—the interactive, human-driven agent container Stack—plus any other Stack with configured attach argv. Input typed into an attached Flight Deck session is audited via the session transcript. No attach configuration means no terminal exposure. All terminal sessions are audit-logged (who attached, when, target, command, and detach reason).
- Control web origin and TLS: run `theozolith-control origin-init` to persist one explicit public origin, normally `https://<128-bit-random-slug>.<base-domain>` with no port for default HTTPS. The public origin is independent of the Uvicorn bind host and port; `THEOZOLITH_PUBLIC_ORIGIN` is the validated expert override. Resolve its hostname only through trusted-network DNS or hosts entries and keep the Control Node without public ingress. Then run `theozolith-control tls-init`: the certificate SAN includes the public origin's hostname only, never its port, and wildcard hosts are refused so each deployment retains its own TLS identity. Cookie-authenticated writes and websockets require the exact Host and Origin; bearer clients remain exempt (ADR-0022).
- Trust model: dashboard access = cluster access. Secret entry and the terminal sit behind the same single admin credential — acceptable for a single-operator deployment where the dashboard is reachable only from the trusted network. Finer-grained roles are post-V1.
- V1 web UI scope: read-only fleet dashboard plus secret entry (web UI or CLI). Config editing stays git-native in V1 — the operator edits the Config Repo directly; the web config editor is post-V1. The terminal is a small addition (PTY bridge plus frontend) and may ship in V1 or immediately after.
## Decisions

- **Private-to-public dependency rule**: the product is self-contained; the private config repo hosts pinned releases. See ADR-0004. [SETTLED]
- **Transport-agnostic HTTP + token protocol**; Tailscale demoted to a deployment overlay. [SETTLED]
- **The product owns the node substrate** (dashboard/monitoring, heartbeat/command, docker lifecycle); private deployments extend it with stacks and overlays. See ADR-0005. [SETTLED]
- **Extension surface** = derived images compiled at config change, declarative Stacks, compose overlays, typed event API — all config, no code hooks. [SETTLED]
- **Git-backed Config Repo is the single source of truth**; the web UI commits to it; authority lives at the Control Node. See ADR-0006. [SETTLED]
- **Secrets are named references with _FILE delivery via pluggable providers**; the default provider distributes values through the Control Node — encrypted at rest, pull-only, node-scoped, TLS mandatory. Container-hosts build derived images locally; no registry for derived images. See ADR-0006 (amended). [SETTLED]
- **Cluster management, not container management**: the Node Daemon is an uncontainerized daemon on every physical node (container-host); bootstrap = install the daemon. [SETTLED]
- **Grilling 2026-07-14**: worker types may declare a Knowledge Source baked in at image build by the knowledge machinery; the same private repo syncs to laptop tool dirs. See ADR-0007. [SETTLED]
- **Grilling 2026-07-14**: network model — flat IP reachability (typically one LAN); Tailscale is a private-side bridge for off-LAN devices, never a product dependency. [SETTLED]
- **Grilling 2026-07-14**: dashboard trust model — dashboard access = cluster access (secrets and terminal behind one admin credential) for single-operator V1; terminal sessions audit-logged. Web terminal = Control Node PTY bridge running a config-supplied attach command; tmux-in-container is the worker-image convention. [SETTLED, amended 2026-07-21: run containers are headless — tmux-in-container survives only in the Flight Deck and other attachable Stacks. See ADR-0019.]
- **Grilling 2026-07-14**: V1 web UI = read-only dashboard + secret entry (web or CLI); config editing stays git-native. [SETTLED]
- **Grilling 2026-07-15**: always-interactive contract — agent processes run interactively in dedicated per-session tmux (never headless); drivers inject prompts, detect completion via per-adapter hooks with a timeout backstop, and read file outputs; agents hold no GitHub credentials (drivers own all GitHub I/O); attached-terminal input is permitted and audited via the session transcript in the evidence bundle. See [AGENTIC-CODING-PIPELINE.md](http://agentic-coding-pipeline.md/), Agent session contract. [SUPERSEDED 2026-07-21: Runs are headless; the Flight Deck owns interactivity. See ADR-0019; archived in Historical Context / Agent Session Contract — Always-Interactive (pre-2026-07-21).]
- **Grilling 2026-07-15 (late)**: node-resident drivers — Stacks gain a process workload kind; Worker/Reviewer drivers run as supervised Node Daemon children (systemd cgroup kill-tree: drivers die with the daemon, no zombies); Runs execute as labeled ephemeral containers, observed via docker and reaped by label when orphaned; daemon + drivers ship in one versioned distribution updated via the update command; deletion test restated (docker + package + .env); Node Agent renamed Node Daemon. See ADR-0013. [SETTLED]
- **Grilling 2026-07-17**: the Control Node is load-bearing for claim dispatch — claim-write-through (the Control Node writes the GitHub claim before handing the issue to the driver; single serialized claim-writer; assign-and-verify deleted). Control Node down: in-flight Runs finish and publish; new claims and review rounds pause; fallback is backlog. See ADR-0017. [SETTLED]
- **Grilling 2026-07-17**: ADR-0002 residual invariant — GitHub remains the sole source of coordination truth; the Control Node never originates coordination beyond claim creation; janitorial liveness corrections are the enumerated exception. See ADR-0017. [SETTLED]
- **Grilling 2026-07-17 (late)**: failure handling — the control database is a cache, never the archive (evidence bundles are the sole durable audit; ~10GB transcript-tail budget, oldest-first eviction; terminal events kept); telemetry rides the channel under the restated invariant (advisory, size-capped at ingestion, never secrets or coordination authority); node quarantine at the dispatch gate after 2 consecutive failed Runs, human-released; boot-time evidence sweep by the driver (delete only after confirmed push; bundles marked swept); zombie escalation waits for swept evidence — stability and token efficiency over uptime. See ADR-0016. [SETTLED]
- **Grilling 2026-07-17**: recycle/update received mid-Run queue behind the current Run as a drain→apply→undrain composition; job-dir presence is the in-flight signal; a dead driver child proceeds immediately (orphaned dirs never block); the heartbeat reports the deferral ("command deferred behind run X"); --force keeps ADR-0013 kill-the-tree semantics; the deferral is bounded by the agent-timeout budget. Implementation notes land with the ADR-0015 amendments at its post-merge Notion uplift. [SETTLED]
- **Grilling 2026-07-17**: shared node token is an accepted risk — all nodes present one bearer token, so a compromised node can impersonate any node; secrets remain node-scoped only by the Control Node's pull filter (self-declared scoping is the seam). Per-node tokens are post-V1. [SETTLED]
- **Grilling 2026-07-21**: headless Runs + the Flight Deck — run containers are headless and never attach targets; the web terminal targets the Flight Deck (human-driven, credentialed, interactive agent container Stack) and other Stacks with configured attach commands. See ADR-0019. [SETTLED]
- **Grilling 2026-07-21 (late)**: worker taxonomy — Worker is the base abstraction (node-resident driver + ephemeral headless Runs + shared heartbeat/container/fetch-execute infrastructure); Implementer, Reviewer, and Initializer are the built-in worker types; the code uses inheritance so custom worker types extend the base type or a built-in one — the long-term code-level extension surface alongside Config-Repo worker-type image definitions. The interactive container is named Flight Deck. See ADR-0020. [SETTLED]
- **Grilling 2026-07-21 (evening)**: error visibility — drivers and the Node Daemon emit theozolith.error typed events (component, error class, message, size-capped context) through the existing typed event API; the dashboard renders an errors panel with node/component filters. Full log shipping rejected: a new subsystem that turns the control database into a log archive, violating cache-not-archive. Error events are summaries pointing at the failing node and component; diagnostic depth stays in the node-local journal and evidence bundles. [SETTLED]
- **Grilling 2026-07-22**: two update paths — `theozolith update` (user path: resolve the latest published release, or an explicit --version, and pin it) and `theozolith build` (developer path: git pull + build from the source checkout on the Control Node; the pin is the checkout's git SHA, -dirty marked when the tree has uncommitted changes; the Control Node serves the built artifact for node pulls). Both converge on the same machinery: pin bump committed to product.toml, fan-out over heartbeat responses (drain-aware queue-behind semantics per 2026-07-17), Control Node self-update last via os.execv. Nodes never pull source and never build the product; "never deploy :latest" is restated as "never deploy an unrecorded version"; rollback = re-pin the previous version and run the same command. Amends ADR-0015 (product.toml's "absent = latest" softens to: absent means the installer resolves the latest release and writes the pin). [SETTLED]
