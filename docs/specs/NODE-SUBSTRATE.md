# Node Substrate

Cluster-management layer of TheOzolith: Control Node, Node Daemon, Config Repo, Stacks, secrets, and extension points. The coding pipeline ([AGENTIC-CODING-PIPELINE.md](http://agentic-coding-pipeline.md/)) is one consumer of this substrate.

## Context

TheOzolith is cluster management, not container management: it manages physical nodes that run declarative workloads. The substrate serves any adopter of a coding-worker fleet; operator-specific needs are expressed as configuration in a private Config Repo, never as product code.

## Design

### Node model

- The Node Daemon (renamed from "Node Agent" — Agent is reserved for LLM tool configs; ADR-0013) is the uncontainerized TheOzolith daemon installed on every physical node, registering it as a Container-Host. It runs as a systemd unit with cgroup kill semantics (KillMode=control-group): every TheOzolith process on the node is a live descendant of the Node Daemon or does not exist — no zombie processes by construction. Bootstrap = install the daemon; everything else flows from config.
- Heartbeats (60s — node, stack, and labeled run-container status) flow to the Control Node; heartbeat responses carry infrastructure commands (drain, recycle, update, rebuild) that the Node Daemon reconciles.
- Ephemeral run containers: pipeline drivers create per-Run containers, labeled (`theozolith.run-id`, `theozolith.owner`) and deterministically named. The Node Daemon observes labeled ephemerals via docker, reports them in heartbeats, kills them on drain/recycle of the owning Stack, and reaps orphans (label present, owner gone) at startup; the pipeline's zombie-claim janitor escalates dead claims evidence-first (ADR-0016). Creation authority is pipeline-side; lifecycle authority is substrate-side (ADR-0013).
- Infrastructure commands are not coordination. The Control Node is authoritative for node and docker lifecycle; in the coding pipeline it is additionally the single writer of claim creation on GitHub (claim-write-through dispatch; ADR-0017, superseding ADR-0002 in part) and performs janitorial liveness corrections. GitHub remains the sole source of coordination truth: the Control Node reconciles to GitHub, never the reverse, and cannot approve, revise, or advance an issue.
### Deployment boundary

- Dependency rule: private depends on public, never the reverse (ADR-0004). The private config repo consumes TheOzolith releases; TheOzolith never references the private repo, specific hosts, or tailnet names.
- TheOzolith publishes versioned product images (GHCR); a deployment's entire private surface is one Config Repo (digest-pinned bases, private Stacks, overlays, secret names). Product changes release in TheOzolith, then a version bump in the Config Repo; hosting changes touch the Config Repo only. Two update paths share one machinery (pin bump committed to product.toml → update command fanned out over heartbeat responses → drain-aware node updates → the Control Node updates itself last): `theozolith update` (user path) resolves the latest published release — or an explicit --version — and pins it; `theozolith build` (developer path) builds the distribution from the local source checkout on the Control Node, pins the checkout's git SHA, and serves the built artifact for node pulls — build refuses a dirty tree, so every pin names a committed SHA (2026-07-22). The pin is desired state: the Node Daemon reconciles its running version against the pin on every heartbeat (startup is the first pass), so a failed update retries automatically. Dispatch eligibility follows the heartbeat-reported running version — an off-pin node receives no new work grants, so an update pauses new dispatch fleet-wide until nodes converge; a node that stays off-pin gets a restart command, then an error event and human attention. When the Control Node is unreachable, node polling backs off exponentially (capped). Nodes never pull source and never build the product. Never deploy :latest — restated: never deploy an unrecorded version; a pinned committed git SHA is a legitimate pin.
- Testing signals: `theozolith test` runs the product test suite and is the local-development signal. Future (design recorded 2026-07-22, not yet scheduled): an **integration-test node** — deploy the candidate build to a dedicated test node whose Stack spawns a fresh, isolated copy of TheOzolith (its own Control Node, Node Daemon, and Stacks) and runs end-to-end tests against it — deployment-grade signals no unit suite provides.
- Substrate admission rule: a feature enters the product only if an external adopter of a coding-worker fleet would want it; operator-specific needs are implemented in the Config Repo against extension points (custom stacks, overlays, out-of-band scripts).
- Transport-agnostic protocol: nodes reach the Control Node via HTTPS with bearer-token auth at a configured URL — an IP-based URL persisted at provisioning; the hostname origin is browser-only, so nodes never depend on DNS (ADR-0023). Control Node IP stability (static IP or DHCP reservation) is a deployment prerequisite; an IP change is recovered with one join-string re-paste per node. TLS is mandatory since secrets transit the channel; a self-signed or install-provisioned CA is fine. Tailscale is a deployment detail: hosts join the tailnet via private-side setup; product images contain no tailscaled, auth keys, or MagicDNS assumptions. Per-container tailnet identity, if wanted, is a compose overlay (tailscale sidecar) layered onto the product compose.
- Network model: the substrate assumes flat IP reachability — every node can reach the Control Node's URL, and the Control Node can reach nodes for interactive access. A single LAN satisfies this; Tailscale's only role (private-side) is extending the flat network to devices off the LAN (laptop or phone away from home). TLS is mandatory even on a LAN because secrets transit the channel.
- Deletion test (restated 2026-07-27; ADR-0023): with the private config repo gone, TheOzolith must run anywhere with docker, the TheOzolith package, and `sudo theozolith init` output — all tunables at shipped defaults, environment variables as the expert override; `.env` is no longer a user-facing surface. Driver `--once` modes are the daemon-less dev path (ADR-0013).
### Extension points (all config, no code hooks)

- Custom worker types: base image + user setup instructions + optional Knowledge Source (git URL + pin to a repo of skills, subagents, and workflows, baked in by the knowledge machinery at image build), declared in the Config Repo and compiled at config-change time into a derived image tagged deterministically (base tag + instruction hash). Setup instructions never execute at container start.
- Stacks: the Node Daemon has no hardcoded workload knowledge. Built-in (worker, reviewer) and user-defined (e.g. script runner) Stacks share one declarative format: name, workload, placement, desired state. The Control Node process is never a Stack: it always runs as its own systemd unit on its host — the substrate never supervises its own control plane (2026-08-04; the built-in control Stack kind is deleted). Two workload kinds: container (image or compose plus overlays) and process (a native command from the product distribution, supervised as a Node Daemon child inside its cgroup — how worker drivers deploy; ADR-0013).
- Compose overlays: topology changes (sidecars such as Tailscale, extra mounts, networks) layer onto product compose files.
- Typed event API: the run-event endpoint generalizes to namespaced event types; dashboards render known types richly and unknown types generically, so custom Stacks get first-class visibility without product changes. Drivers and the Node Daemon report their own faults as theozolith.error events (component, error class, message, size-capped context) — advisory diagnostics under the channel invariant, not log shipping; depth stays node-local (systemd journal) and in evidence bundles.
- Config Repo: git-backed folder (default ~/.theozolith/configs) with its working home on the Control Node; the web UI edits by committing. Desired state flows to Node Daemons over the command channel; nodes cache last-applied config for degraded mode. See ADR-0006.
- Image builds: each container-host builds derived images locally when instructed — base image pinned by digest plus setup instructions from the Config Repo. No registry or builder node for derived images; base and product images still come from GHCR. Containers exist for containment, not byte-identical reproducibility: build skew is surfaced, not prevented — build metadata (base digest, instruction hash, build timestamp) is stamped as image labels and reported in heartbeats, and rebuild is a standard command.
- Secrets: configs carry secret names; values are entered once via the web UI or the Control Node CLI (both write through the same API to the same encrypted store), stored encrypted at rest on the Control Node, and pulled by container-hosts at deploy time — pull-only, node-scoped (only secrets referenced by Stacks placed on that node), TLS mandatory, materialized to /run/secrets (tmpfs), never written to node disk. The provider interface stays pluggable (Control Node default; systemd-creds/SOPS for air-gapped deployments). All TheOzolith services accept the VAR_FILE convention.
- Channel invariant (restated by ADR-0016): the heartbeat/command channel carries desired state, references, and advisory telemetry — typed run-progress events with size-capped payloads enforced at ingestion, never coordination authority; the only secret payload it ever carries is node-scoped secret values over TLS.
- Anything these mechanisms cannot express is a product feature request subject to the admission rule — never a new hook.
### Dashboard and operator access

- Operator TUI (2026-08-04): the primary routine-operations surface is terminal-based — `theozolith top` (in the operator CLI; Textual joins control/'s enumerated dependency exception) plus the stdlib-only `theozolith status` one-shot, run on the Control Node over SSH. It is a pure API consumer over loopback with the admin bearer token (origin-exempt per ADR-0022); it never reads cache.db or the secret store directly. No embedded terminal: the attach action prints a pastable command with `{host}`/`{container}` resolved from the latest heartbeat's live-container record, refusing when heartbeat evidence is stale. Pasted SSH commands bypass terminal-audit.log by accepted design — the audit contract covers the PTY bridge only, and SSH access to the Control Node already equals cluster access. Reads ride `GET /api/v1/state` (which carries `now`, `product_pin`, and `desired_stacks`) and `GET /api/v1/events` (bearer, JSON, node/component/type filters, newest-first, `since` + opaque id cursor; serves whatever survives the cache-not-archive eviction budget and reports evicted history honestly — the `evicted` indicator is query-relative to the call's own filter conjunction, `any_evicted` is the global fact; ADR-0038). `GET /api/v1/audits` never shipped — the auditor died with ADR-0016/0018; `/api/v1/flags` is the de-facto replacement. The web UI (dashboard, secret form, settings form, web terminal) is frozen at its shipped M4/M5 scope until multi-node and per-deployment DNS reinvestment.
- Web terminal: the dashboard embeds a terminal; a Control Node PTY bridge runs a config-supplied **argv array** per Stack, for example `["ssh", "{host}", "-t", "docker", "exec", "-it", "{container}", "tmux", "attach"]`. Free-form command strings are rejected; `{host}` and `{container}` may appear only as complete arguments and are validated before launch. The server resolves the target from a fresh live-container heartbeat and derives the owning Stack from the container record—caller-supplied Stack identity is never authority (ADR-0022). Run containers execute headless and are never attach targets (ADR-0019; see [AGENTIC-CODING-PIPELINE.md](http://agentic-coding-pipeline.md/), Agent session contract). The terminal's primary target is the Flight Deck—the interactive, human-driven agent container Stack—plus any other Stack with configured attach argv. Input typed into an attached Flight Deck session is audited via the session transcript. No attach configuration means no terminal exposure. All terminal sessions are audit-logged (who attached, when, target, command, and detach reason).
- Control web origin and TLS (rewritten 2026-08-04 per ADR-0034/0036 as landed): browsers dial the same persisted control IP nodes dial — the browser origin is `https://<control_ip>[:<control_port>]`, with `control_port` a read-only `[control]` field (absent = 443; present-but-malformed fails closed at load, serve, and recover). The slug origin, `--base-domain`, `THEOZOLITH_PUBLIC_ORIGIN`, and the per-device DNS step are retired. Browser enablement is lazy: `init` mints the CA and a server cert with IP SANs only (the box's IP + loopback), and `init --host` / `tls-init --host` accept validated IP literals only. The opt-in `sudo theozolith origin-init` prompts for the browser origin (IP by default; a hostname here is the one hostname entry point into the certificate) and the admin password together, re-mints the server cert from the same CA (no node touched), and persists `browser_origin` as the enablement bit; until then the whole web mount answers 503 with a pointer at `origin-init` (websockets close 4403) while the bearer `/api/v1` surface is untouched. TLS trust follows the TrueNAS model: first visit clicks through the interstitial; trusting the per-deployment CA is an optional green-lock upgrade; "no HSTS" is an invariant. Cookie-authenticated writes and websockets require the exact Host and Origin derived from the address, armed only over TLS; bearer clients remain exempt (ADR-0022).
- Trust model: dashboard access = cluster access. Secret entry and the terminal sit behind the same single admin credential — acceptable for a single-operator deployment where the dashboard is reachable only from the trusted network. Finer-grained roles are post-V1.
- V1 web UI scope: read-only fleet dashboard, secret entry (web UI or CLI), and the fixed-schema settings form for `control.toml` (ADR-0023 — edits by committing to the Config Repo, following the product.toml pin-bump precedent). Topology editing (`stacks/`, `images/`) stays git-native in V1 — the operator edits the Config Repo directly; the free-form web config editor is post-V1. The terminal is a small addition (PTY bridge plus frontend) and may ship in V1 or immediately after.
