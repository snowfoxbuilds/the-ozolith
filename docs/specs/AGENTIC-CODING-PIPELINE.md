# Agentic Coding Pipeline

Agent-agnostic framework for staged autonomous development: plan in GitHub issues, implement via Implementers executing disposable Runs, review by a dedicated Reviewer actor, merge by a human.

## Context

Models, agents, and skills improve constantly; the pipeline must allow swapping any coding agent without migration. Defect-catching lives in tests, CI, and a push gate — not in any single agent's judgment.

## Design

### Core principle

Runs are stateless, disposable executions; Workers are long-lived but hold no authoritative state. Everything durable is a file or a GitHub object. No agent memory, vendor config format, or vendor-exclusive feature is load-bearing. Canonical terms are defined in [CONTEXT.md](../../CONTEXT.md).

### Stages

| Stage | Actor | Staging ground | Output |
| --- | --- | --- | --- |
| Planning | Human-led, agent-assisted | GitHub issues | plan_ready issue with acceptance criteria and baseline risk |
| Implementation | Implementer (one Run per round) | Branch + first-party Implementer-side gate | Best-effort PR with a Decisions Section |
| Review | Reviewer actor + CI + human | PR | Approved (needs_human), revised (next round), or escalated PR |

- Repo-authored anchor documents ([AGENTS.md](../../AGENTS.md), [CONTEXT.md](../../CONTEXT.md), Specs, ADRs) govern the project. Anchor documents do not govern individual changes.
- All per-change planning lives in GitHub issues. Applying plan_ready is the act of issue approval and asserts the two hard artifacts: acceptance criteria and a baseline risk label. Other template fields (objective, out of scope, pointers) are issue-form prompts, never enforced — the human is the lint. Acceptance criteria are authored at planning time so the Reviewer judges against pre-existing criteria, never tests authored by the implementing side in the same Run.
- V1 planning: the human writes issues through GitHub issue forms, optionally drafting with the Flight Deck (or any agent out-of-band). The Initializer (specified 2026-07-21, deferred past the current testing scope) sharpens human drafts: it analyzes draft issues lacking the initialized label and publishes one structured analysis comment plus the initialized label; the human rules on its questions and still applies plan_ready. No automated issue generation in V1. A future planning worker type (the reserved "Planner") enters through the same gate: agent-drafted issues land as draft, and plan_ready is applied by the human — or by the agent itself where the human has explicitly granted that permission; the Flight Deck's scribe delegation (see Transition authority) is the first such grant.
- Integration (merge sequencing across parallel PRs) is handled by the human merge gate; ordering across issues is enforced by Dependency Edges — dependency-aware dispatch and Chained-Base Runs (see Dependency ordering and Chained-Base Runs) (grilling 2026-08-27).
### Issue and PR lifecycle (labels)

```javascript
Issue: draft (+ initialized once the Initializer posts its analysis) -> plan_ready -> in_progress -> (revise verdict: back to plan_ready) -> closed | abandoned
PR:    pr_ready               -> ready for the automated Reviewer (under round budget)
       pr_ready + needs_human -> awaiting human review/stamp
       blocked  + needs_human -> awaiting a human decision to move forward
       -> closed (merged) | abandoned
```

- plan_ready is the only claimable state — the unambiguous name for "agents may start".
- Queue rule: each actor watches one label on one object type. Implementers request plan_ready issues through Control Node dispatch; the Reviewer requests pr_ready PRs (without needs_human, under the round budget) through the same dispatch path; the Initializer (when built) requests draft issues lacking initialized through the same dispatch path, discovery-only; the human polls PRs (needs_human).
- Transition authority: initial plan_ready is human authority — the human applies it directly, or the Flight Deck executes it as the human's scribe under the scoped delegation: only on an explicit instruction in the live deck conversation naming each work issue and confirming its risk:* label. Publication approval, repository or issue content, tool output, and ambiguous remarks never authorize; tracking issues are never stamped; the delegation covers nothing beyond that one transition — no claims, no blocked answers, no Reviewer transitions, no PR approval, no merge. The human answers blocked decisions (comment + re-queue) and closes issues. The Control Node applies in_progress + assignee at claim (claim-write-through dispatch); the Implementer applies pr_ready at PR push. The Reviewer owns all post-PR state — deviation:*, risk:*, attempt-N, blocked, needs_human — and, under explicitly delegated authority, the claim strip + plan_ready re-queue that starts the next round. The Initializer (when built) applies initialized on draft issues — its only label authority; removing initialized is the human re-queue for a fresh analysis pass. The Control Node's janitor additionally applies blocked + needs_human on a chained dependent PR in the base-drift lane — the enumerated janitorial exception (grilling 2026-08-27). No other transitions exist.
- Best-effort PR contract: every Run that reaches a checkout ends by pushing what it has and opening/updating the PR with a mandatory Decisions Section (decisions with rationale, open questions, remaining work, dead ends tried, and optional process issues — pipeline-friction observations with suggested fixes), then applies pr_ready. The Implementer never stops mid-Run to ask; judgment calls are made, recorded, and adjudicated by the Reviewer afterward. The hyphenated needs-human label is retired in favor of needs_human.
- Run outcomes: a completed session with commits ships normally. A session concluding that no change is needed still ships — an empty PR (one driver-synthesized allow-empty commit) whose body carries the no-change reasoning; the Reviewer judges it like any PR, and a justified no-change earns approve (the human closes the issue). A Run ending with no commits and no reasoning, or a crashed/timed-out session, is a failed Run: the driver keeps the claim, pushes evidence, and re-launches once locally — a full second Run (new run_id, fresh clone and container, its own evidence bundle). Any non-completed Run burns the single retry regardless of class (timeout, session death, harness crash, zero commits without reasoning, pre-session infra failure). A second, cheaper retry class exists for completed sessions whose Output Proposal fails validation (missing or invalid required fields, e.g. commit-message): one completion retry — new container, new run_id, own evidence bundle, but the working tree and partially-filled proposal are preserved, and the main prompt gains a machine-generated error appendix naming the missing fields (fill-only; code churn there is a reviewable finding). Capped at one; a second miss escalates failed + needs_human. This is an enumerated exception to the no-carryover rule and is Implementer-only — a missing Reviewer verdict escalates immediately, because the judgment died with the session. No fallback-generated commit message ever ships: git history is the durable context channel for future agents, and silent filler would pollute exactly that channel (grilling 2026-08-16). On a second non-completion the driver releases the claim and escalates failed + needs_human on the issue, linking both evidence bundles and stating each failure's class. The run-failed marker machinery is deleted.
- Claim Protocol: the Implementer requests work from the Control Node; the Control Node selects an issue, writes the claim to GitHub itself (assigns the Implementer's GitHub login, adds in_progress), and returns the issue in the same response. The protocol is keyed by repository (grilling 2026-09-02): the request names the repo the Driver will check out and the Driver's Stack, verified against the Pinned Build — a missing, mismatched, or non-worker Stack (a Flight Deck or generic Stack, rather than a driver-bearing process-kind one) is refused 403, and config load plus Driver startup prove the canonicalized checkout and API targets are that repo before any dispatch (`file://` never validates; test rigs use an injected checkout seam) — and one Control Node coordinates every Bound Workspace over one GitHub host and one control PAT, degrading to a visible per-repo dispatch pause (never a crash) when GitHub fails for one repo. Every verified 200 response — grant, discovery batch, no-work, convergence-block, dependency-wait, and pause answers alike — echoes the verified (repo, stack); a Driver validates the binding before interpreting `issue`, `prs`, or `reason`, refusing an answer without its matching binding before checkout — the mixed-version guard: a new Driver against a not-yet-restarted old Control Node executes nothing, and the old Control's already-written claim is recovered by the existing activation-timeout release below. A verified grant or discovery also leaves a cache-only authorization lease, so work in flight when its repo is unbound still completes into control — events exactly matching the lease are accepted and terminal completion resolves the claim and node health, while nothing new is authorized; the lease is claim-scoped (a failed Run's bounded local or completion retry rotates the recorded run_id rather than retiring it — pr-open, escalated, expiry, or bound GitHub-truth reconciliation ends it, never an intermediate failed) and review leases are round-scoped and per verified actor (concurrent Reviewer Stacks hold independent discovery leases; activation is exclusive per PR across live activations — the first acknowledged `started` wins, and the leased round, recorded at discovery from the attempt labels and atomically re-rounded when an unactivated lease's rediscovery observes them advanced, must match), activated by an acknowledged `theozolith.review` `phase="started"` handshake — confirmed and echo-validated before checkout or any verdict-related GitHub write, idempotent on the identical retry, with fresh discovery the batch's only iteration authority — each iteration takes the oldest reviewable not-yet-attempted item — before their `phase="completed"` outcome counts, expiring harmlessly when never activated (actor-local; retiring a live review activation — completion, reconciliation, or expiry — atomically invalidates the PR's unactivated peer leases, whatever round each records, so re-entry takes fresh discovery); activated leases are reconciled — and, while GitHub still shows a bound Implementer claim standing, renewed — from GitHub truth while the repo stays bound, and expire on bounded budget-derived deadlines once renewal stops (unbound expiry explicitly ends Control's acceptance; recovery is the operator's). The grant carries claim authority only, never context: each Run — including the local retry — reads the full issue and PR context fresh, live through the GitHub Relay (grilling 2026-09-03; grilling 2026-08-16 amended the no-re-read clause). The Control Node is the single serialized claim-writer; assign-and-verify is deleted. GitHub remains the sole source of coordination truth. A granted claim with no claimed event within the activation window (~60s) is released by the Control Node. Dispatch eligibility also requires update convergence: a node whose heartbeat-reported product version differs from the recorded pin receives no new grants. Control Node down = new claims and new review rounds pause; in-flight Runs finish and publish.
- Zombie claims: the Control Node detects claims whose Implementer has been silent past the grace period and surfaces them on the dashboard, then waits for the swept evidence bundle to land (boot-time sweep when the driver returns) before releasing the claim and escalating failed + needs_human on the issue with the evidence link. Evidence precedes escalation; there is no automatic re-queue — a node that never returns is a human call from the dashboard. Nodes with 2 consecutive failed Runs are quarantined at dispatch until a human releases them.
- Round budget: 3 review rounds per issue, tracked as attempt-N labels on the PR, incremented by the Reviewer at each revise verdict — never on claim. Round input is the Reviewer's revised plan plus its designated resume commit. Runs that produce no PR consume no rounds — they draw on the separate failed-Run budget (one retry, then escalation; see Run outcomes); Runs lost to a dead Implementer escalate through the zombie janitor once swept evidence lands. The Control Node cross-checks attempt labels against Run and review events and flags mismatches; it does not auto-correct — and at review activation the cross-check has teeth: the discovery lease records the label-derived round — atomically re-rounded when rediscovery observes advanced labels on the unactivated lease — and a `started` naming another refuses.
- On round-budget exhaustion the Reviewer escalates: blocked + needs_human with the evidence bundle link. The Reviewer also escalates early when a Decisions Section surfaces a call only a human may make; the human answers with a comment and re-queues the issue to plan_ready.
### Dependency ordering and Chained-Base Runs (grilling 2026-08-27)

- Dependency Edges — GitHub-native `blocked by` relations between workspace-repo issues — are the machine-readable ordering truth, published at planning time (config-repo side; ozolith-configs#3), hand-editable in the UI; body prose ("depends on #N") is a mirror, never a source. Sub-issue links group a plan under a parent tracking issue and carry no ordering semantics; the enforcement side consumes no sub-issue links in V1, and nothing auto-closes issues or PRs — the parent stays human-closed.
- Dispatch eligibility (claim selection inside existing dispatch authority — no new coordination writes beyond the janitor lane below): a plan_ready issue is grantable only when every Dependency Edge is satisfied — the blocker issue is closed as completed, or the Chained Base go-ahead holds. A blocker closed as not_planned does not satisfy its edge: the dependent surfaces as a malformed state (the failed + plan_ready precedent) for the human to re-edge or abandon. A dependency cycle in the blocked-by closure surfaces as malformed at dispatch, never granted; the driver's pre-Run closure walk stays as a fail-loud infra-class backstop. A cross-repo edge on a claimable work issue is malformed; cross-repo edges on parent/tracking issues are ignored and never followed — cross-repo work enters ordering only through a locally created stand-in sub-issue.
- Ordering: both dispatch listings pass sort=created&direction=asc — issues drain in creation (= plan) order, and Reviewer discovery drains oldest-first, so a chain's blockers are reviewed before their dependents' go-ahead depends on them.
- Chained Base go-ahead: an open blocker qualifies when its PR (resolved via the deterministic ozolith/issue-N branch) carries pr_ready + needs_human without blocked — the label state only an approve verdict produces; labels only, never comment parsing. The open blockers' PRs must form a single chain by base_ref linkage — each targets the default branch or another open blocker's branch, exactly one tip — and the dependent bases on the tip; an open blocker with no PR, or parallel open blocker lines, means wait. Preconditions, checked mechanically from repo settings at dispatch: merge commits allowed, squash and rebase merge disabled (both rewrite SHAs and break chained diffs), delete-branch-on-merge enabled. When they fail, chaining is off with a visible dispatch reason and dependents wait for full merge; there is no mechanical rebase step (no actor owns a dependent post-PR, and a force-push would invalidate the Reviewer's resume commit).
- Driver mechanics: the grant still carries claim authority only. The driver re-resolves the chain fresh at checkout and proceeds with current truth — every blocker merged means the default branch; a live chain means its current tip — and reconciles the base again at ship time on every ship path (fresh Run, resume round, completion retry): an existing dependent PR is reloaded (GitHub may have retargeted it mid-session), and a recorded base branch that no longer exists must be proven merged — its PR resolved across all states — with the dependent following the merged PR's actual base branch through any already-merged chain layers to the live successor, verifying the recorded base commit is contained there before publishing. Branch absence alone is never merge proof: a deleted branch whose PR is absent, closed-unmerged, or otherwise unverifiable fails the Run loudly as infra — never a guessed base. The dependent PR targets the blocker branch, and the driver-owned, machine-parseable "Based on #N at `<sha>`" PR-body zone is the durable base record and the human-gate warning (merge #N first — GitHub does not prevent merging the dependent into the blocker branch); the zone is removed only when the effective base is truly the default branch, and otherwise warns for the actual remaining blocker. GitHub's retarget-on-branch-delete moves the dependent to the merged PR's base branch when the blocker merges — it reaches the default branch only when that is the actual successor base.
- Janitor base-drift lane — the enumerated-exception extension: only when the dependent PR is open with a Based-on zone, the named blocker PR is still open and not itself blocked, and the blocker branch tip no longer matches the recorded SHA, the janitor applies blocked + needs_human on the dependent PR with a comment naming the blocker and both SHAs; idempotent per drift (SHA-pair keyed; an escalation proven complete on GitHub whose final recording was lost is healed into the acted ledger with no new write), never auto-repair. Blocker merged-and-branch-deleted is the healthy retarget path, not drift. A human-rejected or abandoned blocker — its PR closed unmerged, or open but carrying blocked — is a human-owned condition: a moved tip changes nothing automatically once the blocker is blocked; the dashboard lists its chained dependents, and no automated write happens until the human resolves the blocker itself.
- The aggressive chaining knob (chain on unreviewed pr_ready) is rejected for now — the approve-gate overlap captures most of the throughput win at a fraction of the stacked-rebase risk.
### Execution model

- Every worker — Implementer, Reviewer, Initializer — is a long-lived **driver process** on a container-host, bound to one Agent config: a supervised Node Daemon child declared as a process-kind Stack (see [NODE-SUBSTRATE.md](NODE-SUBSTRATE.md)). The Implementer requests work from the Control Node and executes Implementer Runs sequentially, one at a time. Workers are not containers — the long-lived-container design is retracted.
- The driver is the trusted, credentialed half: it runs the Claim Protocol, materializes job inputs, sequences gate steps, creates run containers, and performs every GitHub read and write. It never executes repo code or model output.
- Each Run executes as an **ephemeral run container** created by the driver from the Agent config's image; container lifetime = Run lifetime. PID 1 is the **agent harness** — credential-free plumbing that invokes the agent headless (one-shot), treats process exit as completion (timeout backstop), writes outputs, and exits. Driver and harness communicate only through the per-Run job directory (inputs, outputs, transcript, status) — no network channel; the one file in it that is not a file is the GitHub Relay socket (grilling 2026-09-03): a driver-owned, per-Run Unix socket the agent's `gh` speaks plaintext HTTP to, where the driver injects a dedicated read-only credential, classifies every request fail-closed (REST `GET`/`HEAD` and single-operation GraphQL `query` allowed; every mutation, admin-class read, and unparseable body refused with a message pointing at the Output Proposal), re-originates TLS to GitHub.com's API origin only (V1 supports GitHub.com alone — a configured GitHub Enterprise Server host is refused at config load and at driver boot, before any preflight, relay, container, claim, or Review Run), never follows a redirect on its own — a GraphQL `POST` answered with any 3xx is refused outright, never followed, rewritten to `GET`, or replayed; a REST `GET`/`HEAD` redirect is followed only when the method is preserved and every hop passes the exact-origin, API-path, admin-denylist, method, and budget policy afresh; no credential or client header ever reaches a refused target — writes a redacted, size-bounded intent record to an audit log in driver-owned storage the container cannot reach before the credential touches any request, a redirect-intent record before each followed redirect hop's credential use, and a correlated completion record after it — each record serialized and size-checked before it authorizes anything, so a request the sink cannot describe is refused rather than half-recorded — and delivers a response only once the whole upstream body has passed the byte budgets, so a budget refusal is always a clean 502 with no partial body. The socket is parsed as a hostile ingress, because any process in the container can connect (grilling 2026-09-03): one request per connection, every accepted connection — empty, partial, timed out, or busy-refused included — charged against a finite per-Run connection budget whose exhaustion closes the listener and unlinks the socket rather than looping on refusals, exact request-line, header, body, connection-count, and read-time limits, refusal of every ambiguous framing or path spelling (obsolete folding, conflicting or duplicate lengths, transfer-coding tricks, upgrades, `CONNECT`, encoded separators, dot segments, double encoding — the path is canonicalized before classification and the admin denylist, and an ambiguous spelling fails closed), the query decoded once under its own grammar — order and duplicates preserved, malformed escapes and control bytes refused, reserved characters such as `:` and `/` as data — re-encoded canonically and never consulted by classification or the denylist, the upstream request rebuilt from the validated method, canonical path, canonical query, and buffered body under a fixed client-header allowlist (`Host`, `Authorization`, proxy, connection, forwarding, and framing headers stripped and rebuilt), response headers allowlisted and reframed after buffering, and a compressed upstream response refused rather than decoded, so the byte budgets bound real bytes. The relay is a driver child per Run with per-request and aggregate byte budgets, request, concurrency, redirect-hop, and upstream-timeout caps, alive for the agent phase only — gate jobs never see GitHub — and the harness bootstraps the client (gh config with `http_unix_socket` outside the checkout, `GH_HOST`, a sentinel `GH_TOKEN`). No in-container blocking exists: the agent owns its container, so the relay is the single enforcement point. The driver's container observation follows the substrate observation doctrine ([NODE-SUBSTRATE.md](NODE-SUBSTRATE.md)): docker's definitive no-such-object answer is evidence of absence (an exited `--rm` container), but any other inspection failure proves nothing — because a Run is expensive and its finished Output Proposal may already sit in the job dir, the driver retries the aliveness check bounded (a few attempts over seconds), then fails loud into the infra-failure lane, never inferring session completion from a failed read (grilling 2026-09-02).
- Gate steps run agent-authored code, so they execute as harness jobs on the credential-free side — never inside the credentialed driver.
- Every Run starts from a fresh checkout, fresh container, and fresh context. The checkout is a self-contained reference clone — git clone --reference <mirror> --dissociate — from a driver-owned node-local mirror: lazily created per repo, updated under a per-repo lock before each checkout, never mounted into containers, orphans swept at boot. Object transfer moves to local disk while every isolation invariant survives byte-identical (grilling 2026-08-16). Fleet git is operator-controlled, so checkout correctness is version-independent by construction (grilling 2026-08-28): every driver-side git invocation runs maintenance-free (auto-maintenance and auto-gc off — deterministic subprocesses, no detached background children mutating repos outside the mirror lock; git 2.54's auto-written commit-graph plus --dissociate corrupts Run checkouts, fixed upstream only in 2.55); the mirror stays commit-graph-free (the reference clone additionally ignores any graph, and sanitation deletes foreign graph state), with explicit under-lock repacking past a pack-count threshold replacing the auto-maintenance that is turned off — repack, never gc. The mirror is an optimization, never load-bearing for Run success: a failed reference clone falls back once to a full network clone (after an advisory telemetry event, the mirror left in place to heal lazily) before the pre-session infra lane; the node's git version is recorded in each Run's evidence bundle (heartbeat/node telemetry reporting of the git version is deferred), and git >= 2.55 is recommended, never required. No agent session state, build artifacts, or scratch files carry over between Runs; the enumerated carryovers are PR branch content at the Reviewer-designated resume commit plus the Reviewer's revised plan, and — for completion retries only — the working tree and pending Output Proposal (grilling 2026-08-16). Every retry is a new Run with a new `run_id`, so the GitHub Relay follows the same shape: a fresh job directory, socket, relay child, audit sink, spool lifecycle, and evidence bundle per Run, no relay state travelling with the enumerated carryovers, and the previous Run's audit log staying with that Run's evidence bundle (grilling 2026-09-03). The `schema_version` 1 → 2 upgrade — 1 is the value implemented today, and 2 the accepted successor the relay's implementation PR activates atomically with the layout, the renderer signature, the relay entry point, the bench behavior, and the contract's current-version wording — is deliberate at both ends: the driver never writes the retired Context Tree paths and refuses pre-work a version 2 job directory that contains one; version 1 job directories left from before the upgrade are orphans the boot sweep publishes under their own manifest and removes, never re-runs; and every mixed-version pairing — a version 1 manifest under a version 2 driver, a version 1 `format-output` CLI under a version 2 manifest, a manifest whose version and layout disagree — fails closed pre-work (grilling 2026-09-03). Warm caches are named volumes mounted into run containers. For an issue with Dependency Edges the driver derives the base at checkout — the chain re-resolved fresh, Chained Base when the go-ahead holds (grilling 2026-08-27).
- The Reviewer has the same shape: a node-resident reviewer driver executing review rounds as Review Runs (ephemeral containers).
### Monitoring (Control Node)

- The Control Node (TheOzolith's control/ component) receives Node Daemon heartbeats (60s, carrying node, stack, and labeled run-container status), Run events (worker, issue ref, attempt, phase: claimed / gate / pr-open / failed / escalated), and Reviewer review events, plus theozolith.error events from drivers and the Node Daemon (component, error class, message, size-capped context — advisory diagnostics under the channel invariant; depth stays in the node-local journal and evidence bundles), and renders the fleet dashboard. Heartbeat responses carry infrastructure commands (drain, recycle, update, rebuild) that the Node Daemon reconciles.
- Run progress telemetry: drivers emit theozolith.run.progress events — phase, elapsed time, token/tool-call counters, a size-capped transcript tail. The channel never carries secrets (beyond node-scoped pulls over TLS) or coordination authority; telemetry is advisory, size-capped at ingestion, and agent-authored text is untrusted wherever displayed. The control database is a cache, never the archive: evidence bundles are the sole durable audit trail; transcript tails live under a ~10GB budget with oldest-first eviction; terminal events are kept.
- Infrastructure commands are not coordination. The Control Node is authoritative for node and docker lifecycle and is the single writer of claim creation on GitHub; it never originates coordination beyond claim creation — it cannot approve, revise, or advance an issue. Janitorial liveness corrections are the enumerated exception.
- Coordination invariant: a coordination action is valid only once committed to GitHub. GitHub remains the sole source of coordination truth; the Control Node reconciles to GitHub, never the reverse.
- Control Node down = degraded mode: no dashboard, no new claims or review rounds (dispatch pauses; fallback is backlog), slower zombie cleanup. In-flight Runs finish and publish — drivers hold their own PATs for all non-claim GitHub writes.
### Quality gate

A first-party quality gate (in worker/) fronts every push: disposable worktree, test → docs → lint → push → PR → CI. It borrows the no-mistakes concepts but has no dependency on the no-mistakes binary.

- Safe mechanical fixes are auto-applied; structured findings are recorded.
- The gate never blocks PR creation: unresolvable findings are recorded in the Decisions Section of the best-effort PR.
- Adversarial review is not a gate step — it belongs to the Reviewer actor (see Review loop).
- The gate + Reviewer + CI + human triage replace a separate pull-side review-agent fleet.
- Evidence bundles give per-run traceability and per-agent metrics.
### Review loop

- The Reviewer is a separate long-lived actor (own node-resident driver, own GitHub identity, configured with a stronger model than the Implementer adapters; no self-grading by construction). It receives pr_ready PRs (without needs_human, under the round budget) through Control Node dispatch, and owns all post-PR state.
- Review Run inputs (grilling 2026-08-27): every Review Run gets a full sanitized PR-branch checkout with history — same reference-clone machinery and credential isolation as Implementer Runs, base ref fetched — plus the same GitHub read surface as an Implementer Run: the prompt carries the issue body and the PR body as the driver composed it (narrative plus Decisions Section — the artifact under judgment), and the judging agent reads every conversation surface, review, check, and any other issue or repository through the GitHub Relay (grilling 2026-09-03 — the input/issue/, input/pr/, input/deps/ Context Tree is retired). The driver supplies the PR's base commit and the cumulative changed-file list, computed driver-side from git against the PR's own base (also feeding the mechanical review signals); the truncated single-blob diff is retired — the judging agent runs git diff itself. Tests are a permission, not a step: the Reviewer may build and run anything in its workspace at its discretion, citing results in the verdict. Capability parity: inside the container a Review Run can do everything an Implementer Run can; the asymmetry is the Output Proposal schema (a verdict, never applied code) and the driver boundary. Stated consequence, not product-enforced: the Reviewer worker type's base image carries the workspace toolchain. For chained-base PRs, deviation/risk grading is relative to the chained base; the diff under review is the dependent's changes only. Judge isolation (applied to the workspace): agent-instruction artifacts — CLAUDE.md, CLAUDE.local.md, AGENTS.md, AGENTS.override.md, and the .claude/ / .codex/ trees — are removed from the review working tree at any depth and in any filesystem shape (symlinks unlinked, never followed), fail-loud pre-session: an unprovable removal means no session and no verdict-related GitHub write, and history stays reviewable through git. The name set is closed against codex's project-doc discovery (AGENTS.override.md, then AGENTS.md): the config key that would extend it, `project_doc_fallback_filenames`, is refused in the baked codex config at image bake and by the per-Run identity static checks, so the removed set is provably the effective set (adapter-level config-source isolation is #86).
- Verdicts:
  - Approve: add needs_human (keeping pr_ready) plus deviation:* and risk:* labels and an evidence-citing comment; the human stamps and merges. Approve means no revisions are needed at all — approve-with-nits is forbidden; a justified no-change (empty) PR earns approve.
  - Revise: increment attempt-N on the PR, remove pr_ready, comment a clear revised plan plus a resume commit ID (or cherry-picked commits), strip the issue claim, and re-queue the issue to plan_ready under explicitly delegated authority. Revise is unavailable on the final budgeted round — a final-round revise is an invalid verdict.
  - Escalate: blocked + needs_human when a human decision is required to move forward, or when the round budget is exhausted, with the evidence bundle link.
- Verdict emission: the Reviewer's agent proposes its verdict through format-output — enumerated approve | revise | escalate; invalid values and a final-round revise fail loud at write time, absorbing the validate-verdict harness job into the CLI (grilling 2026-08-16). Verdict content is audience-conditional: a non-final revise carries findings plus the amendment prompt (the revised plan the next Run executes); approve and every final-round verdict carry human-facing content — signals, decisions required, findings (grilling 2026-08-16). The Reviewer driver renders the published verdict comment (human-readable plus machine block) and applies all labels under its own identity (see Agent session contract). Any invalid verdict that still reaches the driver — missing, unparseable, or failing validation — escalates immediately: blocked + needs_human with a comment carrying the raw validation error and the evidence-bundle link. There is no driver-side retry: the completion-retry class is Implementer-only — a completed review session that never proposed a verdict is a compliance failure, escalated loudly (grilling 2026-08-16).
- Retries reuse the same PR and branch — never a duplicate PR. The next Run (any Implementer) claims the re-queued issue, detects the existing PR, checks out the Reviewer's resume commit, and executes the revised plan from fresh context. The Reviewer, as the stronger model, holds the decision-making power in this loop; Implementers execute plans. The resume commit and cherry-pick set come only from the latest machine verdict block in a PR-conversation comment whose author GitHub reports as OWNER or MEMBER, read by the driver with its own credential outside the GitHub Relay; a well-formed machine block from any other author, or in any other surface, is visible to the agent through `gh` and inert to the driver (grilling 2026-09-03; the OWNER/MEMBER machine-verdict boundary of 2026-08-17 stands while its visibility half is retired).
- For blocked + needs_human PRs, the human comments the decision and re-queues the issue to plan_ready (human authority).
- Reviewer downtime degrades throughput, never correctness: PRs queue at pr_ready; all state lives on GitHub, so a restarted Reviewer picks up cleanly.
- Review quality is measured per Agent config from evidence bundles (rounds per merged PR, re-litigated decisions, repeated dead ends).
### Human-in-the-loop lanes

| Lane | Where | Purpose |
| --- | --- | --- |
| Planning | Issue approval before plan_ready | Spec conformance, acceptance criteria quality |
| Review | Merge gate, findings queue | Risk-budgeted final review |

### Two-layer risk assessment

- Layer 1 — baseline, at planning: a risk:low|medium|high label applied together with plan_ready, judged on sensitive paths (auth, data model, migrations, public API), blast radius, and reversibility. The planning agent proposes; the human confirms.
- Layer 2 — review, at pr_ready: the Reviewer actor emits two PR labels plus a comment citing evidence. deviation:low|medium|high grades divergence from the plan (files outside the plan's footprint, unrequested behavior changes, new dependencies, size far beyond expectation). risk:low|medium|high is the Reviewer's own overall risk read of the change as implemented, independent of the baseline.
- The Reviewer — a separate actor, never the Implementer adapter — owns both grades, so the judgment is adversarial rather than self-assessed by the implementing side. Mechanical signals (diff size, files touched, dependency changes, sensitive paths) are computed and fed to the Reviewer as evidence; they inform the grades but are not an independent grader. The Decisions Section is a first-class review input: the Reviewer judges the decisions the Implementer made, not just the diff.
- The human combines the three labels (baseline risk on the issue; reviewer risk and deviation on the PR) to budget review depth (all low = skim; high on any axis = line-by-line). The final merge judgment is never automated.
### Agent swap boundary

- Contract: input = issue ref + repo checkout + repo-resident instructions ([AGENTS.md](../../AGENTS.md), [CONTEXT.md](../../CONTEXT.md), specs, skills). Output = branch pushed through the gate + evidence bundle. Everything between is a black box.
- One run-container image per Agent config, with the agent harness as its entrypoint. Vendor-specific flags, permissions, and invocation details are contained in the per-image adapter; Runs invoke the adapter's headless one-shot mode.
- [AGENTS.md](../../AGENTS.md) is the canonical instruction file; vendor files are generated copies, never sources — [CLAUDE.md](../../CLAUDE.md) carries a generated marker, while codex's AGENTS.md ships verbatim (the vendor format IS the canonical format).
- Skills are files in the repo; the knowledge machinery (knowledge/) generates per-tool placement and format (one compiler per tool — claude and codex ship, codex consuming the same skills format natively). Two scopes: global skills live in the private config repo and travel with the operator; project skills live in the target project's repo and travel with the project.
- No code-level LLM abstraction layer — it would couple to every vendor's API churn; the process-level boundary ages better. The swap boundary is the process/artifact contract above.
### Agent session contract (headless Runs, interactive Flight Deck)

- Every Run's agent process — an Implementer Run's implementing agent and a Review Run's judging agent — runs **headless**: the harness invokes the adapter's one-shot mode (e.g. `claude -p`), passing a constant **pointer prompt** at invocation — "work on the task specified in the mounted task file" — while the driver fetches the task and writes it into the job directory the container mounts, so the argv stays constant-size regardless of task size (2026-07-22); completion is process exit, with the hard agent timeout as backstop (reverses the 2026-07-15 always-interactive contract; prior design archived in Historical Context / Agent Session Contract — Always-Interactive (pre-2026-07-21)). Run containers are never attach targets; there is no mid-Run human steering. Headless only — no interactive debug mode for Runs.
- The **agent harness** — PID 1 of the run container, credential-free plumbing — launches the headless session, awaits process exit or timeout, then writes outputs and exits. The **driver** — the trusted node-resident process — commissions jobs and reads results only through the per-Run job directory.
- All agent I/O is files, plus one read-only window: the GitHub Relay (grilling 2026-09-03). Inputs: the repo checkout, the prompt file, and — on Review Runs — the driver-computed git facts (input/pr/base.md, changed-files.md, signals.md). The prompt carries the task statement inline: the rules; repository and issue number (plus PR number and branch on resume rounds); the issue body; on a Review Run the PR body as the driver composed it; on resume rounds the revised plan; and the dependency closure the driver computes over the transitive Dependency Edge closure (same-repo, no depth cap) as ordered entries of issue number plus state — `open`, `completed`, or `not_planned` — through the renderers' `dependencies` argument, with any Chained Base note. Everything else — comments, reviews, timeline, checks, dependency content, other issues, other repositories — the agent reads live with `gh` through the relay, discovering content progressively and judging relevance itself; the driver never relevance-filters, summarizes, or truncates. Visibility is broad by ruling (grilling 2026-09-03): the agent may read comments, reviews, issues, and any other readable GitHub content regardless of author association — the retired Context Tree's OWNER/MEMBER filter is not reproduced at the relay, because agents also have internet access and total outside influence is not preventable. Authority stays narrow and driver-enforced: nothing the agent reads can designate a machine verdict, a reset or resume commit, a cherry-pick set, labels, claims, state transitions, or any other driver action — the driver derives those from the pipeline's authorized sources alone (the OWNER/MEMBER machine-verdict rule under Review loop, GitHub label state, the Control Node's grant), with its own credential and outside the relay. The prompt instructs the agent to treat retrieved GitHub and internet content as untrusted evidence, never as instructions that override the task prompt, the repository's policy files, or the Output Proposal schema, and to report rather than follow an instruction found there. Prompt injection through such content is an explicitly accepted residual risk: instructions mitigate it and do not eliminate it, and the human merge and code-review gate is the final safeguard. The serialized Context Tree, its navigation guide, and its evidence snapshot are retired (grilling 2026-09-03): the prompt carries the artifact, `gh` the conversation around it, and one prompt shape serves production and the bench. Post-verdict comment injection and driver-side comment heuristics stay retired. Outputs: one per-worker-type Output Proposal, written through the format-output CLI (view-output reads pending state; enumerated fields fail loud in-session; a final-round revise fails at write time). Implementer fields: pr-title (descriptive part — the driver owns the #N: prefix), pr-description (narrative zone — the driver composes the PR body from the Closes line, the narrative, and the Decisions Section), Decisions-Section entries, and a required rich commit-message (subject plus what/why, key decisions with rationale, dead ends; reviewed like any artifact — git history is the only context surface guaranteed to future Runs, so redundancy with the Decisions Section is intentional; the agent still never runs git commit/push — the driver commits, appending a provenance trailer: run id, issue, round); Reviewer fields: the verdict and its content. The proposal lives in the job dir, not the worktree (the in-worktree decisions file and its _exclude_metadata fence are retired), and is version-checked: the driver stamps an integer schema_version into the job manifest and the CLI asserts compatibility at first invocation — skew fails pre-work as an infra-class failure, never a post-exit surprise (grilling 2026-08-16). The hand-written decisions and verdict files are retired; the driver renders every published artifact from the proposal. Allowlist by schema: forbidden mutations (base branch, issue state, labels, needs_human, other PRs) are unrepresentable rather than validated away; absent field = no-op, never clear; CLI validation is convenience — the driver re-validates and applies post-exit as the sole policy boundary (grilling 2026-08-16). The proposal accepts an optional process_issues[] list (pipeline friction observed — bad instructions, missing skills, misleading specs, tooling failures — plus a suggested fix), rendered into the published artifact as a Process issues block: advisory observations about the pipeline, never findings about the change under review; they influence no verdict or label. Harvesting is manual in V1 — read at merge, with fixes flowing through grilling or ordinary issues; auto-aggregation and agent-filed issues are rejected (reserved-Planner territory; the PR is the durable record, not the control DB). No pipeline state is ever parsed out of model prose.
- Credential isolation: agent processes hold no GitHub credentials — no tokens in their environment (the `GH_TOKEN` in a run container is a sentinel the relay overwrites), no tokened remotes in their worktrees. Drivers hold the PATs and perform all GitHub writes; reads reach the agent only through the GitHub Relay, which injects a dedicated credential — a required `GITHUB_READ_TOKEN` slot on every driver-bearing worker type, never the driver PAT under any condition (grilling 2026-09-03) — so the transition-authority matrix is enforced by construction: a compromised or prompt-injected agent session can read what the scoped credential can read, corrupt only its own output files, and never write GitHub state. V1 supports GitHub.com only: the slot must hold a GitHub.com fine-grained personal access token — the driver refuses a classic, OAuth, App, or unrecognized token form by name at boot, and there is no classic-token fallback — and a configured GitHub Enterprise Server host is refused at config load and again at driver boot, before any preflight, relay, container, claim, or Review Run, as unsupported until a future relay-host contract. The credential's minimum permission matrix is operator doctrine, not product-enforced: a fine-grained PAT with read-only Metadata, Contents, Issues, Pull requests, Checks, Commit statuses, and Actions on the bound repositories plus public-repository read. The driver's boot preflight proves it before any claim: identity, the Bound Workspace, and one representative read per promised capability against its default-branch commit — empty issue, PR, check, status, and workflow collections pass; an empty repository or a missing default branch is refused pre-work as a workspace condition (a worker cannot check out or run against it), never reported as a missing capability; a 401 is the token, a capability-specific 403 is that capability, a rate-limit 403 is named as such; and the boot report lists each capability's own result — verified, unavailable, or not-probed — never an "all verified" summary when the commit-scoped probes did not run. The preflight is driver-originated, so its record is the boot report (per probe, outside any Run's audit sink, never a credential byte, header, or response content), and authorization failures fail loud naming the capability and host, never a credential byte. Stated honestly: the preflight proves the reads the product needs and cannot prove the token lacks unrelated write grants. A token provisioned as required is defense in depth behind the relay's classifier — a request that evades classification meets a credential that cannot write; a broader token the operator supplies makes the relay's classifier and denylist the write barrier, and the product claims nothing stronger in any message, document, or evidence field. The token's repository scope is also the agent's data-access and disclosure scope (grilling 2026-09-03): an agent may place anything it can read into its working tree, transcript, evidence bundle, PR description, or the automatically created target PR before any human merge — so each Stack binds a token scoped to its target repository where GitHub allows it, a token spanning several private repositories is bound only when every covered repository belongs to the same permitted disclosure domain as the target and its evidence storage, and an operator never binds a token that can read information which may not be exposed to the target repository or its evidence. Operator doctrine, because GitHub cannot prove the absence of broader grants. GitHub's rate limit is per account, so a separate budget needs a separate machine account — the relay's per-Run budgets are the product's protection.
- Run diagnostics is read-only: progress telemetry (phase, elapsed time, counters including the relay's `gh` call count, transcript tail) plus the evidence-bundle transcript, captured from the headless session's structured output stream — which also supplies token usage — and the relay's `gh-audit.jsonl` (grilling 2026-09-03). The audit log is a security record, so it is written only in driver-owned storage the run container cannot write, replace, link, or name, through a descriptor opened once with exclusive creation — and it is written ahead of credential use: after classification and budget reservation the relay appends and syncs an intent record (sequence, classified operation, redacted routing metadata, decision, reserved budgets), and only that durable write authorizes opening the upstream connection with the credential; each followed redirect hop is authorized the same way by its own durable redirect-intent record (sequence, hop number, canonical target path, redacted query) before the credential is attached to it; and a correlated completion record (outcome, upstream status, actual byte counts, the request's redirect decisions as one bounded summary array of at most four entries — three followed hops plus a fourth redirect refused at the hop limit — and no routing metadata) follows the upstream operation — one intent, zero to three redirect-intents, and one completion per request, and at most one terminal record per Run, written once at shutdown after acceptance has ended and the accepted work has drained. Every record kind has an explicit schema with mandatory fields, and an intent or redirect-intent is serialized and size-checked before it authorizes anything (grilling 2026-09-03): a record that would exceed the per-record cap is never truncated — the request is refused as unrepresentable before any upstream I/O with a bounded refusal record, a hop likewise with its refusal in the completion summary — so a record that exists says what it authorized. The invariant covers agent-originated relay requests; the driver's own boot preflight is recorded in the boot report instead. A failed intent or redirect-intent write means no connection, no hop, and no credential; a failed completion write, a short write included, leaves the intent and redirect-intent records as proof of use and puts the relay in an audit-unavailable state — still answering the socket, forwarding nothing, writing nothing more, not even a terminal record, whatever ends acceptance later (a connection-budget exhaustion still closes the listener and writes no terminal); the relay reports the failure to the driver outside the sink, and the summary's accounting rests on that report. Capacity for the intent, three redirect-intent, and completion records is reserved per request before authorization (the terminal record's once per Run), so no hop can be sent and no upstream call can finish without room for its record; exhausting the audit file cap stops new authorizations and new per-request records while reserved work finishes, keeps the relay answering with the stable refusal, and is recorded as a flag in the terminal record at shutdown, never by writing that record early. The sink is published into the evidence bundle only after the agent phase ends, copied byte-for-byte and digested before it is parsed, with a summary — record and byte counts, digest, budgets hit, the counters (accepted, busy-refused, no-request, request lines seen, and request lines charged against the 2,000-request budget) and exhaustion flags copied from a present terminal record and reported unknown — never zero, never reconstructed from parsed records — when that record is missing or malformed, the termination reason (clean, exhausted, killed, crashed, orphaned) read from the relay's exit report and exit status, the terminal record's state (present, missing, or malformed) read from the bytes, and the audit-failure report when there is one — three separate facts, and a Run is healthy only when all three say so — the offset of any unparseable tail, and request counts by outcome: complete, refused before any upstream I/O, incomplete (an intent left without a completion by a reported audit failure; a torn completion counts here, never as complete), and indeterminate (an intent with neither completion nor audit-failure report — the relay died mid-request — always distinguishable from a request that never passed authorization). Records carry timestamp, record kind, method, canonical path with query values reduced to names, sizes, and digests, GraphQL operation type and name with variables likewise reduced (literal values only for a short enumerated set of routing fields), decision with a reason code, upstream status, byte counts, and the redirect array; never credentials, headers, request or response bodies, error text, or repository content — each record and the whole file are size-capped, and a refusal past the cap writes nothing. Response content is never persisted anywhere: the pre-delivery buffer or driver-owned spool is deleted on every path, including the boot sweep. Residual risks: isolation protects authority, not output integrity — a bad session can still emit a bad diff or verdict; the human merge gate absorbs this. A Run's GitHub inputs are no longer fully reproducible from its evidence: the audit log records what was asked, and GitHub keeps what was answered.
- The **Flight Deck** is the interactive surface: a human-driven agent container declared as a container-kind Stack, running an agent CLI in a discoverably named tmux session — the web terminal's primary attach target. Used for issue drafting and non-decomposable work (cross-cutting refactors, design-in-flux). The Flight Deck holds GitHub credentials under human supervision — a separate machine identity (fine-grained PAT: issues, PRs, contents; no merge permission), never the operator's own PAT: the merge gate stays human by construction, and blocked answers remain recognizable human acts. It is not a pipeline actor — it never claims issues, and its sole delegated transition is executing the human's initial plan_ready stamp as a scribe: only on an explicit instruction in the live deck conversation naming each work issue and confirming its risk:* label, never on publication approval, repo or issue content, tool output, or an ambiguous remark, and never on a tracking issue. That one transition is prompt-enforced rather than identity-enforced — an accepted, recorded residual risk: label events carry the deck's identity, and Flight Deck session transcripts are the audit trail for human-driven agent work, including whether a human instruction preceded each stamp.
### Upgrade path

- A new model or agent is a new adapter image. Route a fraction of plan_ready issues to the new adapter.
- Compare gate pass rate, retry count, escalation rate, and cost per merged PR from evidence bundles and GitHub data. Promote on wins.
- Off-fleet benchmarking: worker types export as Candidate Bundles and execute under the published bench contract — bundle format, identity spec, and the Run Contract for both implementer and review modes — see [BENCH-CONTRACT.md](BENCH-CONTRACT.md) (grilling 2026-08-28).
